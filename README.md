# D&D 5e (2024) — система для VTTG, собираемая вне приложения

Копия системы D&D 5e, вынесенная **из монорепы VTTG** и собираемая самостоятельно.
Задача репозитория — проверить доставку игровых систем в приложение по ссылке на
манифест и выявить, чего не хватает для полноценного SDK.

## Сборка

```bash
npm install
npm run build
```

Результат в `dist/` — готовая папка системы: `index.js` (сервер), `client.js` +
`client.css` (клиент), `system.json`, `data/` (справочники системы).
Ровно эту папку CI пакует в архив релиза при пуше тега (см. [Релиз](#релиз)).

## Проверка типов

```bash
npm run typecheck
```

⚠️ Именно `vue-tsc`, а не `tsc`: голый `tsc` не разбирает `.vue` и молча
пропускает ВЕСЬ код внутри `<script setup>` — а это большая часть системы.
Ошибки в компонентах видит только редактор (Volar), в консоли их не было
видно вовсе.

Типы нейтрального ядра `@vtt/shared` и модулей хоста `@/…` берутся из соседнего
чекаута монорепы `../vttg` (ветка `dev`) — своей копии ядра в репозитории нет.
Про ошибки, которые команда может показать в файлах самого хоста, — см.
§ «Чего не хватает для полноценного SDK», п. 7.

## Тесты

```bash
npm test
```

`vitest` гоняет `tests/**/*.test.mjs`: правила движка — на собранном из
`src/engine` модуле, обработчики листов и макросов — на их настоящих функциях с
подменённым окружением хоста. Движок в тестах собирается с настоящим ядром
`@vtt/shared` из соседней папки `../vttg` (путь — `hostSharedEntry` в
`tests/helpers/engineBundle.mjs`), а часть тестов читает оттуда же файлы хоста
(например, `projectileStore`), поэтому монорепо должно лежать рядом — на `dev`,
не старее VTTG 0.9.533: типы и тесты опираются на её контракт (`moveArea`,
`getCombatRound`, `applyMovementEffects`).
Тесты — четвёртая проверка вместе с `lint`, `typecheck` и `build`.

## Локальная установка (без релиза)

Чтобы проверить правки в живом приложении, релиз выпускать не нужно: номер версии
не переиспользуют, и каждая проверка стоила бы публичного релиза. Одна команда
собирает систему и подкладывает её прямо в установленную копию VTTG:

```bash
npm run install:local                     # сборка + установка
npm run install:local -- --skip-build     # установить уже собранный dist/
npm run install:local -- --version 0.5.3  # пометить сборку своим номером
npm run install:local -- --data "D:\путь\к\данным VTTG"
```

Скрипт делает то же, что установщик приложения: кладёт содержимое `dist/` в
`<данные установки>/systems/dnd5e-2024/` (заменяя папку целиком через `rename`) и
**заново подтверждает доверие** — VTTG пинит доверие к SHA-256 кода системы, и
после подмены файлов она снова считается недоверенной: код не исполняется, а
`/system-assets/<id>/*` отдаёт 404. Хэш пересчитывается тем же алгоритмом, что в
приложении, и записывается в `<данные установки>/installed-systems.json`.

Корень данных определяется так же, как в приложении: указатель
`%APPDATA%/VTTG/data-location.json`, а без него (dev-режим) — `%APPDATA%/VTTG`.
Переопределяется флагом `--data` или переменной `VTTG_DATA_DIR`.

> **После установки VTTG нужно перезапустить:** серверный `index.js`
> импортируется один раз за запуск, иначе в памяти останется прежний код.

Что важно помнить:

- **нужен VTTG 0.9.503+** — серверный `index.js` берёт ядро `@vtt/shared` у
  приложения; в более старом VTTG установленная сборка не загрузится
  (`ERR_MODULE_NOT_FOUND`), и система там перестанет работать. То же относится к
  `npm run dev`. Спасброски зон, аур и ходов запросом владельцу работают с
  VTTG 0.9.510 — на более старом сервер бросает их сам; зона на месте шаблона
  заклинания и ауры в серверных бросках — с VTTG 0.9.516. Срабатывания эффектов
  опираются на контракты следующих версий: участие в бою для лимита «раз в
  ход» — 0.9.517, события урона от боевого снимка — 0.9.518, ход наложившего —
  0.9.519, конец каста (концентрация) и срабатывания на броске атаки на сервере
  — 0.9.520, вход и выход у ауры по шагам маршрута — 0.9.521, соседи по сцене
  для «всем в радиусе» — 0.9.523, действующее отношение фишки
  (`withTokenDisposition`) — 0.9.525, кубики бросков правил в чате — 0.9.528,
  принудительное перемещение фишки (`moveToken`) — 0.9.532, сдвиг зоны
  (`moveArea`), номер раунда (`getCombatRound`) и события перемещения носителя
  (`applyMovementEffects`) — 0.9.533, галочка над выбранной целью — 0.9.546,
  запрос с адресатом «ведущий» (`recipient: 'gm'`) — 0.9.547, сверка значков
  состояний на каждой правке записи (`onWorldItemsChanged`) — 0.9.575. Сам
  `compatibility.minimum` сейчас 0.9.577;
- **версию в репозитории руками не поднимают** — это делают только pre-commit
  (патч на каждый коммит) и `npm run release` (см. ниже). Чтобы отличить
  локальную сборку от релиза в списке систем, передайте `--version X.Y.Z`: номер
  попадёт ТОЛЬКО в собранный `dist/system.json`, как это делает CI со штампом из
  тега;
- канал обновлений (`system-sources.json`) остаётся прежним: если на GitHub
  появится релиз новее, кнопка «Обновить» перезатрёт локальную сборку;
- вернуться на официальную версию можно, переустановив систему по ссылке на
  манифест из интерфейса.

## Разработка: правки видно сразу (`npm run dev`)

Когда VTTG запущено в dev-режиме, систему не обязательно переустанавливать руками
после каждой правки. Отдельным терминалом:

```bash
npm run dev
npm run dev -- --no-reload             # без автоперезагрузки страницы
npm run dev -- --data "D:\путь\к\данным VTTG"
```

Скрипт держит две инкрементальные сборки (клиент — Vite, сервер — esbuild) и
после каждой пересборки делает то же, что `install:local`: кладёт `dist/` в папку
установленной системы и заново подтверждает доверие к коду. Цикл — 1–2 секунды на
правку компонента.

**Страницу перезагружать не нужно**: в установленную копию `client.js`
дописывается опросчик, который следит за файлом-штампом `dev-stamp.json` в папке
системы и перезагружает страницу, когда тот сменился. Приложение для этого править
не пришлось — штамп отдаёт та же раздача `/system-assets/`, что и сам бандл. В
`dist/` и в релиз этот код не попадает (дописывается уже после копирования), а
вернуть чистую сборку можно в любой момент через `npm run install:local`.

> ⚠️ **Страницу открывать с ПОРТА МИРА** — кнопкой «открыть в браузере» в списке
> миров (`http://localhost:<порт мира>`). В окне приложения адрес — Vite-сервер
> хоста (`:3000`), а он раздачу `/system-assets/` не проксирует. На порту мира
> работает и то, и другое: мир-сервер отдаёт файлы системы сам, а всё остальное
> проксирует в Vite вместе с его HMR.

Чего watch не умеет и уметь не может:

- **Серверная часть системы (`src/server`, серверная сторона движка) требует
  перезапуска VTTG.** Приложение импортирует `index.js` системы один раз за запуск
  процесса, а ESM-кэш Node не сбрасывается. Скрипт печатает про это отдельную
  строку, когда пересобралась именно серверная часть.
- **Справочники из `src/engine/*.json` (категории снаряжения, свойства, базовые
  виды) тоже требуют перезапуска VTTG.** Мир-сервер читает их с диска один раз и
  держит в памяти (`loadCachedJsonFile` в `systemDataModule.ts`): новый файл
  watch уже положил, а форма до перезапуска показывает старый список, и новое
  значение в выпадающем списке видно сырым ключом (`potion`).
- **Это не HMR**: состояние окон теряется, как при F5. Настоящий HMR упирается не
  в нашу сборку, а в контракт загрузчика систем — см. § «Чего не хватает для
  полноценного SDK», п. 10.

Если бандл вышел негодным (те же проверки клиента и сервера, что и в релизной
сборке), скрипт
печатает причину и **не** кладёт его в приложение — в папке остаётся прежняя
рабочая сборка.

## Версия

Номер версии живёт в четырёх местах (`package.json`, `system.json`, поле
`readonly version` движка и сам git-тег). Руками его не правят — разъезжается:
менять номер разрешено только двум скриптам, и оба пишут его сразу везде
(общий код — [`scripts/lib/version.mjs`](scripts/lib/version.mjs)).

### Патч растёт сам при коммите

Каждый коммит в `main` (и в `dev`, если такая ветка появится) поднимает patch на
единицу: [`.githooks/pre-commit`](.githooks/pre-commit) вызывает
[`scripts/bump-version.mjs`](scripts/bump-version.mjs) и добавляет файлы с номером
в тот же коммит. Так каждая сборка отличается номером от предыдущей — иначе в
списке систем VTTG не видно, какой именно код туда попал, а обновление по
манифесту (сравнение номеров) не срабатывает вовсе.

Хук включается сам при `npm install`: скрипт `prepare`
([`scripts/install-git-hooks.mjs`](scripts/install-git-hooks.mjs)) выставляет
`core.hooksPath=.githooks`. Без этой настройки git папку `.githooks` не видит, и
версия молча перестаёт расти.

Что важно помнить:

- **на побочных ветках патч не растёт** — там правки ещё не факт что доедут до
  `main`, а разошедшийся номер даёт конфликт при мёрже сразу в трёх файлах;
- **`git commit --no-verify` подъём пропускает** — так делает и сам релизный
  скрипт, иначе тег `vX.Y.Z` указывал бы на код с версией X.Y.Z+1;
- **коммит с перечислением путей (`git commit <файл>`) тоже пропускается**, и хук
  говорит об этом вслух: такой коммит git собирает во временном индексе, поэтому
  номер попал бы в коммит, но в рабочем дереве остался бы «изменённым»;
- **слияния и `git revert` хук не трогает** — pre-commit на них не запускается.
  Откат коммита откатывает и номер (он лежит в том же коммите); следующий обычный
  коммит поднимет его снова, а занять уже выпущенный номер не даст релизный
  скрипт — такой тег уже существует;
- **файлы с номером добавляются в коммит целиком:** если в `package.json` были
  ещё и незаиндексированные правки, они уедут вместе с номером — скрипт про это
  предупреждает отдельной строкой.

## Релиз

Релиз выпускается **одной командой** — `npm run release`. Без аргумента он
выпускает номер, уже накопленный коммитами: ничего не переписывает, а вешает тег
на текущий коммит. Аргумент нужен, когда релиз обязан отличаться от накопленного
патча:

```bash
npm run release              # выпустить текущий номер (тег на HEAD)
npm run release -- patch     # 0.0.8 → 0.0.9  — фиксы
npm run release -- minor     # 0.0.8 → 0.1.0  — новые возможности
npm run release -- major     # 0.0.8 → 1.0.0  — несовместимые изменения
npm run release -- 0.2.5     # явный номер
```

С аргументом скрипт поднимает номер во всех трёх файлах и делает отдельный
коммит `chore(release): vX.Y.Z`; без аргумента релизного коммита нет.

### Порядок действий

1. **Влить всё в `main`** и убедиться, что рабочее дерево чистое: скрипт
   откажется работать с незакоммиченными изменениями и с любой другой ветки.
2. **Запустить `npm run release`** — без аргумента, если выпускаем накопленный
   патч, или с шагом по SemVer (`minor` / `major` / явный номер), если релиз
   должен отличаться сильнее. Скрипт сам:
   - проверит чистоту дерева, ветку `main` и что такого тега ещё нет;
   - поднимет версию в `package.json`, `system.json` и `src/engine/dnd5eSystem.ts`
     — только если шаг указан;
   - прогонит `npm run build` — те же проверки бандла, что и в CI; если бандл
     негодный, изменения версии откатываются и релиза не будет;
   - создаст аннотированный тег (и коммит `chore(release): vX.Y.Z`, если номер
     менялся).
3. **Опубликовать.** Без флага скрипт останавливается на локальном теге и печатает
   команду — это последний шанс передумать, потому что публикация видна всем:

   ```bash
   git push origin main --follow-tags
   ```

   Либо сразу: `npm run release -- --push`.
4. **Проверить** вкладку Actions и созданный Release.

> Отдельно поднимать `compatibility.minimum` / `verified` в `system.json` нужно
> руками — когда система начала использовать новые API хоста или проверена на
> новой версии VTTG. Скрипт эти поля не трогает.

> ⚠️ `compatibility.minimum` сейчас `0.9.577` — не ниже текущей VTTG. С 0.9.503 серверный `index.js`
> импортирует ядро `@vtt/shared` у приложения (§ «Чего не хватает для
> полноценного SDK», п. 1), а на VTTG старше он падает с `ERR_MODULE_NOT_FOUND` —
> система не загружается вовсе. С 0.9.510 спасброски зон, аур и ходов уходят
> запросом владельцу через сервер (п. 19): на 0.9.503–0.9.509 система
> загрузилась бы, но бросала бы их сама, мимо выключенных авто-спасбросков. С
> 0.9.516 заклинание оставляет зону на месте шаблона
> (`custom-area:create-for-entity`), а ауры попадают в серверные спасброски и урон
> на ходу (`resolveAmbientEffects`): на старом хосте зона не создастся, а «Аура
> защиты» не прибавится к спасброску зоны. С 0.9.517–0.9.521 работают
> срабатывания эффектов (§ «Чего не хватает», п. 20): без них урон не будит
> «получил урон» и «хиты упали до 0», концентрация не заканчивается, «ход
> наложившего» молчит, а спасбросок и урон на броске атаки не выполняются. С
> 0.9.525 действующее отношение фишки система берёт у ядра
> (`withTokenDisposition` из `@vtt/shared`, § «Чего не хватает», п. 21): на
> старом хосте функции нет, и «Тактика стаи», отбор «всем в радиусе» и входы в
> ауры падали бы. С 0.9.528 кости урона и лечения срабатываний ядро пишет в
> чат карточками бросков (`chatRolls`), и сводка их итог больше не повторяет:
> на старом хосте зелье лечило бы молча. Пока VTTG 0.9.528 не опубликована,
> релиз системы выпускать нельзя. С 0.9.532 ядро ставит фишку по толчку
> (`moveToken`), с 0.9.533 сдвигает зону (`moveArea`), отдаёт номер раунда
> (`getCombatRound`) и зовёт систему на перемещении носителя
> (`applyMovementEffects`). Все четыре необязательны: на старом хосте система
> загрузится, но толчок, сдвиг зоны, расписание «на раунде N» и срабатывания
> «прошёл N футов» молча не выполнятся. С 0.9.547 запрос можно адресовать
> ведущему (`recipient: 'gm'`): на старом хосте поле срезается, и просьба
> «разрешить применение дальше касания» уходит владельцу получателя — ведущий её
> не увидит, а ответ не ведущего система считает запретом. С 0.9.575 ядро зовёт
> `onWorldItemsChanged` и нормализацию на каждой правке записи — без этого
> значки состояний по правилу («Окровавленный») сверялись бы только при загрузке
> мира. С 0.9.601 условие ауры на накрытом несёт эффект ауры целиком и носителя
> ауры наложившим, а система правит его хуком `shapeAuraCondition`
> (необязателен): на старом хосте запись остаётся урезанной, и аура с условием
> броска («Ореол: помеха исчадиям и нежити») действует на любого в ней
> безусловно, как раньше. Сейчас `minimum` — 0.9.592, `verified` — 0.9.596
> (`system.json`); на VTTG 0.9.601 и новее отметка `verified` ещё не поднята.
> По той же
> причине `npm run install:local` и `npm run dev` в установленный VTTG старше
> 0.9.503 ломают там систему — проверять в dev-сборке VTTG из `../vttg`.

Дальше всё делает CI ([`.github/workflows/release.yml`](.github/workflows/release.yml)):

- `scripts/stamp-manifest.mjs` проставляет в `system.json` `version` (из тега) и
  ссылки `url` / `download` / `manifest` / `readme` / `bugs` / … (из адреса
  репозитория). Поэтому значения этих полей в закоммиченном `system.json` — лишь
  заготовка: при релизе они перезаписываются.
- `npm run build` собирает `dist/` и прогоняет проверки бандла (см. «Проверка
  бандла»).
- содержимое `dist/` пакуется в `<id>.zip` (`system.json` — в корне архива).
- по тегу создаётся GitHub Release: к нему прикладываются архив и отдельный
  `system.json`. Канал обновлений — постоянная ссылка
  `releases/latest/download/system.json` (поле `manifest`): по ней VTTG видит
  новые версии.

### Откат

- **Тег ещё не запушен:** `git tag -d vX.Y.Z`, а если был релизный коммит (релиз
  с шагом) — ещё и `git reset --hard HEAD~1`. Нужные команды печатает сам скрипт.
- **Релиз уже опубликован:** удалить тег локально и на origin
  (`git tag -d vX.Y.Z && git push origin :refs/tags/vX.Y.Z`), затем удалить сам
  Release на GitHub. Номер версии не переиспользуют — выпускают следующий.

## Структура

| Папка | Что это |
|-------|---------|
| `src/engine` | движок правил D&D (переехал из `shared/src/system/dnd`) — **часть системы**, не SDK |
| `src/client` | интерфейс: листы, модалки, карточки, типы предметов, макросы |
| `src/server` | серверная точка входа системы |

## Манифест

Ключевые поля `system.json`: `manifest` (стабильная ссылка на свежий манифест — по
ней проверяются обновления), `download` (архив конкретной версии), `compatibility`
(минимальная и проверенная версия VTTG), `authors`, `url`, `license`, `readme`,
`bugs`, `changelog`, а также поля VTTG: `dataPath`, `client`, `defaultDistanceUnit`.

## Система эффектов

Активный эффект — общий знаменатель постоянных правок листа: механика черты и
дары предыстории при применении разворачиваются в обычный эффект
(`buildFeatGrantEffect`), защиты вида — тоже (`buildSpeciesDefenseEffect`).
Своего пути расчёта у них нет. Вне эффектов остались двое: скорость и тёмное
зрение вида (`speciesGrants`) и чувства черт (`actorSenses`) — их считают на лету
по набору особенностей листа, а шапка сливает с чувствами эффектов по большей
дальности.

Список того, что движок понимает, — закрытый, и правило у него одно в обе
стороны: **форма предлагает ровно то, что движок умеет вычислить, а всё, что
движок умеет, форма предлагает**. Разошлись — эффект выглядит настроенным и
молча не работает.

Считает эффекты трёхфазный конвейер `effectPipeline`: базовые значения листа →
изменения и флаги → производные (спасброски, навыки, КД, Сл заклинаний).

На носителя действуют его собственные эффекты и эффекты вложенных записей —
надетых предметов и черт существа (`listCarriedEffectEntries`: без эффектов «на
цели» и аур наружу). Вкладка «Эффекты» листа показывает вторые разделом «От
снаряжения и особенностей» с источником и без переключателя: они действуют,
пока есть запись. Строка модификатора с прибавкой 0 или множителем 1
(`isNoOpEffectChange`) подписана предупреждением: преимущество и помеха — особые
правила, а не модификатор.

### Что задаёт эффект

| Часть | Сколько | Где список |
|---|---|---|
| Ключи изменений (`changes`) | 64 | `EFFECT_TARGET_SUGGESTIONS` |
| Режимы изменения | 6 | `EFFECT_CHANGE_MODE_LABELS` |
| Флаги | 206 | `EFFECT_FLAG_LABELS` |
| Условия | 98 | `EFFECT_CONDITION_SUGGESTIONS` |
| Подсказки значений | 35 | `EFFECT_VALUE_SUGGESTIONS` |

Ключи по группам: `ability.*` (6), `save.*` (6 и `save.concentration` — только
спасброски концентрации), `skill.*` (18), `abilityCheck` (все проверки
характеристик, навыки тоже), `deathSave` (спасброски от смерти), `attack.*`
(4), `attacksAgainst` (прибавка атакующему от защитника), `damage.*` (5),
`movement.*` (5), `sense.*` (5), `terrain.*` (1) и одиночные — `armorClass`,
`initiative`, `proficiencyBonus`, `spellSaveDC`, `hitPoints.max`,
`critThreshold`, `creatureType`. Пустой ключ
допустим: строку завёл готовый пункт меню ради условия, а что менять — автор
назовёт сам; на расчёт такая строка не влияет.

Для `attack.melee`, `attack.ranged`, `attack.spell`, `save.*`, `abilityCheck` и
`skill.*` режим `add` принимает кубиковые бонусы, например `1d4` у «Благословения»
или `skill.perception` = `1к4` у «Наставления». На одну проверку
допускается суммарно не более 1000 бонусных костей, не более 1 000 000 граней
у каждой кости; отрицательные кости тоже расходуют общий предел. Неподдержанная
формула или формула, превышающая оставшийся предел, пропускается целиком. Поддержаны
суммы и разности костей и целых чисел, русская запись `к`/`д` и переменные
носителя. Такие бонусы не меняют постоянные числа листа: кости бросаются при
каждой атаке, спасброске или проверке, в том числе отдельно для каждой атаки
снаряда. Проверка навыка собирает кости `abilityCheck` и своего `skill.*`
(`getSkillCheckBonusKeys`) — на листе, в статблоке и в «вырваться». Что сейчас
влияет на бросок навыка (кость, преимущество, помеха, помеха от доспеха), лист
показывает значком у навыка (`listSkillEffectInfluences`). Кость у ключа, где
её никто не бросит (`armorClass`, скорость), форма эффекта помечает ошибкой
(`isRollTimeDiceKey`). Режим «Вычесть (−)» есть только в форме: в данных это
`add` со знаком минус у всей формулы (`effectChangeSubtract`), так что сайт и
выгрузка компендиума нового режима не видят.
Преимущество и помеха относятся только к d20; крит определяется по оставленной
d20, а не по сумме с бонусной костью. Для «Благословения» нужны девять changes
с `mode: add`, `value: 1d4`: три ключа атаки и шесть ключей спасбросков.

`damage.all` — «весь наносимый урон»: одна строка вместо трёх ключей
(`matchesDamageKey`). «Метка охотника» прибавляет свои кости и к рукопашной
атаке, и к дальнобойной, и к заклинанию.

`damage.weapon` и `attack.weapon` — «только этим предметом»: строка работает
лишь у эффекта, который ЛЕЖИТ на предмете, и лишь когда бьют именно им
(`changeReachesItem`). Предмет запоминается при СБОРЕ эффектов
(`listCarriedEffectEntries` ставит `carriedItemId`), поэтому эффект уезжает в
чужие руки вместе с вещью. На листе такие строки не считаются вовсе
(`isItemScopedKey` в `isRollTimeDiceChange`): каким предметом будут бить, лист
не знает, и прибавка досталась бы всем атакам носителя. Так собрано
«Магическое оружие».

`creatureType` меняет ТИП существа, пока эффект действует
(`resolveEntityCreatureType`): «Обращение в зверя» перебивает и статблок, и
выбор мастера, а гейты урона «только по нежити» и условия `self.creatureType`
смотрят на новый тип.

`sense.darkvision` — механика сцены: итог (база токена плюс эффекты умений и
черт, надетые и настроенные предметы, заклинания) система отдаёт хуком
`resolveEntityVision` контракта `VttSystem` (`src/engine/entityVision.ts`), и
сцена приложения считает по нему туман и видимость. Настройки токена система
не переписывает: снятый эффект сразу пропадает и со сцены. Эффект, давший
тёмное зрение токену с выключенным зрением, зрение включает. База тёмного
зрения — зрение токена: «Добавить 60» даёт +60 к тёмному зрению вида или 60 без
него, «Повысить до 60» — не меньше 60. Хук работает с ядром, которое его знает
(см. § «Чего не хватает», п. 12); старое ядро его просто не зовёт.

**Свет от эффекта** (`light`, `engine/entityLight.ts`) — «Корона света»,
«Священное оружие», «Сияющая душа», светящиеся предметы: пока эффект
действует, носитель излучает яркий свет `bright` и тусклый «ещё на» `dim`
(фт, как в тексте правил), с цветом и анимацией света фишки. Свет не
складывается: итог носителя — сильнейший из действующих эффектов (своих,
надетых предметов, черт существа) по дальнему краю, при равенстве — по
яркому. Свет фишки, который ставит ведущий, система не переписывает: эффект
светит поверх, и если фишка светит не слабее — ответ пустой. Итог отдаёт хук
`resolveEntityLight` по образцу `resolveEntityVision` (ответ — излучатель
фишки `LightEmitter`: `brightRadius` и `dimRadius` до дальнего края),
кэшируется по объекту сущности и меняется только вместе с набором
действующих эффектов — лишних перерисовок нет. Ядро зовёт хук с VTTG 0.9.580
(§ «Чего не хватает», п. 33); на старом ядре свет виден только в описании
эффекта, на сцене — нет.

**Для сайта (core-app):** поле `light` — `{ bright, dim, color?, animation? }`:
радиусы в футах (0–1000, хоть один больше нуля), `dim` — тусклый свет ЗА
ярким, `color` — `#rrggbb`, `animation` — `pulse` | `flicker` | `torch` |
`strobe` (нет — ровный). Пример `{"bright":30,"dim":30,"color":"#ffeeaa"}`.
Старая система поле отбрасывает.

Прочие `sense.*` (слепое, истинное зрение, чувство вибрации, телепатия) —
СПРАВКА, а не механика сцены: у зрения токена в приложении для них нет полей.

`terrain.movementCost` — правило ЗОНЫ, а не листа, и это единственный ключ,
который трёхфазный конвейер не считает вовсе. Его читает `resolveAreaTerrainCost`
из эффектов пользовательской области сцены и отдаёт ядру через
`VttSystem.getAreaMovementCost`: число — во сколько раз дороже клетка под зоной
(`override: 2` — труднопроходимая местность, меньше единицы — «дорога»,
пересечение зон перемножается). Повешенный на ЛИСТ, этот ключ не делает ничего —
персонажу труднопроходимость задаёт зона, под которой он стоит. Обратная сторона
правила есть и на листе, но флагом: `terrain.ignoreDifficult` отключает
труднопроходимость для носителя целиком.

Иммунитеты к состояниям и защиты от урона — не изменения: первые лежат в поле
`conditionImmunities`, вторые во флагах `resistance.*` / `immunity.*` /
`vulnerability.*`.

**Ограничения действий** (`engine/actionRestrictions.ts`) — одна модель: флаг
запрещает вид траты хода, срок — обычный срок эффекта. Проверка одна на все
пути (`resolveEntityActionBlocks` — одним расчётом статов на список): лист
персонажа (кнопка заклинания гаснет с причиной в подсказке, нажатие —
плашкой), статблок (раздел «Реакции» / «Бонусные действия» по месту записи,
`findCreatureActionSection`), горячая панель (отказ тем же уведомлением), вкладка
«Эффекты» («вырваться» и «При действии» этой ценой) и срабатывания
(`admitTrigger`). Провоцированной атаки как отдельного действия у системы нет:
это атака реакцией, и общий запрет реакций закрывает и её; запрет только
провоцированных атак — отдельный флаг (ниже). «Одно действие или бонусное за ход»
(«Замедление», `actions.oneActionOrBonus`) — та же модель со счётчиком: трата
хода пишется в счётчики хода носителя (`recordActionSpend`,
`client/composables/actionSpend.ts` — каст заклинания, удар оружием с листа
и панели (в свой ход — действие, `WEAPON_ATTACK_COST`; вне хода — реакция,
её в счёт не пишут), действие статблока, «вырваться»,
действие эффекта; только в бою и только у носителя с флагом), после одной
траты вторая гаснет с причиной, конец хода счёт обнуляет. Применение и
включение переключателя («Ярость» — бонусным действием) пишут трату, если она
названа полем `activation.cost`.

Колдовство ограничивается той же моделью, только по заклинанию:
`spellcasting.blocked` — нельзя накладывать заклинания (Ярость, Газообразная
форма), `spellcasting.noVerbal` — нельзя заклинания с вербальным компонентом
(Тишина), `concentration.blocked` — нельзя концентрироваться: заклинания с
концентрацией не накладываются, а текущая концентрация прерывается, как только
запрет начал действовать (`listBlockedConcentrationCasts` в
`settleCombatState`: включение «Ярости» идёт боевым каналом, и её касты
заканчивает ядро по `endCasts`). Проверка каста одна
(`resolveSpellCastBlock` / `findSpellCastBlock`): лист персонажа (кнопка
гаснет с причиной), быстрые заклинания, статблок существа и горячая панель.

**Для сайта (core-app):** новые ключи флагов `actions.noReaction`,
`actions.noBonusAction`, `actions.oneActionOrBonus`, `spellcasting.blocked`, `spellcasting.noVerbal` и
`concentration.blocked` — обычные строки в `flags`, пример
`{"flags":["actions.noReaction"],"duration":{"type":"turn","value":1}}`.
Старая система незнакомый флаг молча отбрасывает.

**Ход и атаки точнее** (этап 2A). Три флага уточняют трату хода:

- `actions.oneOfMoveActionBonus` — «за ход одно из: перемещение, действие,
  бонусное действие» («Психическая плеть Таши», «Оглушить» плута). Тот же счёт
  трат, что у «действия или бонусного», только в наборе есть перемещение
  (`EXCLUSIVE_SPEND_RULES`): его пишет сервер, когда фишка носителя сама прошла
  путь в свой ход в бою (`applyMovementEffects`; толчок, телепорт правилами и
  чужой ход не считаются). После действия или бонусного действия запас хода
  нулевой (`getTotalMovementSpeed` / `getMovementRange` → 0, ядро не даёт
  тянуть фишку); после перемещения действие и бонусное гаснут. «Перемещение или
  действие» (Ледяной дьявол) — этот флаг вместе с `actions.noBonusAction`.
- `actions.oneAttackPerAction` — «действием Атака только одна атака»
  («Замедление», «Изувечен»). Считается и гаснет только атака ДЕЙСТВИЕМ: она
  пишет счётчик атак хода, вторая такая гаснет с причиной
  (`planWeaponAttack`, `findCreatureActionBlock`). Удар бонусным действием и
  реакцией счётчик не двигает и под запрет не попадает
  (`recordActionSpend`). Чем совершается атака, система узнаёт так:
  - **вне своего хода** любой удар — реакция (провоцированная атака,
    заготовленное действие): `resolveAttackCost` по трекеру инициативы
    (`isEntityOwnTurn`; вне боя хода нет — удар считается действием, а счёт
    не ведётся). Такой удар гасит запрет реакций (`actions.noReaction`), а не
    действий, и в «действие или бонусное за ход» он не пишется;
  - **у существа** цену называет раздел статблока: атака — запись «Действий»
    с броском попадания (мультиатака — несколько таких записей подряд),
    «Бонусные действия», «Реакции» и легендарные действия не считаются;
  - **у персонажа** своего поля цены нет ни у оружия, ни у приёма, ни у
    умения, дающего удар бонусным действием (второе лёгкое оружие, «Мастер
    древкового оружия», удар без оружия монаха). В свой ход удар оружием с
    листа и панели — действие «Атака». Когда единственная атака действием уже
    была, второй удар не гаснет молча: плашка называет причину и спрашивает,
    не бонусным ли действием он совершается (`runWithWeaponAttackCost`);
    ответ уходит в чат («Кинжал: удар бонусным действием»), удар тратит
    бонусное действие и в счёт атак не идёт. Бонусного действия нет («нет
    бонусных действий», «действие или бонусное» после действия — то же
    «Замедление») — вопроса нет, удар гаснет с причиной. Закрытая плашка удар
    отменяет;
  - заклинания, применение умений (`activation.cost`) и срабатывания с ценой
    атакой действием «Атака» не считаются вовсе: это действие «Магия» или
    своя трата.

  Чего система не различает: второе действие «Атака» в тот же ход («Всплеск
  действий») — его удар остаётся атакой действием и гаснет.
- `actions.noOpportunityAttack` — «не может совершать провоцированные атаки»,
  остальные реакции доступны («Электрошок» 2024; прежде это был
  `actions.noReaction`, который шире правила). Отдельного действия
  «провоцированная атака» у системы нет — это удар вне своего хода: в бою такой
  удар носителя флага показывает предупреждение с именем эффекта
  (`warnOpportunityAttack`), кнопку не гасит — вне хода бьют и по
  заготовленному действию.

**Колдовство точнее** (этап 2A):

- `spellcasting.noMagicAction` — «не может совершать действие Магия»:
  заклинания со временем накладывания «действие» гаснут, бонусным действием и
  реакцией колдовать можно. Действие «Магия» без заклинания (предмет, умение)
  система от прочих действий не отличает.
- `spellcasting.noSchool.<школа>` — нельзя заклинания школы; школы:
  `abjuration`, `conjuration`, `divination`, `enchantment`, `evocation`,
  `illusion`, `necromancy`, `transmutation`.
- **Правило каста** (`castRule` эффекта, `engine/effectCastRule.ts`) — то, что
  требует чисел. Читается с эффектов носителя и с аур на нём. Правило каста —
  длящаяся нагрузка (`hasLastingEffectPayload`): эффект, у которого кроме него
  ничего нет, ложится на цель; так же — эффект только с `escape`,
  `conditionImmunities`, `suppressConditions`, `light`, `saveOverride`,
  `stages` или `exhaustionLevel`.
  - `maxSlotLevel` / `minSlotLevel` — ячейки не выше / не ниже круга («не может
    использовать ячейки 7-го круга и выше» — `maxSlotLevel: 6`). Заклинание
    круга выше лимита гаснет с причиной, выбор круга сужается
    (`limitCastLevels`), плата ячейкой (`pay`) — тоже. Заговоры и заклинания с
    зарядами лимит не трогает; из нескольких правил действует самое строгое.
  - `failChance` — шанс провала каста в процентах; `failSave` — спасбросок
    заклинателя при попытке каста; `failComponent` — только заклинания с этим
    компонентом; `failLosesSlot` — при провале тратится и ячейка. Проверка
    идёт, когда каст подтверждён и действие потрачено, до цены сверх ячейки
    (`client/composables/castFailure.ts` — лист, горячая панель, статблок):
    к100 бросает система, спасбросок — владелец заклинателя обычным окном.
    Провал — строка в чат, каст закончен; с `failLosesSlot` списывается ячейка
    выбранного (или наименьшего доступного) круга, у существа — применение
    заклинания. Сл 0 у `failSave` — Сл наложившего, проставляется при наложении
    (`stampSourceTurnSaveDc`); непроставленную не бросают.

**Для сайта (core-app):**

- флаги — обычные строки в `flags`: `actions.oneOfMoveActionBonus`,
  `actions.oneAttackPerAction`, `actions.noOpportunityAttack`,
  `spellcasting.noMagicAction`, `spellcasting.noSchool.<школа>` (восемь ключей,
  школы перечислены выше);
- поле эффекта `castRule` — необязательный объект, все поля необязательны:
  - `maxSlotLevel`, `minSlotLevel` — целое 1–9;
  - `failChance` — целое 1–100;
  - `failSave` — `{ "ability": "<характеристика>", "dc": <целое от 0; 0 — Сл
    наложившего>, "dcFormula"?: "<формула до 200 знаков>" }`;
  - `failComponent` — `"verbal"` | `"somatic"` | `"material"`; пишется только
    вместе с `failChance` или `failSave`;
  - `failLosesSlot` — `true`; так же только вместе с провалом.

  Пустое правило и негодные поля система отбрасывает; старая система поле не
  знает и молча его теряет.

```json
{
  "name": "Замедление",
  "flags": ["actions.noReaction", "actions.oneActionOrBonus", "actions.oneAttackPerAction"],
  "castRule": { "failChance": 25, "failComponent": "somatic", "failLosesSlot": true }
}
```

```json
{
  "name": "Слово силы: Боль",
  "castRule": { "failSave": { "ability": "constitution", "dc": 0 } }
}
```

```json
{ "name": "Копьё Драконьей Чешуи", "castRule": { "maxSlotLevel": 6 } }
```

Спасбросок «против заклинания» различает псевдо-заклинания: удар оружием,
действие существа и предмет несут `Spell.rollSource` (`isSpellRoll`).

Состояние от зоны умеет спадать при выходе из неё: у действия «Наложить
состояние» есть галочка «Спадает при выходе из зоны» (`endsOnExitAreaId`), и
своего срока такому состоянию не нужно — «Опутанность» от «Паутины» уходит,
как только существо выберется. Это не то же, что `endsWithAreaId`: тот ждёт
конца самой зоны, а этот — ухода существа из неё.

### Числа, которые считаются один раз

Формула, которую бросают, бросается ОДИН раз — при наложении, и дальше эффект
живёт числом. Считает это `applyTimeFormulas.stampApplyTimeFormulas`, а зовёт
его `withInitializedDuration` — единственная точка, через которую проходят все
пути наложения.

| Поле | Что | Пример |
|---|---|---|
| `savedRoll` + токен `@roll` | сохранённый бросок: одно число во всех формулах эффекта | «Вибрирующие жидкости» бьют одним и тем же броском на каждом тике |
| `durationFormula` | срок формулой вместо числа: уезжает в `duration.value` | «Замешательство» на 1к4 раунда |

Порядок такой: сперва числа ИСТОЧНИКА (`bindSourceEffectFormulas`: `@mod.spell`,
`@prof`, `@classLevel`), потом кость. Формула, в которой после подстановки
остался `@`-токен, пропускается ЦЕЛИКОМ — как и кубиковый бонус, наполовину она
не считается.

Строка модификатора умеет и **двигаться со временем** (`change.step`): «−1 к
проверкам за каждый следующий ход, до −5». Шаг не считается на лету, а двигает
значение самой строки на границе периода — ход носителя (`processTurnEffects`)
или раунд боя (`decrementActorEffectDurations`), — так что конвейер листа о шаге
ничего не знает и видит обычное число. Работает только у плоского числа: у
формулы двигать нечего, её считают заново при каждом броске. Выключенный эффект
в тишине не досчитывается.

### Запись сущности: разница эффектов и свежая сущность

Клиент считает новое состояние сущности от своей копии; сервер мог изменить
сущность после этой копии (конец каста снял эффекты, легла метка
концентрации, прошёл чужой урон). Поэтому запись идёт двумя помощниками, и
мимо них система на сервер сущность не шлёт (тест `entityWriteCallsites`):

| Помощник | Что пишет | Как |
|---|---|---|
| `changeEntityCombatState` (`entityCombatWrite.ts`) | хиты, эффекты, журнал срабатываний (`system.effectUsage`) | сущность перечитывается из мира в момент записи, преобразование выполняется над ней; снимок несёт разницу эффектов и журнала |
| `sendComputedCombatState` | то же, когда копию посчитали заранее (оплата через вопросы) | разница «основа копии → копия» |
| `sendTriggerUsageSpend` | только расход журнала с заранее посчитанной копии (отметка оплаты) | разница журнала «основа → копия» поверх свежей сущности: хиты и эффекты — её |
| `changeEntitySheet` (`entitySheetWrite.ts`) | ресурсы листа: ячейки, заряды, счётчики, предметы, заклинания | полная запись из свежей сущности; стор правится сразу; хиты и эффекты этим путём не меняются — такую запись помощник не шлёт; журнал срабатываний помощник не шлёт и из преобразования не берёт |

**Боевой снимок с разницей.** `DndCombatState.effectChanges` — `{ add,
update, removeIds }` относительно основы копии (`combatEffectChanges.ts`).
Основу записывают хуки системы `applyDamageToEntity` / `applyEffectsToEntity`
(ими ядро правит свою копию цели — `targetStore`) и помощник записи.
`applyCombatState` сливает разницу со списком СЕРВЕРА: снятое убирается,
изменённое заменяется только у живущего (снятое сервером не воскресает),
новое ложится по правилу наложения (одноимённое заменяет). Без поля — полная
замена списка, как раньше (старый клиент); негодное поле — снимок отвергнут.
Поле `activeEffects` остаётся полным: старый сервер разницу не знает. Хиты в
снимке по-прежнему абсолютные — их окно гонки сужено перечитыванием перед
записью, но не закрыто.

**Пустой снимок не шлётся.** Копия, которая относительно основы ничего не
меняет — ни хитов, ни эффектов, ни журнала, ни удара с потерей хитов
(`changesCombatState`, тот же перечень, по которому `applyCombatState` решает,
принять ли снимок), — на сервер не уходит: спасшаяся цель и «-0 HP» давали
отвергнутый снимок и предупреждение ядра в журнале. Вызывающему копия
возвращается как раньше — сводку в чат он пишет сам (тест
`combatEmptySnapshot`). Снимки, которые шлёт само ядро (`targetStore` — удар
оружием по цели окна броска), этим не закрыты: см. п. 37 § «Чего не хватает».

**Журнал срабатываний разницей.** `DndCombatState.effectUsageChanges` — `{
spend, removeKeys }` относительно той же основы (`diffTriggerUsage` в
`effectTriggerUsage.ts`): расход — приращением, сброс периода — снятием
ключа. `applyCombatState` прибавляет расход к журналу СЕРВЕРА
(`applyTriggerUsageChanges`), поэтому расход «раз в ход», записанный после
копии, снимок урона от этой копии не откатывает, а два расхода из разных
копий складываются. Есть основа — поле шлётся всегда, даже пустое: без него
сервер взял бы журнал копии целиком. Без поля — полная замена журнала, как
раньше (старый клиент); негодное поле — снимок отвергнут. Поле `effectUsage`
остаётся полным для старого сервера.

**Полная запись.** `actor:updated` / `creature:updated` сервер не сливает
(п. 35 § «Чего не хватает для полноценного SDK»): сохранения листов и окон
настройки остаются правкой владельцем, а во время игры полную запись
собирает только `changeEntitySheet` — из свежей сущности, только разделы
листа. Ресурсы, посчитанные заранее, переносятся на свежую сущность
`withSheetResources(current, spent)`: хиты, эффекты и журнал срабатываний
остаются от свежей сущности — журнал ранней копии не расход, а устаревшее
целое (вопрос о цене мог провисеть через конец хода, и ключ прошлого хода с
копии вернулся бы).

**Эффекты в полной записи — с посланным, а не из стора.** Стор клиента
эффекты меняет только по ответу сервера, а полная запись несёт сущность
целиком. Запись листа, ушедшая следом за боевым снимком или концом каста,
возвращала бы серверу эффекты стора: прежнюю метку концентрации вместо новой
(заряд «N/день» существа без окна броска — живая проверка 03.10). Поэтому
`entityCombatWrite.ts` помнит посланное по порядку отправки — разницу
эффектов каждого снимка и конец кастов (`rememberSentCastEnd`, его зовёт
`requestEndCasts`), — а `changeEntitySheet` берёт эффекты через
`readSentActiveEffects`: эффекты стора, по которым посланное применено тем же
слиянием, что на сервере. Наложенный эффект, уже дошедший до стора, берётся
из стора. Память живёт, пока стор не догнал посланное, не дольше
`SENT_EFFECTS_TTL_MS` (2 с) и до смены хода. Хиты так не защищены: в полной
записи они из стора, и защищает их только порядок «ресурс → боевое
состояние» (тесты `sheetWriteSentEffects`, матрица `spellCastFlowCallsites`).

**Журнал едет одним путём и один раз на действие.** Журнал — боевое
состояние. Его расход считает тот, кто делал действие, разницей «до → после»,
и шлёт только боевой помощник: `changeEntityCombatState` (преобразование над
свежей сущностью — трата хода, «преуспеть вместо провала»),
`sendComputedCombatState` (копия после действия — кнопка «При действии»,
включение переключателя), `sendTriggerUsageSpend` (отметка оплаты — её шлёт
одно место, `commitPaySettlement`, разницей «платящий до оплаты → после»).
Помощник листа журнал не шлёт; преобразование листа, тронувшее журнал, —
ошибка вызывающего (в консоль), лист при этом уходит, журнал — нет. Раньше
помощник листа слал разницу журнала сам, и действие, писавшее и лист, и
боевой снимок, тратило лимит дважды (тест `triggerUsageSingleSend`).

Полная запись несёт журнал, посланный боевыми снимками
(`readSentTriggerUsage`): по каждому ключу — большее из стора и посланного,
пока стор посланного не догнал. «Догнал» сверяется по содержимому журнала, а
не по смене объекта `system`: ответ сервера на более раннее сообщение расхода
ещё не несёт. Посланное забывается с концом хода (сервер сбросил счётчики
хода и раунда) и через 5 с (снимок мог не лечь — пауза, нет прав). Журнал
стора меняет только ответ сервера. Сервер обрабатывает сообщения клиента по
порядку, поэтому трата хода снимком и запись заряда полной записью в одном
тике друг друга не затирают. Остаётся окно чужих правок: расход, записанный
сервером по снимку ДРУГОГО клиента и ещё не дошедший до этого, полная запись
этого клиента затрёт (п. 35). И проверка лимита на клиенте читает журнал
стора: два действия одного клиента до ответа сервера лимит «раз в ход» оба
пройдут (расход при этом сложится верно).

**Листы подтягивают то, что пишут помощники.** Лист правит черновик —
глубокую копию сущности — и сохраняет его целиком, поэтому раздел, изменённый
в мире и не подтянутый в черновик, следующее сохранение листа возвращает
прежним. Разделы названы один раз — `worldSheetSections.ts`:
`SHEET_WRITE_SECTIONS` (`system`, `equipment`, `spells` — их кладёт в стор
`changeEntitySheet`) и `COMBAT_STATE_SECTIONS` (`system`, `activeEffects` — их
меняет боевой снимок); их объединение `WORLD_SHEET_SECTIONS` подтягивает
`useWorldSheetSync` — один на лист персонажа и лист существа (раньше у
существа были свои наблюдатели без `spells`: заряд «N/день», списанный
кастом, на открытом листе не уменьшался и возвращался первой же правкой
листа). Наблюдатель у каждого раздела свой: копируется только изменившийся.
В режиме правки синхронизация стоит; выход из правки без изменений
подтягивает все разделы. Быстрые панели (`Quick*Modal.vue`) копируют сущность
мира целиком на каждое её изменение. Заряды заклинания существа проверяются
по существу мира в момент каста (`hasLiveCreatureSpellUsesLeft`), а не по
строке листа или ссылке панели. Тест `worldSheetSync`.

### Вид каста и разбор каста

Какое окно открыть и что делает его кнопка, решает одна функция движка —
`resolveSpellCastPlan` (`spellCastPlan.ts`): окно (`none` — сразу, `confirm`
— выбор круга без броска, `roll` — бросок), вид броска (атака, урон, лечение)
и путь применения (одна формула, многочастный, серия снарядов, снаряды без
атаки, только эффекты). Без частей урона и без атаки окна броска не бывает ни
при каком спасброске: спасбросок бросает цель (`settleNoRollSpellTargets`).
Итог окна идёт в разбор как урон, только если у каста есть части урона
(`resolvePlannedDamageTotal`). У существа план получает два своих правила:
атаки нет у заклинания со спасброском или областью, путь всегда многочастный.

**Атака и спасбросок в одном заклинании — ограничение системы.** Части урона
доставку не различают: нет «эта часть — по попаданию, та — по спасброску».
Запись, где в «Бое» стоят и тип атаки, и спасбросок («Ледяной кинжал»: 1к10
колющего атакой и 2к6 холодом спасброском), ведёт себя неверно на обоих листах:
персонаж бросает атаку, а спасбросок цели ложится на обе части; существо
атаку не бросает вовсе, и обе части идут через спасбросок. Правильно записать
такое заклинание можно тем, что система умеет: в «Бое» — только атака и урон
по попаданию, а вторая половина — эффект «на цели» со срабатыванием «при
наложении» на всех в радиусе от цели вместе с ней (тест `iceKnifeRecipe`).
Чего рецепт не даёт: при промахе эффект не ложится, и взрыва нет — для этого
системе нужен признак «эффект ложится и при промахе» либо части урона со
своей доставкой.

**Для сайта (core-app):** новых полей нет. «Ледяной кинжал»
(`spells/ice-knife-phb`): в `effect` оставить `attackType: "RANGE"`,
`deliveryType: "ranged"`, `damageFormulas: ["1к10@dmg.piercing"]`,
`damageTypes: ["PIERCING", "COLD"]`; убрать `savingThrows`, `saveEffect` и
`scaling.additionalDice`; в `activeEffects` добавить эффект:

```json
{
  "name": "Ледяной кинжал: взрыв",
  "effectTarget": "target",
  "duration": { "type": "special" },
  "triggers": [{
    "id": "trigger_ice_burst",
    "event": "applied",
    "recipient": "area",
    "area": { "radius": 5, "target": "allWithSelf" },
    "save": { "ability": "dexterity", "dc": 0 },
    "actions": [
      { "type": "damage", "parts": [{ "formula": "(@castLevel + 1)к6", "type": "cold" }] },
      { "type": "removeSelf", "on": "always" }
    ]
  }]
}
```

Сл 0 — Сл заклинателя; `@castLevel` — круг ячейки (у существа — круг
наложения из группы, без него — круг заклинания).

Разбор каста персонажа — `spellCastFlow.ts` (лист и горячая панель), существа
— `creatureSpellCast.ts` (лист существа и панель). Порт у входов один (фабрика
мира), и отказ один — уведомлением у действовавшего.

**Отказ видит только тот, кто действовал** (`actionRefusal.ts`). Действие,
которое не началось — нет зарядов или ячеек, цель вне дальности или
досягаемости, запрет траты хода, нет боеприпасов, выбранные цели уже не
годятся, — объясняет почему уведомлением у нажавшего: `refuseAction(title,
description)`, для каста — `refuseSpellCast` («<заклинание>: <причина>»), для
удара — `refuseWeaponAttack`. Способ один на лист и горячую панель, на
персонажа и существо. Раньше панель писала отказ строкой «нельзя…» в общий чат,
и игроки видели, что у чудовища кончились заряды или что оно не дотягивается.
Совершённое действие (каст, урон, спасброски, сорвавшийся каст, свёрнутый
спасбросок) пишет в общий чат как раньше — это не отказ (тест `actionRefusal`).

### Окно броска и порядок необратимого

`DiceRollModal` открывает один помощник — `openDiceRollWindow`
(`diceRollWindow.ts`; тест `diceRollWindow` держит это). Менеджер окон ядра
узнаёт окно по ключу (`_modalKey`, иначе имя и `id` свойств): у окна броска
без ключа ключ один на всё приложение, и второй вызов, пока первое окно
открыто, свёрнуто или ещё закрывается, поднимал ПРЕЖНЕЕ окно с прежними
свойствами и возвращал `null`. Помощник даёт каждому открытию свой ключ;
общий ключ передают только окна, которым повторный щелчок должен поднимать
уже открытое (инициатива участника, спасбросок по запросу).

**Повторное действие заменяет своё окно.** Окна действий открываются с
ключом источника (`buildRollSourceKey`: сущность + оружие, заклинание или
действие существа — раздел статблока и название). Второй щелчок по тому же
источнику — с листа или с панели — не копит второе окно: прежнее закрывается
как отменённое (`closeRollWindow`: окно само сворачивает своё действие —
шаблон области; у заклинания персонажа — шаблон и выбор снарядов), новое
встаёт на его место со свежими свойствами. Прежнее окно ничего не потратило
(см. ниже), поэтому ход и заряд тратятся один раз — броском нового окна; окна
разных источников и разных сущностей живут независимо. Окно, в котором уже
бросили, не трогается. Отказ до окна (нет зарядов, запрет траты хода) прежнее
окно не закрывает. Цена сверх ячейки платится до окна — повторный щелчок по
заклинанию с такой ценой заплатит её ещё раз (окна оплата не знает).

**Ход и ресурсы тратит бросок, а не открытие окна** — один порядок на все
входы: заклинание персонажа и существа, действие существа, удар оружием.
Вызывающий отдаёт расход помощнику окна (`commit` в `DiceRollWindowOptions`),
тот ставит его в `beforeRoll` окна после проверки (`validateRoll` — выбор
целей и снарядов ещё в силе) и зовёт один раз, когда нажали «Бросить»: ход
(`recordEntityActionSpend`), заряд заклинания или общий счётчик группы,
боеприпас; ячейку окно списывает следом (`onSpellSlotConsume`). Окно, закрытое
без броска — крестиком или заменой, — ничего не потратило: «Волна грома»
1/день больше не сгорает от случайного щелчка. Шаблон при отмене убирается,
как раньше. Раньше ход и заряд тратились при открытии окна.

Трата «в долг» закрыта перепроверкой в самом расходе: окно могло простоять,
пока заряд общего счётчика ушёл другим заклинанием группы или ход заняло
другое действие («Замедление»). Тогда `commit` отказывает с причиной (та же,
что у входа: «Не осталось зарядов», запрет траты хода), ничего не тратит и
возвращает `false` — бросок не идёт, окно остаётся. Действие без окна (каст
«только эффекты», действие существа без урона) тратит сразу, когда
применяется, — после выбора типа урона плашкой, а не до него; сорвавшийся каст
(«Замедление») действие тратит по своему правилу (`spendTurn` в
`CastFailureOptions`). Строка чата о решённом уроне «или» по-прежнему идёт,
когда окно открылось. Применение умения и предмета окна броска не открывает
и тратит при подтверждении — после выбора получателя и вопроса о цене. Цена
сверх ячейки оплачивается до окна: от потраченного считаются формулы
заклинания; закрытое окно её не возвращает (тесты `diceRollWindow`,
`spellCastFlowCallsites`).

**Порты входов — из мира.** Окно живёт в менеджере окон и переживает
вкладку (`v-if`) и лист, а ячейку, заряд и боеприпас списывает его бросок.
Поэтому порт входа собирает фабрика мира — `createSpellCasterPort`,
`createCreatureSpellCasterPort`, `createWeaponAttackPort`: сущность читается
из мира в момент обращения, ресурс пишется `changeEntitySheet`. Лист и
горячая панель не различаются и отказом (один помощник — `actionRefusal.ts`);
`emit` и `props` компонента порт не трогает (тест `sheetPortLifetime`).
Применение предмета и умения с листа идёт теми же входами мира, что кнопки
горячей панели (`applyEntityItemUse`, `applyEntityEffectUse`): заряд и ресурс
списываются после выбора цели и вопроса о цене, когда вкладка уже может быть
размонтирована; разбор применения (`applyEffectSource`) лист сам не собирает
(тест `entityStatsCallsites`).

**Лист в режиме правки не действует.** В правке лист держит черновик и мир в
него не подтягивает, а действия тратят ресурсы и накладывают эффекты через
мир. Пока лист сущности у этого пользователя в правке, её действия не
выполняются и объясняют почему («Сохраните или отмените правку листа»): каст
заклинания персонажа и существа, удар оружием, действие существа, применение
умения и предмета, переключатели эффекта и предмета, кнопка «При действии»,
«Вырваться» (и носителю, и помощнику), отдых. Правило одно на лист, быстрые
панели и горячую панель — проверка `refuseWhileSheetEditing`
(`sheetEditLock.ts`) стоит первым делом в общем входе действия, а не в
кнопках; отметку правки держит сам лист (`useSheetEditLock`). Кнопки действий
вкладки эффектов («Применить», «Вырваться», «При действии») правка поэтому не
гасит: погашенная кнопка причины не говорила. Тест
`sheetEditLock` сверяет: каждая функция пишущего модуля, которую зовёт
интерфейс, либо проверяет лист, либо названа в списке с причиной.

**«Сохранить» сливает черновик с миром.** Запрет закрывает действия этого
пользователя, но мир меняют и другие: урон от чужого клиента, срабатывание
сервера, расход одноразового эффекта броском. Поэтому «Сохранить» листа в
правке шлёт не черновик, а слияние по трём точкам — сущность на входе в
правку, черновик, мир (`mergeEntityDraft` в `entityDraftMerge.ts`): что
владелец не менял — из мира, что менял — из черновика, поменяли оба — правка
владельца. Сравнение идёт вглубь по полям, а списки записей с `id` (предметы,
заклинания, эффекты, счётчики) сливаются по записям: правка одного заклинания
не возвращает заряд другого. Вне режима правки лист сохраняет черновик, как
раньше: он следует за миром (`useWorldSheetSync`). Остаётся окно п. 35:
правка мира, не дошедшая до клиента к моменту «Сохранить».

### Счётчик растёт вместе с максимумом

Как хиты на повышении уровня: максимум вырос на Δ — текущее растёт на Δ
(«Возложение рук» 5/5 → 20/20, 3/5 → 18/20), упал — обрезается
(`resizeCounterCurrent`). Ресурс «появляется пустым», свой ресурс листа,
которому отдых ничего не возвращает, и счётчик с прежним максимумом 0 —
по прежним правилам. Так в мастере класса, у ресурсов черт и вида и при
пересчёте максимумов листа; отдых не тронут.

### Окно эффекта: что где работает

Один и тот же эффект живёт в разных местах, и в каждом работает своё
подмножество полей. Окно (`ui/effect/ActiveEffectFormModal.vue`) показывает шаги
«Когда срабатывает → Спасбросок → Урон → Что меняет → Длительность →
Срабатывания» только там, где они что-то делают. Решает это движок
(`effectFormLayout.resolveEffectFormLayout`) по МЕСТУ окна — проп `context`,
который передаёт каждое окно-владелец. Сверху стоит фраза
`activeEffectScenario.describeEffectScenario` — как эффект сработает с текущими
настройками.

| Место (`context`) | Куда ложится | Спасбросок и урон срабатывания | Длительность | Срабатывания |
|---|---|---|---|---|
| `ownEffects` — свои эффекты | носитель, аура | аура при входе/выходе | да | носитель: ход, атака, урон и 0 хитов, поступки; аура: см. ниже |
| `feature` — черта, предыстория, вид, класс | носитель, аура | аура при входе/выходе | только аура при входе/выходе | носитель: атака, урон и 0 хитов, поступки, без снятия; аура |
| `item` | носитель, аура | аура при входе/выходе | только аура при входе/выходе | носитель: атака, урон и 0 хитов, поступки, без снятия; аура |
| `creatureTrait` | носитель, аура | аура при входе/выходе | только аура при входе/выходе | носитель: ход (только свой), атака, урон и 0 хитов, поступки, без снятия; аура |
| `weapon` | владелец, цель при попадании, аура | цель; аура при входе/выходе | цель | владелец: атака и поступки, без снятия; цель: ход и атака; аура |
| `spell` | цель, заклинатель, аура, зона на месте области | цель; аура и зона при входе/выходе (Сл 0 — Сл заклинателя) | да; у зоны «пока внутри» — нет | цель: ход и атака; заклинатель — и урон, 0 хитов; аура; зона |
| `creatureAction` | цель | да (Сл 0 — Сл действия) | да | ход и атака |
| `zone` | существо в зоне | при входе/выходе | при входе/выходе | ход, вход и выход; копия «при входе» — и атака |
| `condition` | носитель | нет | нет | нет |
| без места (старое ядро) | всё | всё | всё | ход и атака |

«Поступки» — события о том, что делает сам носитель: отдых, пройденный путь,
снятое с него состояние, поверженная им цель; вместе с броском атаки их слышит
всё, что действует вместе с носителем (`listCarrierEventSources`): его
собственные эффекты, эффект умения, надетый и настроенный предмет, оружие в
руке, черта статблока. Постоянный эффект предмета — «при попадании цель
получает 1к6», «после продолжительного отдыха в этом доспехе…» — работает
срабатыванием, а не кнопкой; «только этим оружием» срабатывание не различает
и слышит любую атаку владельца. Снять сам себя и потратить заряд может только
эффект, лежащий на существе: у умения, предмета и черты снимать нечего.
Срабатывание «после отдыха» выполняется на уже отдохнувшей сущности, и всё, что
оно сделало, остаётся: отметки, состояния, снятие, списанная цена, возврат
ресурсов, урон и лечение.

**Для сайта (core-app):** формат данных не менялся. В редакторе эффектов места
`item`, `weapon` (доставка «владельцу») и `creatureTrait` больше не помечают
неработающими срабатывания с событиями `attackRoll`, `rest`, `moved`,
`conditionLost`, `downedOther` — набор тот же, что у `feature`; действие
«Снять эффект» там по-прежнему не предлагается.

У ауры и зоны в «Срабатываниях» всегда есть ход, вход и выход. Аура «пока
внутри» слышит ещё урон и 0 хитов того, кого накрыла; аура и зона «при
входе/выходе» — атаку и снятие своей копии. «Чей ход» (носителя или
наложившего) выбирается везде, кроме черты на самом существе: у неё
наложившего нет.

**Шаг «Срабатывания»** (`form/EffectTriggersStep.vue`, строка —
`EffectTriggerRow.vue`, условие — `EffectTriggerConditionPicker.vue`, подписи —
`ui/effect/triggerLabels.ts`, варианты выбора — `ui/effect/effectFormOptions.ts`):
пресеты «Урон каждый ход», «Повторный спасбросок», «Снять после атаки», «Вместо
0 хитов — 1 хит», «Отметка от урона» и «Своё…». Строка:
- **когда** — событие; у атаки — чья («Своя атака» / «Атака по носителю»), у
  хода — чей («Носителя эффекта» / «Наложившего эффект»). Кроме хода, входа,
  выхода, наложения, броска атаки, урона, нуля хитов, конца каста, отдыха и
  включения есть ещё три, которые видит боевой снимок на сервере: «когда
  носителя лечат» (подъём хитов; временные хиты лечением не считаются),
  «когда с носителя снимается состояние» (с полем «Какое состояние») и «когда
  носитель сваливает цель» (идёт на эффектах свалившего, поверженный —
  другая сторона). Ещё одно приходит от ядра при перемещении фишки: «когда
  носитель проходит путь» (`moved`, `applyMovementEffects`, VTTG 0.9.533+) —
  без шага раз за перемещение, с полем «За каждые, фт» (`everyFeet`) — за
  каждый шаг пути; остаток короче шага не переносится;
- **кому** — носителю, другой стороне события (тому, кто нанёс урон, цели
  атаки или атакующему), наложившему эффект, всем в радиусе или выбранным
  человеком. «Наложившему» предлагается там же, где «всем в радиусе»
  (`triggerEventAcceptsSource`): получателя, кроме субъекта, ищет только путь
  событий, а на границе хода действия идут прямо на носителя. Эффекту без
  наложившего (из компендиума) такое срабатывание молчит, а не бьёт носителя;
- **если** — условие из частей «и» (урон типа / не этого типа, крит / не крит,
  хиты носителя, отметка есть / нет, тип носителя или другой стороны, бросок с
  преимуществом / помехой, другая сторона помечена носителем, атака попала /
  промахнулась). У броска атаки попадание известно не всегда: серия снарядов
  сообщает о броске раньше, чем сделаны сами броски, — и тогда обе части о
  попадании НЕ выполняются, как всякая часть без данных;
- **спасбросок** (`SaveDcField`): Сл числом, «Авто» или «Формулой» по
  владельцу эффекта, у событий урона формула читает и `@damage`;
- **что сделать** — действия с исходом спасброска: урон или лечение, наложить
  состояние, поставить отметку, хиты становятся N или полный запас (только на
  «хиты упали до 0» и «при наложении»: Неутомимость и Слово силы: Исцеление),
  закончить каст, снять эффект. Окно считает рецепт собираемым, только если
  предлагает и событие, и каждое его действие (`listInertEffectFields`);
- **с броском на шанс** — процент; бросок идёт ПЕРЕД лимитом: неудавшийся шанс
  — это несостоявшееся срабатывание, и «раз в ход» на него не тратится;
- **не чаще** N раз за ход / раунд / короткий / долгий отдых.

У всего списка срабатываний есть общие **заряды** (`charges`): каждое
сработавшее тратит один, зарядов не осталось — эффект молчит, а с пометкой
«Последний заряд снимает эффект» ещё и снимается. Заряд списывают из самого
экземпляра эффекта, поэтому у ауры чужого токена и у эффекта зоны зарядов нет:
списывать там нечего (`takeEffectCharge`).

«Всем в радиусе» и отбор кандидатов выбора знают, кого задеть: союзников,
врагов, всех — и те же три «и носителя» (`alliesWithSelf`, `allWithSelf`).
Соседей по сцене ядро отдаёт БЕЗ субъекта, и добавить его может только система
(`findEntitiesInArea`); прежние карточки с «всем в радиусе» от этого носителя
задевать не начинают.

Что доступно, решает движок: `layout.triggerEvents`, `layout.triggerActions`,
`layout.triggerTurnOwners`, `listTriggerActionTypes`, `listEffectTriggerPresets`,
`triggerEventAcceptsDcFormula`, `triggerEventHasOtherParty`,
`triggerEventHasRole`, `listTriggerConditionKinds`. Строка пишется
`writeEffectTriggerRow` — «сначала старые поля»; срабатывание не для этого места
— плашка `triggers` с кнопкой «Убрать».

«При успехе» — один выбор вместо трёх полей (`readEffectSuccessOutcome` /
`writeEffectSuccessOutcome`):

| Вариант | `applySave.onSuccess` | `applyOnSuccess` | `applyOnSuccessOnly` |
|---|---|---|---|
| Ничего | `negate` | — | — |
| Половина урона | `half` | — | — |
| Половина урона и эффект | `half` | `true` | — |
| Эффект без урона | `negate` | `true` | — |
| Эффект только при успехе | `negate` | — | `true` |

Поля, заданные, но в этом месте не работающие (`listInertEffectFields`), окно не
стирает молча: показывает плашку с кнопкой «Убрать». Спасбросок эффекта зоны,
ауры и хода у сущности без авто-спасбросков уходит запросом владельцу (§ «Чего
не хватает», п. 19).

Урон каждый ход (`recurringDamage`) может требовать спасбросок на каждом тике —
`recurringDamage.save`: провал — полный урон, успех — без урона или половина,
эффект при этом остаётся. Так собирается «Облако смерти»: зона «пока в зоне»,
урон в начале хода, спасбросок Телосложения. Сл 0 — Сл заклинателя, её
проставляет наложение (`stampSourceTurnSaveDc`).

У черты существа урон и лечение каждый ход тикают на его ходу («Регенерация»
чертой статблока); повторного спасброска и снятия у черты нет — снимать нечего.

**Срабатывания (`triggers`).** Периодика, спасбросок наложения и «снять после
атаки» — частные случаи одной модели «когда → спасбросок → что сделать → сколько
раз» (`engine/effectTriggerTypes.ts`). Старые поля читаются как срабатывания
(`collectEffectTriggers`), запись идёт сначала в старые поля
(`writeEffectTriggers`), а в `triggers` — только то, чего они не выражают:
- события «получил урон» (`damageTaken`), «хиты упали до 0» (`hpZero`), вход и
  выход (`enter` / `exit`) у зоны и ауры, ход наложившего (`turnOf: 'source'`),
  «при наложении на цель» (`applied`), «когда заклинание заканчивается»
  (`castEnd`), «после отдыха» (`rest`, `restType`: долгий по умолчанию,
  короткий, любой);
- условие (`condition`), получатель (`recipient: 'other'`, `'area'`,
  `'choice'` — выбранным человеком), Сл формулой (`save.dcFormula`),
  преимущество или помеха самого спасброска (`save.mode`), режим по условию
  (`save.modeIf`) и автоматический исход (`save.autoSuccessIf` /
  `save.autoFailIf`: провал главнее успеха);
- цена (`cost`: действие, бонусное, реакция, часть перемещения), цена ресурсом
  (`pay` — см. «Цена ресурсом») и вопрос человеку (`ask`, `asker`) — см.
  «Вопрос человеку» ниже;
- действия «наложить состояние» (`applyCondition`, с повторным спасброском
  `recurringSave` и собственными срабатываниями `triggers`) — «Зловоние» в
  начале хода, «Сон» с пробуждением от урона, «поставить отметку» (`applyTag`,
  счётчиком `stack`), «уменьшить максимум хитов» (`reduceMaxHp`: число, кости
  или `@damage`, до отдыха `endsOnRest`), «хиты становятся» (`setHp`),
  «закончить каст» (`endCast`, свой или получателя — `whose`), «сообщить
  человеку» (`notify`: текст, кому и необязательный бросок; строка уходит в
  сводку чата хода, события, входа и выхода — на броске атаки такое
  срабатывание выполняет сервер), «следующая
  ступень» (`nextStage`), «снять состояние» (`removeCondition`: одно по ключу
  или все), «временные хиты» (`tempHp`: поставить, прибавить, потратить),
  «убить» (`kill`) и «вернуть к жизни» (`revive`), «уронить из рук»
  (`dropHeld`), «вернуть ресурс» (`restore`: ячейка круга или счётчик листа;
  сколько — формулой `amount`, у счётчика `set` ставит его в это число вместо
  прибавки), «хиты становятся» формулой (`setHp.formula`), срок наложенного
  состояния и отметки формулой (`durationFormula`),
  «рассеять заклинания» (`dispel` до круга по `castLevel` эффекта), «дать
  вдохновение» (`grantInspiration`), «переместить» (`move`: толчок,
  притягивание, перенос — точку считает `engine/forcedMovement.ts`, ставит
  фишку ядро через `SystemTriggerContext.moveToken`, VTTG 0.9.532+), «сдвинуть
  зону» (`moveArea`: от получателя, к получателю или за носителем на событии
  пути — сдвигается зона того же каста, смещение считает
  `engine/areaShift.ts`, вершины переносит ядро через
  `SystemTriggerContext.moveArea`, VTTG 0.9.533+);
- лимит «не чаще N раз в ход / раунд / короткий или долгий отдых» —
  `limit: { max, per, key? }`. Счётчик лежит на субъекте
  (`system.effectUsage`), общий `key` связывает срабатывания: урон «Лунного луча»
  при входе и в конце хода — один раз за ход. Ход сбрасывается в
  `expireTurnEffects` на конце хода, раунд — в `decrementActorEffectDurations`,
  отдых — в `restEngine`;
- срабатывания у черт существа, надетых предметов и ауры чужого токена (снять
  их нельзя).

Лимит хода и раунда считается только в бою: вне боя сбросить его некому. Идёт
ли у сущности бой, ядро сообщает полем контекста `isInCombat` (VTTG 0.9.517+);
без него вход в зону лимитом хода не ограничен. Срабатывания хода бывают только в
бою и считаются всегда. Условие проверяется раньше лимита: невыполненное условие
«раз в ход» не тратит.

Диспетчер — `engine/effectTriggerRunner.ts`; спасбросок игрока уходит запросом
(`deferredEffectSaves.ts`), как у старых полей.

Кости урона и лечения срабатываний бросает сервер (`rollDamageFormula` отдаёт и
кости по граням), а исход ядру несёт их полем `chatRolls`
(`buildEffectDiceRolls`, VTTG 0.9.528+): ядро пишет их в чат
сообщениями-бросками раньше сводки, и клиенты катают кубики. Итог исхода
подписан у его броска — «Зелье лечения → Грок: +6 HP», восстановленное на деле
(`restoreEntityHitPoints`), при упоре в максимум — «+2 HP (хиты полные)», — и
сводка его не повторяет: в ней остаются исходы без костей, спасброски и заметки
(«при наложении» — своя подпись). Эффект, который при наложении снимает сам
себя (`removesItselfOnApply`: зелье лечения), в список наложенного не входит
(`postSpellEffectsMessage`), а отдельной строки «применяет» у применения нет —
зелье даёт одно сообщение.

**Условие** (`engine/triggerConditions.ts`) — строка из частей через `&&`,
словарь закрытый: `damage.type === "fire"` / `!==`, `damage.isCritical === true`
/ `false`, `self.hp.value <= (self.hp.max / 2)`, `self.hp.value < self.hp.max`,
`self.tag === "x"` / `!==`, `self.tagFromSource === "x"` / `!==` (отметка от того
же наложившего — «невосприимчив к этому источнику»), `self.tagCount["x"] >= N`
(ступени отметки-счётчика), `self.hp.value <= N` / `>= N`, `self.size <= "large"`
/ `>=`, `self.condition === "prone"` / `!==`, `self.creatureType === "…"`,
`target.creatureType === "…"` (другая сторона), `roll.hasAdvantage === true`,
`roll.hasDisadvantage === true`, `target.markedBySelf`, `self.hp.temp === 0`,
`self.grounded === true`, `self.species === "…"`, `self.ability["strength"] >= N`
/ `<=`, `target.isSource === true` (другая сторона — тот, кто наложил эффект),
`target.hp.value <= (target.hp.max / 2)`, `target.hp.value <= N`,
`damage.amount >= N`, `source.distance <= N` (наложивший в пределах футов),
`attack.kind === "melee"`, `attack.ability === "strength"`, `combat.round === N`
/ `>= N` (расписание по раунду боя: номер даёт ядро на сервере и трекер
инициативы на клиенте) и `move.forced === false` / `true` (на событии пути:
носитель шёл сам или его переставили правила). Часть, у которой на этом
событии нет данных (тип урона на ходу), и незнакомая часть не выполняются —
срабатывание с непонятым условием молчит, а не бьёт всегда. Окно собирает
условие выбором частей, строку как есть оставляет видимой.

**Вопрос человеку** (`engine/triggerPrompt.ts`). Канал тот же, что у
спасброска и выбора цели (`rollRequests`), — отличается метка нагрузки
(`effectPrompt`). Нагрузка несёт вопрос и ЗАКРЫТЫЙ список вариантов ответа:
ответ сверяется с тем же списком, и ответить тем, чего не предлагали, нельзя.
Отказ, молчание и «спрашивать некого» — одно и то же: срабатывание отменяется с
заметкой в чат. На нём стоят галочка «Спрашивать разрешения» (`ask`), цена
«Реакция» и цена ресурсом (`pay`): реакция и ресурсы листа — ресурс человека,
поэтому они сами делают срабатывание добровольным. Реакция тратится не чаще
раза за раунд общим счётчиком носителя (`REACTION_TRIGGER_LIMIT`). Спрашивают
на всех событиях сервера: на границе хода, при входе и выходе, на событиях урона,
наложения и броска атаки (`runTriggerEventSource`); срабатывание броска атаки с
вопросом выполняет сервер, а не клиент. Лимит «не чаще N раз» и заряд эффекта
вопрос только проверяет — тратит их согласие (`takeTriggerAdmission`): отказ не
съедает ни «раз в ход», ни реакцию раунда. Окно адресата —
`EffectQuestionPromptModal`.

Вопрос ничего не меняет в самом срабатывании: данные события привязываются до
развилки «спросить или нет» (`runTriggerEventSource`), и после согласия оно
выполняется тем же, чем выполнилось бы сразу. Тип урона события (`@dmg.event`)
едет в снимке срабатывания — защиты получателя его видят и с ценой «Реакция»;
числа владельца подставлены при сборе срабатываний, `@paid.*` — оплатой по
ответу, крит атаки и смещение пути едут в опциях ответа. Спасбросок получателя
после согласия или выбора цели считает Сл от урона события (`@damage`), режим
«если…» и автоматический исход по тем же данным события
(`EntryEffectOptions.eventData`). Ауры, накрывающие субъекта, чужому получателю
защит не дают — как и без вопроса.

Срабатывания, которые выполняет клиент (кнопка «При действии», включение
переключателя), идут через `runEntityEffectAction` и `toggleEntityEffect`: цена
спрашивается плашкой оплаты, ресурсы листа уходят обычным сохранением
(`emitActedEntity` — боевой канал их не несёт), а сводка — урон, лечение, строки
«Сообщить», списанная цена — пишется в чат (`formatSelfTriggerReport`).

Срабатывания «после отдыха» тоже выполняет клиент — отдых это кнопка листа, —
но нажатие «отдохнуть» согласием не служит. Срабатывание отдыха с галочкой
«спрашивать» или ценой ресурсом идёт тем же порядком, что остальные пути:
разбор цены → при нехватке вопроса нет → вопрос владельцу → списание →
действия. Вопрос задаёт плашка стола (`runRestWithTriggers` →
`askRestTriggers` → `EffectQuestionPromptModal`; у цены с выбором — варианты
платежа и «Не платить»), ответы уходят в отдых
(`RestTriggerOptions.triggerAnswers`). Без ответа такое срабатывание НЕ
выполняется — ни молча, ни бесплатно: отказ, закрытая плашка и цена не по
карману оставляют строку в сводке чата («Эффекты (после отдыха)…»), как отказ
у срабатываний сервера. Ветки «отказался — получи истощение» у срабатывания
нет: что делать при отказе, оно не описывает — это ставит игрок или ведущий по
строке сводки.

**Вырваться** (`escape`, `engine/effectEscape.ts`) — действие, снимающее эффект:
кто действует (`by`), чем платит (`cost`), проверка навыка (`check`) и что даёт
успех (`onSuccess`). Кнопка живёт на вкладке «Эффекты» листа: у своего эффекта —
в его строке, у эффекта-состояния («Схваченный», «Опутанный» — строки у них нет,
их показывает плитка) — над сеткой состояний, с именем эффекта в подписи
(`listConditionEscapeEffects`). Плитка состояния в просмотре снимает его боевым
каналом (`removeEntityCondition`) — тем же, что и «вырваться»: сервер будит
срабатывания «когда состояние снимается», и «Ошеломлённый до конца захвата»
уходит вместе с захватом; в правке листа плитка меняет черновик. Выключенный
эффект не держит — из него не вырываются. Сл «Авто» (0) проставляется при наложении тем
же путём, что и у отложенных спасбросков (`stampSourceTurnSaveDc`); осталась
нулевой — кнопка честно отказывается действовать: проверка против нуля прошла бы
у кого угодно.

- **Навыки на выбор** (`check.skills`) — правило захвата 2024: «Атлетика или
  Акробатика». У навыка списка могут быть своя Сл (`dc`: кандалы — Ловкость рук
  20, Атлетика 25), роль (`by`: кому навык доступен) и пометка (`label`).
  `check.skill` при списке — его первый навык: по нему проверку читают версии
  системы без списка, поэтому в данных пишутся оба поля. При нескольких навыках
  кнопка спрашивает, каким бросать (`listEscapeChecks`).
- **Кто действует** (`by`): `self` — носитель, `adjacent` — существо рядом,
  `any` — любой из них. Помощник бросает СВОЙ навык со своими флагами: кнопка у
  носителя при нескольких кандидатах спрашивает «кто действует» (кандидаты —
  существа в 5 фт, которыми управляет пользователь; ведущий — любыми), а на
  листе помощника есть блок «Помочь рядом» с эффектами соседей
  (`listEscapeHelpOffers`). Наложивший эффект (`sourceActorId`) помощником не
  предлагается ни там, ни там (`canHelpEscapeEffect`): он эффект держит, а не
  снимает проверкой против своей же Сл. Цену и её запрет («нет реакций») несёт
  тот, кто действует.
- **Режим броска** (`resolveEscapeRollMode`): режим самой проверки навыка (общие
  флаги проверок, флаги характеристики и навыка), режим из эффекта
  (`check.mode`: «проверки для освобождения — с помехой», Мимик), флаги
  вырывающегося `escape.advantage` / `escape.disadvantage` и
  `escape.advantage.grappled` / `escape.disadvantage.grappled` (только из
  состояния «Схваченный»: Голиаф), флаг того, кто наложил захват,
  `grapple.escapeDisadvantage` («из вашего захвата высвобождаются с помехой»).
  Преимущество и помеха гасятся по обычному правилу.
- **После** — `onSuccessApply`: состояние носителю после освобождения («…и
  получает состояние лежащий ничком»); `onFailDamage`: части урона носителю за
  каждую неудачную проверку (охотничий капкан). Исход уходит боевым каналом:
  помощник снимает эффект с чужого носителя, а урон будит события урона.
- **У состояния из срабатывания**: действие `applyCondition` несёт свой блок
  `escape` (кнопка появляется у наложенного состояния) и `flags` — правила
  сверх самого состояния, пока оно лежит («пока цель отравлена, она не может
  совершать реакции»).

**Для сайта (core-app):** блок `escape` эффекта и действия `applyCondition`:

- `by`: `"self"` (по умолчанию, не пишется) | `"adjacent"` | `"any"`;
- `check.skills` — необязательный массив до 6 навыков: `{ "skill": "<навык>",
  "dc"?: <целое от 1>, "by"?: "self" | "adjacent", "label"?: "<до 100 знаков>"
  }`; навык строкой система читает тоже. Писать ВМЕСТЕ с `check.skill` (первый
  навык списка) — старые версии системы читают только его;
- `check.mode`: `"advantage"` | `"disadvantage"`;
- `onSuccessApply` — ключ состояния (`"prone"`);
- `onFailDamage` — массив частей урона `{ "formula": "1", "type": "piercing" }`;
- у действия `applyCondition` — `escape` (тот же блок) и `flags` (массив ключей
  флагов эффекта);
- флаги `escape.advantage`, `escape.disadvantage`, `escape.advantage.grappled`,
  `escape.disadvantage.grappled`, `grapple.escapeDisadvantage`.

```json
"escape": {
  "by": "any",
  "cost": "action",
  "check": {
    "skill": "athletics",
    "dc": 14,
    "skills": [{ "skill": "athletics" }, { "skill": "acrobatics", "by": "self" }],
    "mode": "disadvantage"
  },
  "onSuccess": "removeSelf",
  "onSuccessApply": "prone",
  "onFailDamage": [{ "formula": "1", "type": "piercing" }]
}
```

68 захватов бестиария с одной Атлетикой работают как раньше; перевод их на
`skills` — правка данных.

**Ступени** (`stages`, `engine/effectStages.ts`) — у каждой ступени свои
`changes` и `flags`. Перевод на следующую ПЕРЕПИСЫВАЕТ их у эффекта, поэтому
конвейер листа о ступенях не знает вовсе. Переводит человек — кнопкой на листе
или действием срабатывания `nextStage`.

**Согласная цель** (`applySave.allowWilling`) — в окне спасброска появляется
«Не сопротивляюсь»: бросок не делается, спасбросок считается проваленным.
Решает владелец цели, а не тот, кто накладывает; разрешение едет в нагрузке
запроса (`allowWilling`).

**Провал в успех** (`saveOverride`, `engine/saveOverride.ts`,
`client/composables/saveOverrideOffer.ts`) — «Легендарное сопротивление»
босса, черты и предметы игроков: носитель, проваливший спасбросок, тратит
единицу и преуспевает. Возможность даёт поле эффекта
`saveOverride { limit?: { max, per }, counter? }` (свой счётчик «N раз до
короткого / долгого отдыха» в общих счётчиках носителя `system.effectUsage`,
либо ресурс листа `classCounters`; задано оба — платит ресурс) или число у
черты существа `saveSuccessPerDay` (N раз в день = до долгого отдыха; в форме
черты — «Провал спасброска → успех, раз в день»). Сообщение чата ядро править
не умеет, поэтому спрашивают до того, как по итогу лягут урон и эффекты, —
там, где бросок только что посчитан: управляет носителем сам (владелец,
ведущий) — окно вопроса у него: остаток назван в тексте («…Легендарное
сопротивление (осталось N): преуспеть вместо провала?»), кнопок две —
«Преуспеть» и «Оставить провал», крестика нет (отказ уже среди кнопок);
бросал за чужое существо (игрок кастует в босса без владельца) — вопрос
уходит ведущему каналом запросов (`SAVE_OVERRIDE_REQUEST_KIND`), ресурс
списывает ведущий, «да» засчитывается только от ведущего. Бросок в чате
остаётся провалом, следом идёт строка «Аболет: Легендарное сопротивление —
провал спасброска становится успехом (осталось 2)». Спасброски зоны, ауры и
хода, которые сервер у сущности с авто-спасбросками бросал сам, у носителя с
такой возможностью уходят запросом владельцу (`shouldRequestEffectSave`; без
управляющих в сети ядро отдаёт запрос ведущему): его клиент бросает сам и
спрашивает только при провале. Такой запрос получают ВСЕ ведущие в сети, и
каждый клиент кидает свой бросок (в чате их будет несколько, засчитан первый
ответ); как только один ответил, у остальных вопрос закрывается и ресурс не
тратится (`reply.onCancelled`). Не спрашивают пока там, где бросок синхронный:
серия снарядов с авто-броском.

**Для сайта (core-app):** у черты существа — число `saveSuccessPerDay` (целое,
1–20; «3/день» → `3`), пример
`{"name":"Легендарное сопротивление","description":["…"],"saveSuccessPerDay":3}`.
У эффекта — `saveOverride`, пример `{"limit":{"max":3,"per":"longRest"}}` или
`{"counter":"luck"}` (`per`: `shortRest` | `longRest`). Старая система оба поля
не знает и молча пропускает.

**Отметка** (`applyTag { tag, label?, duration? }`) — лёгкий эффект с полем
`tag`, который читает условие `self.tag`. Срок по умолчанию — до начала
следующего хода носителя. Так собирается «Регенерация» тролля: урон огнём или
кислотой ставит отметку, лечение в начале хода идёт при `self.tag !== "…"`.

**Запертое и подавленное состояние.** `applyCondition.locked` помечает
наложенное состояние `conditionLocked`: плитка состояния на листе и действие
«снять состояние» его не трогают — снимает только то, что наложило.
`suppressConditions` у эффекта, наоборот, состояние не снимает, а ГАСИТ:
`collectActiveEffects` выбрасывает его из расчёта, пока подавляющий эффект жив,
и возвращает обратно, когда тот кончился («Свобода перемещения» против
Опутанного).

**Ход наложившего.** `turnOf: 'source'` у начала или конца хода срабатывает на
ходу того, кто наложил эффект (`ActiveEffect.sourceActorId`, его ставит каждое
наложение): «повторный спасбросок в конце хода заклинателя», огненная аура
существа в конце его хода. Ядро зовёт `runSourceTurnEffects` у участников боя на
границе хода наложившего (VTTG 0.9.519+). Наложивший неизвестен или не в бою —
срабатывание идёт на ходу носителя: его ход не наступит.

**Срок «до хода наложившего».** `duration: { type: "turn", turnAnchor:
"source" }` истекает на границе хода наложившего (`expireTurnEffects`): начало
— на первом же его ходу, конец — на следующем, если эффект наложен в его
собственный ход (`turnSkipFirst`), иначе на первом (удар реакцией в чужой
ход). Одинаково для персонажа и существа в любой паре — тесты
`tests/sourceTurnDuration.test.mjs` повторяют порядок вызовов ядра. Носитель,
которого нет в инициативе, получает границу хода наложившего-участника так же,
как участник боя (VTTG 0.9.597+); на более старом ядре и там, где ждать нечего
(срок по своему ходу, наложивший тоже вне боя), срок идёт по границе раунда
(см. § «Чего не хватает», п. 30).

**Вход и выход у ауры.** Явные срабатывания `enter` / `exit` у ауры работают
так же, как у зоны: ядро проходит маршрут фишки по шагам (VTTG 0.9.521+), и
извилистый путь сквозь ауру бьёт один раз. Вход и ход в той же ауре делят один
счётчик лимита (`aura:<копия>`).

**Бросок атаки.** Простые срабатывания — без спасброска, урона, конца каста и
действий другой стороне (`isClientAttackRollTrigger`): «на своей следующей
атаке», «на следующей атаке по носителю» — расходует само окно броска
(`DiceRollModal`, проп `attackerId`) через
`composables/useEffectTriggerEvents.ts` → `runAttackRollTriggers` ДО броска:
одинаково для макросов хотбара и листов персонажа и существа. У серии снарядов
целями считаются назначенные цели снарядов. Счётчик лимита уезжает боевым каналом
разницей журнала (`DndCombatState.effectUsageChanges`).

**Израсходованный эффект действует на эту атаку целиком.** Расходуются
броском атаки: эффект «снять после своей атаки» / «снять после атаки по цели»
(`consumeOn: 'carrierAttack' | 'attackOnCarrier'`), простые срабатывания
`attackRoll` (снять эффект, наложить состояние или отметку, сообщить) с их
лимитами и заряды эффекта (`charges`, последний с `endsWhenEmpty` снимает
эффект). Такой эффект участвует в этой атаке — бросок, урон, защиты цели — и
уходит после неё; исход не зависит от сети и от пути. Что считается ДО
расхода, в тике броска: режим броска и бонусы попадания, КД и флаги цели,
бонус-части урона. Что считается ПОСЛЕ — урон и защиты — делится на два пути:
окно применяет урон само в том же тике (мир расхода ещё не видел), либо части
урона и разбор целей идут после показа броска и ожиданий, когда ответ сервера
эффект из мира уже убрал. Поэтому расход (он уезжает на сервер сразу — другие
атаки эффекта не увидят) отделён от расчёта: `dispatchAttackRollTriggers`
возвращает снимок броска `AttackRollSnapshot` — цели и израсходованные
эффекты сторон, какими они были до расхода, с их местами в списке
(`listHeldAttackEffects`). Окно отдаёт снимок каждому обработчику урона
(`onRoll`, `onRollParts`, `onProjectileAttack`, `onHit`), обработчик собирает
сущности разбора `listAttackResolutionEntities(attack)` и кладёт снимок в
контекст; разбор считает стороны по свежей сущности мира с израсходованными
эффектами на прежних местах (`withHeldAttackEffects`): защиты цели,
сопротивления, которые игнорирует атакующий, условия частей по цели. Держатся
только эффекты, израсходованные этим броском, — остальное состояние сторон
свежее (эффекты прежнего каста, снятые концом концентрации, не возвращаются);
запись идёт от свежей сущности, и снятый эффект снимком урона не возвращается
(эффекты едут разницей). Одинаково для оружия, заклинания-атаки, серии
снарядов и действия существа, с листа и с панели (тест `attackRollSnapshot`).
Не покрыто: условие наложения эффекта «на цель», читающее наложившего
(`resolveLandingSource`), берёт его из мира без снимка.

Остальные выполняет сервер: после записи урона
атаки окно шлёт `system:client-event { type: 'attackRoll', attackerId,
targetIds, rollMode, landed?, critical? }` (`reportAttackRoll`), система
проверяет, что отправитель управляет атакующим, и прогоняет срабатывания
сторон со спасброском, уроном и получателем (`settleAttackRollTriggers`, VTTG
0.9.520+). Другая сторона атакующего однозначна только при одной цели.
Срабатывания броска атаки собираются со всего, что действует вместе со
стороной (`listAttackRollSources` → `listCarrierEventSources`): её эффекты,
надетые и настроенные предметы, черты существа.

**Крит и урон срабатывания.** Урон срабатывания на броске атаки идёт отдельным
броском сервера, но при критическом попадании кости удваиваются по тому же
правилу, что у урона самой атаки (`doubleDiceInFormula`: кости — да, плоские
прибавки — нет): «Мистическая кара» `(1 + @paid.slotLevel)к8` ячейкой 3-го
круга критом бросает 8к8 — число костей считается после подстановки цены.
Событие несёт признак `critical` (только у попавшего броска), и удваивается
лишь урон ЦЕЛИ этой атаки (`criticalTargetId`): у срабатывания атакующего —
получателю «другая сторона», у срабатывания цели — ей самой. Урон другим
получателям (ответный огонь по атакующему, «всем в радиусе», выбранному),
лечение и временные хиты крит не меняет. Серия снарядов сообщает о броске до
самих бросков — крита у неё в событии нет. Прибавки урона строками `damage.*`
в это правило не входят: они и раньше шли в сам бросок урона атаки.

**События урона** (`engine/effectDamageEvents.ts`, `settleDamageEvents`). Урон
приходит двумя путями: клиент наносит его атакой или заклинанием и шлёт боевой
снимок с ударами (`DndCombatState.damage`, записаны `recordDamageHit`; сервер
урезает их до реально потерянных хитов), сервер наносит сам — урон на ходу, вход
в зону, ответ игрока, срабатывание на атаке. Источники — эффекты на субъекте,
надетые предметы, черты существа и ауры «пока внутри». Порядок: сначала «хиты
упали до 0» по последнему удару — первыми срабатывания с «хиты становятся»,
остальные не идут, если хиты снова больше нуля («Неумолимая стойкость» сохраняет
концентрацию); затем «получил урон» на каждый удар отдельно (правило 2024:
отдельный спасбросок концентрации на каждый источник). Сл формулой читает
`@damage` — урон удара. Урон, нанесённый самими событиями, новых событий не
порождает. Отмена урона (Ctrl+Z), правка хитов на листе и токене и отдых событий
не будят.

**Условие наложения** (`landingCondition`, `passesLandingCondition`) — строка того
же словаря на событии «при наложении»: эффект ложится, только если она выполнена.
Субъект — тот, на кого ложится эффект, другая сторона — кто накладывает;
`source.weaponMastery === true` — удар оружием, приёмом которого атакующий
владеет (`entityHasWeaponMastery`: вид оружия во владениях приёмами или сам
приём). Проверяют клиент при наложении на цель и на заклинателя и сервер при
входе и выходе из зоны и ауры. Считается ДО урона этого удара.

Цель, на которую эффект не ляжет, ради него не бросает: ни спасбросок самого
эффекта (`listLandingEffectsWithOwnSave`), ни спасбросок действия, если своего
урона у действия нет и не ляжет ни один его эффект — не проходит условие
наложения либо цель невосприимчива к состоянию эффекта без урона
(`targetEffectsCanLand`; «Ужасающий облик» не спрашивает нежить и тех, кто к
нему уже невосприимчив). Заклинание со спасброском вовсе без эффектов бросают
как раньше: исход нужен ведущему.

**Варианты** (`variant { group, label, pick? }`, `effectVariants.ts`). Эффекты с
одной группой — альтернативы: ложится один. `pick: random` бросается сам, иначе
перед броском плашка `EffectVariantPromptModal` спрашивает бросающего
(`runWithEffectVariants` в точках запуска: лист и хотбар — заклинания, оружие,
действия и заклинания существ). Группа без выбора не ложится вовсе; выпавшее
пишется в чат. `pick: multi` — бросающий отмечает один или несколько вариантов
группы («выберите 1 или несколько типов существ»), ложатся все отмеченные.

**Для сайта (core-app):** новое значение `variant.pick` — `"multi"` (у всех
эффектов группы одинаковое).

**Применение и включение** (`activation { mode, counter?, amount?, exclusive? }`,
`effectActivation.ts`). Эффект без поля действует постоянно. `use` — эффект
спит (`isEffectDormant`: его не видят сбор эффектов, ауры, срабатывания и отдых)
и ложится копией без признака, когда источник применяют: предмет — пунктом
«Использовать» (`buildItemUseSpell`, расход `spendItemUse`: заряд, иначе единица
у «Расходуемого»; на нуле предмет остаётся строкой «Закончились» —
`isItemDepleted`: не действует, не надет, не применяется и не бьёт), эффект листа — кнопкой
«Применить» (`buildEffectUseSpell`), боеприпас — выстрелом. Копия идёт путём
заклинания (`applyEffectSource`): «на носителе» — боевым каналом, там же сервер
будит «при наложении» (зелье лечит и снимает себя), «на цели» — разбором цели;
Сл 0 у умения — Сл применившего. Расход уходит ДО наложения: сохранение листа
иначе затёрло бы наложенное. `toggle` — эффект ложится с умения выключенным
(`withActivationDefaults`), включение на листе в просмотре тратит ресурс
(`system.classCounters`, `payActivation`) и прогоняет срабатывания «При
включении» (`activate`, `activateEffectOnEntity`) боевым каналом; истечение
длительности и «Снять эффект» такой эффект выключают, а не удаляют
(`removeOrSwitchOffEffects`). Место окна задаёт способы: предмет, оружие,
умение и свои эффекты — оба; у применяемого предмета и умения есть доставка
«на цели». Получателем можно выбрать и себя: расстояние от сущности до своей
единственной фишки — 0 (`measureTokenDistanceOnScene`; у существа с несколькими
копиями на сцене мерится до ближайшей другой копии, как раньше).

**Переключатель предмета** (`listItemToggles`, `switchItemToggle`,
`client/composables/itemEffectToggle.ts`). Эффект предмета с `mode: "toggle"`
включают и выключают пунктами меню предмета («Язык пламени»: зажечь и
погасить). Эффект лежит в инвентаре, поэтому включение — обычное сохранение
сущности, а не боевой канал. Включение проверяет трату хода, берёт цену
ресурсом (`pay`, в том числе заряды самого предмета) и выключением ничего не
стоит. Срабатывания «При включении» у предмета не выполняются. Прибавка урона
«только этим оружием, пока включено» — строка `damage.weapon` эффекта на
оружии. Применяемый эффект оружия (`use`) — кнопка предмета, при попадании он
не ложится.

**Трата хода применения** (`activation.cost`): `action`, `bonus`, `reaction`.
Запрещённая трата («нет бонусных действий», недееспособность) применение и
включение не пускает, сделанная пишется в счёт хода («Замедление»). Выключение
бесплатно.

**Область применения** (`activation.area`, только у `use`): шаблон на карте
вместо выбора одной цели — конус, сфера, линия, куб. Применивший ставит шаблон
(`placeAreaTemplate`), эффекты «на цели» получают все, кого он накрыл, тем же
разбором, что у заклинаний; эффект с доставкой «в зону» остаётся зоной на месте
шаблона (`requestSpellZone`) на срок эффекта: раунды, минуты и часы — столько,
иначе — до снятия вручную. Дальность применения (`range`) ограничивает точку
шаблона. У вариантов одного применения область своя: шаблон ставят по
выбранному варианту (`settleUseSpellArea`), а вариант без области идёт выбором
одной цели — «луч» камня сияния не требует конуса «вспышки». Эффекты одного
варианта делят область между собой, как раньше.

**Кнопка «При действии» с областью.** Срабатывание «При действии» с
получателем «всем в радиусе» (и «наложившему») выполняет сервер: клиент шлёт
событие правил `effectAction`, сервер раздаёт действия, просит спасброски у
владельцев и пишет сводку. У такого срабатывания может быть шаблон
(`area.template`): нажавший ставит его на карту, и получатели — те, кого он
накрыл (отбор «союзники / враги» делает сервер); без шаблона — радиус от фишки
носителя. Действия самому носителю по-прежнему выполняет клиент.

**Для сайта (core-app):** поля `activation`:

- `cost` — `"action"` | `"bonus"` | `"reaction"`;
- `area` — `{ "shape": "cone" | "circle" | "ray" | "rect", "size": <футы от 1>,
  "width"?: <футы, у линии> }`, только при `mode: "use"`;
- `mode: "toggle"` и `"use"` теперь работают и у эффектов предметов и оружия.

У срабатывания (`triggers[]`) в `area` — необязательный `template` той же
формы; событие `activate` принимает получателя `"area"` и `"source"`.

```json
{
  "name": "Тату монстра: Цветной дракон",
  "activation": { "mode": "use", "cost": "action", "area": { "shape": "cone", "size": 30 } },
  "effectTarget": "target",
  "applySave": { "ability": "dexterity", "dc": 10, "dcFormula": "8 + @mod.wis + @prof", "onSuccess": "half" },
  "damageParts": [{ "formula": "2к8 + @mod.wis", "type": "fire" }]
}
```

```json
{
  "id": "breath",
  "event": "activate",
  "cost": "action",
  "recipient": "area",
  "area": { "radius": 0, "template": { "shape": "cone", "size": 15 } },
  "save": { "ability": "dexterity", "dc": 0 },
  "actions": [{ "type": "damage", "parts": [{ "formula": "3к6", "type": "fire" }], "halfOnSave": true }]
}
```

**На выбор из тех, кто в области** (`areaChoice`, `engine/areaChoice.ts`,
`client/composables/areaTargetChoice.ts`). Всё, что ставит шаблон на карту,
превращает его в цели одним разбором — `resolveAreaTargets`: заклинание с
областью (персонажа и существа), действие существа с областью, применение
умения и предмета с областью (`activation.area`), кнопка «При действии» с
шаблоном (`area.template`). Правил два:

- **мёртвых область не задевает** (`isAreaTarget`): существо с меткой «Мёртв»
  спасбросок не бросает и урон не получает; сущность с несколькими фишками в
  шаблоне считается один раз;
- **правило выбора `areaChoice`** — поле эффекта. Одно на применение: его
  несёт любой эффект заклинания, действия или применения (берётся первое
  найденное). Нет поля — задеты все, кого накрыл шаблон, как раньше; записанные
  данные менять не нужно.

Что делает правило: отсеивает накрытых по отношению к применившему (`target` —
тот же словарь, что у «всем в радиусе»), а в режимах «до N» и «ровно N» просит
применившего отметить цели — плашкой выбора цели, той же, что у срабатываний
«по выбору» (`EffectTargetPromptModal`; на большой сцене в ней есть поиск).
Только отмеченные бросают спасбросок, получают урон и эффект. Вопрос задаётся,
когда шаблон поставлен и бросок сделан, — в общем разборе, поэтому работает
одинаково на всех путях. Закрытая плашка — умолчание правила (`fallback`).
Отношение считается по фишкам, как у аур: персонажи друг другу союзники,
существа из компендиума — враждебные; применившего без фишки на сцене ни
«союзники», ни «враги» не находят.

Срабатывания с радиусом от носителя выбирают получателей своим полем `choice`
(`{ radius, target, count, optional, chooser }`) — оно было и раньше; словарь
`target` и плашка у обоих одни. Мёртвых радиус срабатывания по-прежнему не
отсеивает: этот отбор делает сервер, правило области — клиент.

**Для сайта (core-app):** новое необязательное поле эффекта `areaChoice` —
объект рядом с `effectTarget`. Лежит внутри эффекта, а не в «Бое» заклинания,
потому что эффект core-api хранит как есть вместе с незнакомыми ключами
(`UnknownFieldsHolder`) — правка API не нужна, а одно и то же поле годится
заклинанию, действию существа, умению и предмету; у «Боя» заклинания такого
места нет, и у умений с предметами «Боя» нет вовсе. Поля, все необязательные:

- `count` — сколько можно отметить: целое от 1 до 99 либо строка-формула до
  200 знаков от чисел применившего (`"@castLevel + 1"`, `"@mod.cha"`). Нет —
  без предела;
- `mode` — `"upTo"` (до N, можно никого), `"exactly"` (ровно N; накрытых
  меньше — все они), `"all"` (выбора нет, правило только отсеивает). Нет поля —
  `"upTo"` у правила с `count` и `"all"` без него;
- `target` — кого можно выбрать: `"allWithSelf"` (все в области вместе с
  применившим — умолчание), `"all"` (все, кроме применившего), `"allies"`,
  `"enemies"`, `"alliesWithSelf"`;
- `fallback` — кого задеть, если плашку закрыли: `"none"` (никого —
  умолчание) или `"all"` (всех, кого правило допускает).

Примеры:

```json
{ "areaChoice": { "count": 6 } }
```

«Замедление» (`spells/slow-phb`): до шести существ на выбор в кубе — поле
ставится в эффект «Замедленный» (доставка «на цели»).

```json
{ "areaChoice": { "target": "enemies" } }
{ "areaChoice": { "target": "all" } }
{ "areaChoice": { "count": "@castLevel", "mode": "exactly", "target": "allies", "fallback": "all" } }
```

«Только враги в области» без вопроса; «все, кроме вас»; «ровно столько
союзников, каков круг ячейки, а без выбора — все союзники в области».

Что пока не покрыто: заклинание с областью, у которого только урон и нет ни
одного эффекта, — правилу негде лежать (нужно поле в «Бое» заклинания, то есть
правка API); в окне эффекта системы поля нет — оно заполняется на сайте, окно
его сохраняет как есть.

**Перемещение на выбор и перенос вплотную** (`engine/effectMoveChoice.ts`,
`forcedMovement.ts`). У действия `move`:

- `kind: "bring"` — перенос вплотную к опоре («телепортируется в незанятое
  пространство в пределах 5 футов от вас»); расстояние не читается, запрет
  телепортации его останавливает;
- `kind: "choose"` — оттолкнуть или притянуть, выбирает применивший;
- `upTo: true` — расстояние «до N», выбирает применивший (шаг — клетка, есть
  «не двигать»).

Выбор спрашивают на столе у применившего вместе с выбором варианта эффекта
(`runWithEffectVariants` → `runWithMoveChoices`) — до спасброска цели; выбранное
записывается в действие, и серверу оно приходит обычным. Где спросить некого
(срабатывание ауры, ход), «на выбор» толкает от опоры, «до N» — на все N.

Фишка после перемещения стоит в клетке (`resolveForcedMovePosition`):
расстояние считается по счёту сетки сцены — на квадратной сетке диагональ
стоит по её правилу (`diagonalRule`, по умолчанию клетка наискось = 5 футов), —
а итоговая точка привязывается к сетке (`snapTokenTopLeft` ядра). До 0.8.189
толчок на 5 футов наискось уводил фишку на 0,7 клетки по каждой оси — мимо
сетки («Телекинетический толчок» ставил её в 1085,565).

**Для сайта (core-app):** у действия `move` — новые значения `kind`: `"bring"`,
`"choose"`; новое поле `upTo: true`:
`{ "type": "move", "kind": "choose", "distance": 10, "upTo": true }`.

**Срок «до конца текущего хода»** — поле эффекта `turnCurrent: true` при сроке
`duration.type: "turn"` с концом хода: эффект, наложенный в ход того, по чьему
ходу считается срок, кончается с концом этого же хода, а не следующего
(`stampTurnDuration`). Наложенный вне хода якоря — как всегда. Контракт срока
ядра не тронут: поле лежит на эффекте.

**Для сайта (core-app):** `"turnCurrent": true` рядом с
`"duration": { "type": "turn", "value": 1, "turnTiming": "end" }`.

**Рассеивание от круга ячейки** — у действия `dispel` поле
`maxLevelFormula` (строка, до 200 знаков): `"@castLevel"`. Число подставляется
при касте; не посчиталась — действует `maxLevel`.

**Для сайта (core-app):**
`{ "type": "dispel", "maxLevel": 3, "maxLevelFormula": "@castLevel" }`.

**Одно включение** (`isSameEffectActivation`, `needsActivationPayment`,
`canSwitchOnEffect`). Переключатели одного включения горят по одному:
включение другого гасит прежний и ресурс **не тратит** — это та же ярость.
Включение с нуля тратит как обычно; выключил и включил снова — снова трата.
Одно включение — это:

- варианты одного переключателя (`variant.group`, ключ `effectToggleGroupKey`:
  «Ярость диких земель» — Медведь, Орёл, Волк) — без пометки в данных;
- переключатели с одним ресурсом и одним **именем включения**
  `activation.exclusive` (строка, до 100 знаков, только у `toggle`; форма
  эффекта — поле «Одно включение» рядом с ресурсом). Так «Ярость» класса и её
  копии в умениях подклассов (`exclusive: "Ярость"` у всех) становятся одной
  яростью: при горящем Орле включение «Ярости» класса гасит Орла без траты.

Без пометки переключатели на общем ресурсе независимы — и это нужно: на
проде ресурс Дикой формы тратят и её копии («Дикая форма (Круг луны)»), и
умения, которые горят ВМЕСТЕ с ней («Гнев моря», «Симбиотическая сущность»,
«Обряд Кровавой луны», «Воплощение погибели»). Правило «общий ресурс = одно
включение» сломало бы их, поэтому система объединяет только по пометке.
Ресурс входит в ключ: одно имя на разных ресурсах — разные включения, и смена
не переводит включение на чужой ресурс бесплатно. Правило одно для вкладки
«Эффекты», строки особенности и панели быстрого доступа (`toggleEntityEffect`):
на вкладке группа вариантов в просмотре — одна строка с выбором варианта при
включении, у горящей — её вариант («Ярость диких земель · Орёл»).

**Для сайта (core-app):** поле `activation.exclusive` — необязательная строка
рядом с `counter`, пишется только у переключателя; пустое не пишется. Данные:
все переключатели на `rage` — `exclusive: "Ярость"`; копии Дикой формы —
`"Дикая форма"`; «Гнев моря» и «Гнев моря (Рождённый бурей)» — `"Гнев моря"`;
«Обряд Кровавой луны» и его «Кровавая жажда» — `"Обряд Кровавой луны"`.
Старая система (≤ 0.8.121) поле не знает и молча отбрасывает.

**Цена ресурсом (`pay`, `engine/effectPay.ts`).** Плата не действием, а
ресурсом: «потратьте ячейку заклинания», «бросьте одну или две свои Кости
Хитов», «потратьте 6 очков удали». Одна форма на три места:

- **у эффекта** (`effect.pay`) — её платит тот, кто эффект запускает: у
  заклинания это цена каста сверх ячейки («вы должны потратить две Кости Хитов,
  иначе заклинание провалится»), у применения (`activation.mode: "use"`) и
  переключателя (`"toggle"`) — цена кнопки. Цена одна на каст или кнопку: берётся
  у первого эффекта источника, у которого она задана (`collectSourcePay`);
  выбранный вариант — после выбора варианта. У эффекта, который действует
  постоянно, цена — неработающее поле: платить некому;
- **у срабатывания** (`trigger.pay`) — её платит носитель эффекта. Ресурс —
  решение человека, поэтому срабатывание с ценой спрашивает владельца так же,
  как цена «Реакция»: «Заплатить цену?» либо «Чем заплатить?» с вариантами
  (круг ячейки, число костей) и «Не платить». Цена в вопросе названа по
  листу платящего (`describePayPlan`): счётчик — как на листе, а не ключом,
  количество — посчитанным числом, а не формулой; цена «Реакция» рядом с
  ценой ресурсом названа тоже («Потратить реакцию и заплатить цену?»,
  «Цена: реакция и 1 заряд»). Платить нечем — вопроса нет,
  срабатывание молчит. Эффект «на цели» с таким срабатыванием «при наложении» —
  это «платит получатель» («цель может потратить Кость Хитов»).

Платёж — объект с `kind`:

| `kind` | Поля | Что тратит |
|---|---|---|
| `counter` | `counter` (ключ), `amount?`, `max?` | счётчик листа `system.classCounters` |
| `hitDice` | `amount?`, `max?` | кости хитов платящего; грань — из класса, при нескольких гранях её выбирает игрок |
| `spellSlot` | `minLevel?`, `maxLevel?`, `pact?` | ячейку заклинания: круг выбирает игрок; `pact: true` — только ячейка договора |
| `itemUses` | `amount?`, `max?` | заряды предмета, с которого пришёл эффект; заменяет обычный расход применения, `"0"` — бесплатно |
| `inspiration` | — | героическое вдохновение |

`amount` и `max` — строки: число или формула по платящему (`"2"`,
`"@castLevel"`, `"1 + @mod.con"`). Нет `amount` — одна единица. `max` — верхняя
граница выбора: игрок платит от `amount` до `max` («одну или две кости», «от 1
до 5 единиц»); `amount: "0"` с `max` — цена по желанию. Платежи в списке
платятся ВСЕ («кость хитов и использование умения»). Формула с `@castLevel` у
цены каста заставляет спросить круг до оплаты — дальше каст идёт этим кругом.

Порядок оплаты один на все пути: разбор цены по листу (`planEffectPay`) → отказ,
если ресурса не хватает → выбор там, где вариантов больше одного (плашка
`EffectPayPromptModal` на клиенте, вопрос владельцу у срабатываний сервера) →
списание (`settleEffectPay`) и строка в чат. Ресурсы листа боевой канал не
несёт, поэтому оплата уходит обычным сохранением сущности и ДО наложения
эффектов; прежний расход источника (счётчик `activation.counter`, заряд
предмета) уходит тем же сохранением.

Потраченное подставляется в формулы токенами `@paid.*` (`effectPaidTokens.ts`)
и записывается в эффект полем `paid` — как круг каста:

| Токен | Что подставляет |
|---|---|
| `@paid.slotLevel` | круг потраченной ячейки |
| `@paid.hitDice` | сколько костей хитов потрачено |
| `@paid.hitDie` | грань потраченных костей |
| `@paid.hitDiceRoll` | сумма броска потраченных костей — бросок ОДИН, при оплате |
| `@paid.counter` | сколько единиц счётчиков потрачено |
| `@paid.itemUses` | сколько зарядов предмета потрачено |

Токены работают во всех формулах эффекта (модификаторы и их условия, урон при
наложении и каждый ход, формулы действий срабатываний, срок формулой, Сл
формулой, радиус ауры) и — у цены каста — в уроне и лечении самого заклинания
(`bindSourcePaid`). «Бросьте потраченные кости заново каждый ход» —
`(@paid.hitDice)к(@paid.hitDie)`; «урон равен броску потраченных костей» —
`@paid.hitDiceRoll`. Кости бросаются, только если сумму кто-то читает: иначе они
лишь цена. Платёж, которого не было, — ноль. У наложенной копии числа вписаны в
формулы, а цена снята; переключатель остаётся шаблоном — его числа читаются из
`paid` при сборе эффектов (`bindLivePaid`), выключение `paid` стирает. Эффект
заклинания, у которого кроме цены ничего нет, после оплаты не накладывается —
так цену держит заклинание, чей урон записан в его собственных полях. До каста
лист показывает подпись токена («бросок потраченных костей хитов»).

Кости хитов тратятся тем же `hitDiceUtils.spendHitDice`, что и на коротком
отдыхе, и бросаются по тем же правилам черт (`resolveHitDiceSpendRules`): флаги
`hitDice.maximize` («максимум вместо броска»), `hitDice.lowAsThree` («1 и 2
считаются как 3») и `hitDice.firstFree` («первая кость после отдыха не
тратится» — отметка в `system.effectUsage`, отдых её сбрасывает).

У существа ресурсов листа нет: ячейка и кости хитов не списываются (их ведёт
ведущий), число всё равно выбирается и уходит в формулы; счётчиком, зарядами и
вдохновением существо не платит. Списанное не возвращается, если игрок закрыл
окно броска после оплаты.

**Для сайта (core-app):** новые поля внутри эффекта:

- `pay` — массив платежей у эффекта и у срабатывания (`triggers[].pay`), не
  больше 4; пустой не пишется. Платёж: `{ "kind": "counter", "counter":
  "<ключ>", "amount"?: "<формула>", "max"?: "<формула>" }`, `{ "kind":
  "hitDice", "amount"?, "max"? }`, `{ "kind": "spellSlot", "minLevel"?: 1–9,
  "maxLevel"?: 1–9, "pact"?: true }`, `{ "kind": "itemUses", "amount"?, "max"?
  }`, `{ "kind": "inspiration" }`. `amount` и `max` — строки до 100 знаков
  (число система читает тоже); незнакомый `kind` отбрасывается один, без
  остальных;
- `paid` — проставляет система при оплате, редактору его показывать не нужно, но
  стирать при сохранении нельзя: `{ counter?, hitDice?, hitDie?, hitDiceRoll?,
  slotLevel?, itemUses? }` — целые числа от нуля;
- токены `@paid.slotLevel`, `@paid.hitDice`, `@paid.hitDie`,
  `@paid.hitDiceRoll`, `@paid.counter`, `@paid.itemUses` — в любых формулах
  эффекта и в уроне заклинания; подписи — `FORMULA_VARIABLE_LABELS`;
- флаги `hitDice.maximize`, `hitDice.lowAsThree`, `hitDice.firstFree`;
- действие `restore`: `amount` теперь строка-формула (старое число читается),
  новое `set: true` — «установить счётчик в это число»; действие `setHp`: новое
  `formula` (строка) — хиты формулой; действия `applyCondition` и `applyTag`:
  новое `durationFormula` (строка) — срок формулой, без `duration` — в раундах.

Старая система (≤ 0.8.145) полей не знает и молча отбрасывает: эффект работает

**Боеприпасы.** Оружие со свойством «Боеприпасы» заряжают на листе: правый
клик → «Боеприпасы» (`listLoadableAmmunition` — любой расходуемый предмет
инвентаря, кроме того, что стреляет сам; `loadWeaponAmmunition` пишет
`loadedAmmunitionId` оружию, повторный выбор снимает заряд). Не заряжено или
заряженного предмета больше нет — боеприпас подбирается по `ammunitionType`
(стрелы и болты из компендиума). Есть чем стрелять (`tracksWeaponAmmunition`,
хоть и кончившимся) — выстрел берёт его (`findWeaponAmmunition`, надетый
первым): без него атаки нет, магический бонус и эффекты «при применении»
боеприпаса идут в бросок (`withAmmunition`: бонус — полем `ammunitionBonus`,
в разборе атаки и урона отдельной строкой «Боеприпас» рядом с «Магией»
оружия), сам он тратится, когда бросок пошёл (`beforeRoll` окна броска).
Нечем — оружие стреляет как раньше. Строка оружия показывает, чем оно
заряжено и сколько осталось (`findLoadedAmmunition`), или «Не заряжено», если
зарядить есть чем; плитки «Атака» и «Урон» строки и карточка оружия считают
с бонусом заряженного боеприпаса (`withLoadedAmmunition`).

**Панель быстрого доступа.** С листа на панель ложится атака оружием
(`weapon-attack`) и применение предмета с эффектами «при применении»
(`item-use`, `applyEntityItemUse` — без листа, инвентарь пишется в сущность мира).
С вкладки «Эффекты» перетаскивается любой эффект с применением или
переключателем: «Применить» — макрос `effect-use` (`applyEntityEffectUse`,
варианты группы, выбор цели и расход ресурса — как у кнопки листа),
переключатель («Ярость») — тот же `feature-toggle`, что у строки особенности.
Регистрация макроса отдаёт ядру `resolveState`: движок решает доступность
(`describeItemUseAvailability`, `describeWeaponAttackAvailability` — предмета нет,
закончился, нет зарядов, нет боеприпасов) и остаток (заряды, количество
расходуемого, `countWeaponAmmunition`), `toHotbarSlotState` превращает это в
погасший слот с причиной в подсказке и число в углу. Ядро без
`MacroSlotState` (до VTTG 0.9.527) параметр пропускает: кнопка не гаснет, но
закончившийся предмет всё равно не применяется, а оружие не бьёт.

**Условие броска** (`rollCondition`). Эффект с условием не о носителе не входит
в числа листа (`effectAppliesOnSheet` в `resolveActorStats`) и работает только в
бросках, где условие выполнено (`isRollOnlyEffect`, `rollConditionHolds`): его
флаги — `collectRollConditionFlags`, числа и кости — в `evaluateConditionalBonuses`,
`collectBonusRollFormulas`, `collectBonusDamageFormulas`. У атакующего условие из
словаря броска. «Союзник рядом с целью»: клиент кладёт в контекст броска
союзников в 5 фт от цели и их состояния (`findAlliesAdjacentToTarget` →
`listAdjacentAllies` в `auraMath`: фишка того же действующего отношения; бьёт
ближайшая к цели фишка атакующего, другие фишки той же записи — союзники), а
условие решает, какой союзник годится: `target.allyAdjacent` — дееспособный
(«Тактика стаи» 2024), `target.allyAdjacentAny` — любой,
`target.allyAdjacentWith === "<состояние>"` / `target.allyAdjacentWithout ===
"<состояние>"` — в состоянии или без него. В окне это один пункт «Действует» и
поле «Какой союзник» (`ADJACENT_ALLY_CONDITION_OPTIONS`). У защитника — словарь
входящей атаки: вид атаки и
`incoming.attackerCreatureType === "…"` («Защита от добра и зла»); флаги —
`collectIncomingAttackFlags`, КД — `evaluateDefensiveACBonus` (тип атакующего
кладёт окно броска в контекст атаки, ядро передаёт его как есть). Ключ
`attacksAgainst` — прибавка атакующему (`-1d4` у «Защиты от клинков»):
`collectIncomingAttackRollFormulas`, в бросок её добавляет
`buildRollBonusEvaluator` через `composables/incomingAttack.ts`. Все пути атаки
получают это через `resolveTargetedAttackRollMode`.

**Всем в радиусе** (`recipient: 'area'`, `area { radius, target? }`). У событий,
которые выполняет сервер (урон, «0 хитов», наложение, бросок атаки —
`AREA_RECIPIENT_TRIGGER_EVENTS`), действия достаются всем сущностям в радиусе от
фишки субъекта: соседей по сцене даёт ядро
(`SystemTriggerContext.getSceneSurroundings`, VTTG 0.9.523+), отбор и расстояние
— `findEntitiesInArea` той же геометрией, что у аур. Каждый бросает свой
спасбросок (игроку — запросом), изменённые уходят в `related`. Старое ядро
соседей не даёт — в радиусе никого.

**Выбранным** (`recipient: 'choice'`, `choice { radius, target?, count?,
condition?, optional?, chooser? }`). Правила сплошь и рядом говорят «одно
существо на твой выбор» — движок сам такой выбор сделать не вправе. Кандидаты
отбираются так же, как «всем в радиусе» (та же геометрия и отношение фишек), и
дополнительно просеиваются условием кандидата из ОБЩЕГО словаря условий
(`self.creatureType === "undead"`, `self.hp.value <= 10`) — второго словаря для
отбора нет. Дальше уходит запрос владельцу выбирающего — носителя эффекта или
наложившего (`chooser`) — тем же каналом, что спасбросок, со своей меткой
нагрузки (`TARGET_CHOICE_REQUEST_KIND`, `triggerChoice.ts`); окно выбора —
`EffectTargetPromptModal`. Ответ проверяется по списку кандидатов: выбрать того,
кого в запросе не было, нельзя.

Что достанется выбранным, решают обычные действия срабатывания — урон, лечение
(`@heal`), временные хиты (`@heal.temp`), состояние, отметка. «Снять эффект» и
«Закончить каст» остаются эффекту субъекта. Отказ, молчание и «спросить некого»
отменяют срабатывание с заметкой в чат; `optional` делает отказ законным.
События — `CHOICE_RECIPIENT_TRIGGER_EVENTS`: граница хода (там получателя
раньше не было вовсе), урон, «0 хитов», наложение, бросок атаки, вход и выход.
«Авто-спасброски» на выбор не влияют: они про броски.

**Своё срабатывание наложенного состояния** (`applyCondition.triggers`, одна
ступень вложенности). «Сон» кладёт «Бессознательного», который снимается, когда
цель получает урон: `endCast` тут не годится — он снял бы сон со ВСЕХ целей
каста. Вложенное срабатывание живёт на состоянии и реагирует на то, что видит
его носитель (`NESTED_TRIGGER_EVENTS`).

**Аура** (`DndEffectAura`): `radiusFormula` считается от носителя при сборе аур
(`shapeEntityAuras` в `collectAllAuraEffects`, уровень класса подставлен),
`whileCapable` гасит ауру недееспособного носителя. Хост рисует и считает ауры
через `collectAuraEffects` системы — и то и другое работает без ядра.

**Условие ауры на накрытом** (`engine/auraCondition.ts`). Аура с флагами лежит
на каждом, до кого достаёт, ещё и записью в его `activeEffects` (id
`aura_cond_<id ауры у цели>`) — её ведёт сервер ядра. С VTTG 0.9.601 в запись
идёт эффект ауры целиком, а наложившим (`sourceActorId`) записан носитель ауры;
до этого в ней были только имя, значок, числа и флаги, и аура с условием броска
действовала безусловно: «Ореол: помеха исчадиям и нежити»
(`self.creatureType === "fiend, undead" && target.isSource === true`) давал
помеху любому в ауре и по любой цели. Теперь условие броска и условия строк
читаются у самой записи, «цель — носитель ауры» — по её `sourceActorId`.

Целый эффект накрытому не нужен: ту же ауру система получает ещё и списком аур
(`resolveAmbientEffects` на сервере, стор аур на клиенте), и исполняемое
сработало бы дважды — срабатывания на ходу идут и по эффектам сущности, и по
аурам, — а читаемое только с сущности появилось бы зря (кнопка чужого
переключателя, свет, цена, право переброса). Поэтому хук
`shapeAuraCondition` оставляет запись пассивной: числа, флаги, `rollCondition`,
наложивший, состояние и иммунитеты «пока в ауре», метка
(`AURA_CONDITION_CARRIED_FIELDS`); остальное убирается
(`AURA_CONDITION_DROPPED_FIELDS`) и по-прежнему берётся из списка аур. Каждое
поле эффекта обязано стоять в одном из двух списков — проверяет тест
`auraCondition`. В числах листа и в костях спасброска запись и аура из списка
— один эффект (`combineEffectsWithAmbient`, отсев одноимённых). Аура из одних
чисел («Аура защиты») записью не ложится и считается из списка аур; отношение
(`allies` / `enemies`) отсеивает `calculateAmbientAuras`, как и раньше. На ядре
старше 0.9.601 хук не зовётся и запись остаётся урезанной — прежнее поведение.

**Отношение фишки по умолчанию.** Ядро фишку без отношения считает враждебной
(`withTokenDisposition`: сущность → фишка → `hostile`). Существу это умолчание
ставит нормализация (`normalizeCreature`), а персонажу нормализация ставит
«дружественный» (`normalizeActor`, `DEFAULT_ACTOR_TOKEN_DISPOSITION`): персонажи,
собранные мастером создания, отношения не имели, считались враждебными — и
аура «союзникам» накрывала чудовищ, а не отряд. Заданное отношение не
трогается; персонаж-противник отмечается «враждебным» в настройках фишки
(тест `auraAllyDisposition`).

**Спасброски от смерти** (`deathSaves.ts`). Персонаж на 0 хитов бросает из блока
листа (`DeathSavesPanel`): Сл 10, 20 — 1 хит, 1 — два провала, три успеха —
стабилен, три провала — метка «Мёртв». Режим — флаги `save.advantage.death` /
`save.disadvantage.death`, прибавка — ключ `deathSave` (`stats.deathSaveBonus`).
Сервер в `settleCombatState` сбрасывает серию при подъёме хитов (и снимает метку
смерти) и при новом падении до нуля (`syncDeathSavesWithHp`), а урон по лежащему
— провал, крит — два, урон не меньше максимума — смерть (`settleDeathSaveDamage`
в `withDamageEvents`; удар везёт `dealt` — урон до среза хитами). Сброс — пустые
счётчики, не `undefined`: пустое поле выпадает при рассылке.

**Действие существа на себя.** Эффект действия «на существе» ложится на само
существо: у действия без броска — сразу, с броском — после разбора урона
(`applyActionSelfEffects`).

**При наложении** (`applied`, `settleAppliedEvents`). Эффект, который боевой
снимок положил на цель, прогоняет свои срабатывания «при наложении» после
записи снимка: урон события — урон этого же снимка (`@damage`, типы, крит),
другая сторона — наложивший, хиты в условии — уже после урона («оглушён, если
хитов не больше 150»). Урон того же снимка события «получил урон» у только что
наложенного эффекта не будит («Сон» не просыпается от урона наложения).

**Конец каста** (`castEnd`). `removeCastEffects` прогоняет срабатывания снятых
эффектов каста; наложенное ими не привязывается к касту и переживает его
(«Ускорение» — вялость).

**Отдых** (`rest`, `applyActorRest` / `applyCreatureRest`) — по эффектам самой
сущности, её надетых предметов и черт. Порядок один у персонажа и существа:

1. отдых возвращает своё — счётчики, ячейки, заряды, кости хитов, хиты, одну
   степень Истощения (`recoverActor` / `recoverCreature`); у короткого отдыха
   до этого списываются кости, потраченные в окне (`spendShortRestHitDice`);
2. срабатывания «после отдыха» выполняются на уже отдохнувшей сущности
   (`settleRestTriggers`), и всё, что они сделали, входит в патч отдыха;
3. хиты продолжительного отдыха поднимаются ещё раз, если срабатывание сняло
   то, что их держало (уменьшение максимума, запрет лечения —
   `resolveRestedHitPoints`); хиты, которые срабатывание изменило само,
   остаются как есть.

Отсюда: цена «половина оставшихся Костей Хитов» (`ceil(@hitDice.left / 2)`)
считается после возврата костей; степень Истощения, наложенную срабатыванием
отдыха, этот же отдых не снимает (он снял одну прежнюю, срабатывание положило
новую); урон и временные хиты срабатывания остаются поверх полных хитов. Лимит
«раз в отдых» отдых сбрасывает до срабатываний — срабатывание отдыха тратит его
уже на новый период. Отдых без пользы (`rest.noBenefit.*`) ничего не
возвращает, а срабатывания идут — и цену берут с того, что есть. Цена и вопрос
у срабатывания отдыха — см. «Вопрос человеку».

**Урон эффекта** катает один бросок движка — `rollEffectDamageParts`: сервер на
ходу, входе и выходе, в событиях урона и срабатываниях на броске атаки, клиент
для эффекта на цели при попадании (кубиками клиента). Половина при успехе
берётся от суммы частей, защиты цели — после половины.

**Концентрация** (`engine/concentration.ts`) — не галочка, а обычный эффект.
Каст заклинания с концентрацией кладёт на заклинателя метку «Концентрация:
<заклинание>» (`buildConcentrationEffect`, `concentration: true`) с двумя
срабатываниями: «получил урон» — спасбросок Телосложения Сл
`min(30, max(10, floor(@damage / 2)))`, провал — «Закончить каст»; «хиты упали
до 0» — «Закончить каст». Метку видно в списке эффектов, срок — как у
заклинания. Все эффекты каста — на заклинателе, на целях и у зоны (`source.castId`)
— несут один `castId` (`client/composables/spellCasts.ts`). Конец каста — ядро по
`endCasts(casterId, castIds)` (VTTG 0.9.520+) зовёт `removeCastEffects` у всех
существ мира и удаляет зоны каста; снимаются только эффекты с этим `castId`,
наложенные этим заклинателем. Каст заканчивают: провал спасброска, 0 хитов, новая
концентрация того же заклинателя, истёкший срок метки и кнопка «Прервать
концентрацию» на метке (`system:client-event { type: 'endCasts' }`, только тот, кто
управляет заклинателем), а ещё отдых: срок метки отсчитывается раундами боя,
вне боя часов нет, поэтому отдых листа (`runRestWithTriggers`) сам шлёт тот же
`endCasts` и ждёт ответа сервера до своей записи. Продолжительный отдых
заканчивает любую концентрацию (во сне — «Без сознания»), короткий — касты,
которым осталось не больше часа (`listRestEndedCastIds`); остальные эффекты
со сроком вне боя по-прежнему не истекают. Спасбросок концентрации — не против магии; «Боевой
заклинатель» — флаг `save.advantage.vsConcentration`. Зоны, созданные до меток
(без `castId`), новая концентрация снимает по-старому, с клиента. Каст, круг и
наложившего эффект цели получает при наложении (`stampEffectOnApply`) по
заклинателю из контекста разбора — `SpellResolutionContext.casterId`,
обязательное поле: путь каста, который его не передал (лист персонажа у
заклинаний со спасброском до 0.8.179), оставлял эффект без `castId`,
`castLevel` и `sourceActorId` — его не снимали ни конец концентрации, ни
«Рассеивание магии», а `@castLevel` в его формулах не подставлялся.
Порядок у всех путей каста один: ячейка и заряд → `completeSpellCast`
(`client/composables/spellCastCompletion.ts`: конец прежней концентрации →
эффекты на заклинателе с новой меткой → зона) → разбор целей. Эффекты
заклинателя готовит и пишет только он — боевым снимком с разницей эффектов;
сохранение листа после конца концентрации писало сущность целиком, стирало
новую метку и возвращало эффекты прежнего каста. `completeSpellCast`
возвращает промис: он выполняется, когда в сторе не осталось эффектов
закончившихся кастов этого заклинателя (`waitForCastsEnded`, тайм-аут
`CAST_END_WAIT_MS`), и цели разбираются после него (`afterSpellCast`) —
иначе окно спасброска видело бы эффект прежнего каста («Автоматический
провал — из-за… Парализованный»). Эффекты на цель по попаданию атаки ложатся
тоже после доведения каста. У каста существа без окна броска ход и заряд
тратит `commitCastStart` — до доведения (`openCreatureSpellRoll`). Так на всех входах: лист и горячая панель
персонажа (`spellCastFlow.ts`), лист и панель существа
(`creatureSpellCast.ts`), применение умения и предмета
(`effectActivationUse.ts`). Тесты `spellCastCompletionOrder`,
`spellCastFlowCallsites`.

**Сл: «Авто», «Вручную» или «Формулой».** Все поля Сл окна (спасбросок эффекта,
повторный спасбросок, спасбросок срабатывания, проверка «вырваться») — один компонент
`ui/effect/form/SaveDcField.vue`. Где у Сл есть источник
(`layoutAcceptsSourceSaveDc(layout)`: заклинание, действие существа, приём
оружия), выбирается «Авто» — в данных это `SOURCE_SAVE_DC` (0), Сл источника
подставится при наложении — или «Вручную» со своим числом.
Окно-владелец, которое знает источник, передаёт число проп `sourceSaveDc`, и
«Авто» показывает «Сл заклинателя · 13»: лист персонажа и блок существа — через
`resolveCasterSaveDc` окна заклинания, форма действия — Сл самого действия.
Переход в «Вручную» начинается с этого числа. У зоны мастера, предмета и черты
источника нет — число или формула. «Формулой» есть везде, кроме своей Сл
заклинания (см. «Сл формулой» ниже).

**Сл формулой** (`dcFormula`, `engine/effectSaveDc.ts`). Сл умения, которое не
колдует, — «8 + мастерство + модификатор» ВЛАДЕЛЬЦА: варвар пугает Силой, монах
ошеломляет Мудростью, дракорождённый дышит Телосложением; Сл ауры умения — «Сл
ваших заклинаний». Поэтому у каждого поля Сл эффекта есть третий режим —
«Формулой»: при наложении (`applySave.dcFormula`), повторный спасбросок
(`recurringSave.dcFormula`, и у состояния, наложенного срабатыванием), против
урона каждый ход (`recurringDamage.save.dcFormula`), срабатывание
(`triggers[].save.dcFormula`) и проверка «вырваться» (`escape.check.dcFormula`).
Токены — числа владельца (`@prof`, `@mod.*`, `@str`…, `@level`,
`@classLevel`) и `@spellDc`; у событий урона ещё `@damage`. Число `dc` рядом
остаётся запасным: формула с ошибкой или без данных бросается против него.

Считается формула по владельцу эффекта, одним путём для всех полей
(`mapEffectSaveDcs` / `listEffectSaveDcs`):

- эффект, который владелец отдаёт другим, получает его числа при наложении —
  там же, где урон (`bindSourceEffectFormulas`): цель заклинания или умения,
  аура при сборе аур, зона заклинания. Формула без оставшихся `@`-токенов сразу
  становится числом `dc`, поэтому дальше спасбросок ничем не отличается от
  числового;
- срабатывание своего эффекта, которое достаётся другому (другая сторона, «всем
  в радиусе», выбранный), получает числа носителя до броска
  (`bindTriggerSourceSaveDcs`): «Ошеломляющий удар» — Мудрость монаха, а не
  цели, и наложенное им состояние уносит уже готовую Сл повторного спасброска;
- свой эффект носителя (спасбросок самого носителя с Сл формулой) считается в
  момент броска по носителю (`resolveSaveDc`).

**Непосчитанная Сл** (`engine/effectSaveDcProblem.ts`). Формуле не хватило
значения (`@mod.feat` у черты без выбранной характеристики), а запасное число —
0, то есть «Сл наложившего», которой у не-заклинателя нет: итог не больше нуля.
Против нуля спасбросок не бросают — его прошёл бы любой:

- применение эффекта (кнопка «Применить», предмет, действие существа без
  броска — `applyEffectSource`) останавливается до выбора цели и оплаты:
  ресурс и действие не тратятся, уведомление называет формулу и причину
  («в черте не выбрана характеристика»);
- разбор эффектов цели (`useTargetEffectResolution`) такой спасбросок не
  спрашивает и эффект не накладывает — с тем же уведомлением;
- на сервере срабатывание со спасброском (`admitTrigger`) и разовый эффект
  входа в зону или ауру (`runEntryEffect`) пропускаются, лимит и заряд не
  тратятся, а в сводку чата идёт строка «<эффект>: Сл спасброска не посчитана
  (…) — спасбросок не брошен, срабатывание пропущено». Спасбросок с готовым
  исходом («автоматический провал, если…») Сл не читает и идёт как раньше.

Сл от проверки навыка (`applySave.dcSkill`) до броска проверки непосчитанной не
считается.

**Числа владельца в срабатываниях своего эффекта** (`engine/ownEffectFormulas.ts`).
Постоянный эффект умения, черты, надетого предмета и черты существа никто не
накладывал: он лежит на владельце как записан, с `@mod.con`, `@prof`,
`@level`, `@classLevel` и `@choice.*` в формулах и условиях срабатываний. Числа
и выборы подставляются по носителю, когда событие собирает его срабатывания
(`buildTriggerSources` с владельцем → `bindOwnEffectFormulas`): урон, «0 хитов»,
бросок атаки, граница хода, лечение, перемещение, отдых, кнопка «При действии»
и включение. Путь тот же, что у наложения, — выборы и уровень класса
(`bindOwnerTokens`), затем числа листа (`bindSourceEffectFormulas`), без
модификаторов: их и так считает конвейер листа. Запись сущности не меняется —
копия собирается только у эффекта, в котором есть что подставить, и только у
эффектов, слушающих это событие. Ауре чужого токена и эффекту, наложенному
другим, числа подставил их владелец — там подставлять уже нечего. Прежде
часть урона или лечения с таким токеном («Кровавый пир» `1к10@heal +
@mod.con`) у постоянного эффекта молча пропускалась, а условие с `@choice.*`
молча не выполнялось.

**Непосчитанное слагаемое видно.** Часть урона или лечения срабатывания, в
которой после всех подстановок остался `@`-токен (круг ячейки вне каста,
`@mod.spell` у умения без заклинательства, опечатка), бросок по-прежнему
пропускает целиком — наполовину формула не считается, — но пишет об этом в
сводку чата: «Кровавый пир: не посчитано автоматически — 6 + @castLevel»
(`formatSkippedFormulaNote`; события урона и атаки, граница хода, вход и выход,
ответ игрока, кнопка «При действии»). Форма эффекта предупреждает о таком
слагаемом заранее («Не посчитается автоматически»). Условие с выбором, которого
владелец ещё не сделал, не выполняется без строки в чат: срабатывание просто
не начинается.

Сл заклинаний (`@spellDc`) считается только по нужде — это статы листа
целиком: у персонажа — Сл листа, у существа — его заклинательство, у заклинания
и зоны — Сл самого каста.

**Для сайта (core-app):** поле `dcFormula` — необязательная строка до 200 знаков
рядом с `dc` во всех пяти местах выше; пустое не пишется, `dc` остаётся. Пример
`{"ability":"wisdom","dc":10,"dcFormula":"8 + @prof + @mod.str","onSuccess":"negate"}`.
Старая система поле отбрасывает и бросает против `dc`. У срабатываний поле было и
раньше (только на событиях урона) — теперь оно работает на любом событии.

**Своя Сл заклинания** (`Spell.saveDC`, в окне заклинания «Сл заклинания»):
число, не зависящее от заклинателя, — жезл, свиток, предмет. Главнее и листа, и
блока существа (`readSpellOwnSaveDC`): его получают спасбросок заклинания, эффекты
со Сл «Авто» и зона. Без неё Сл считает `resolveSpellSaveDC`: у заклинания со
своей характеристикой — `8 + мастерство + модификатор` с настройкой листа и
прибавками эффектов; своё число в «Настроить заклинательство» остаётся числом.
Персонажу без класса Сл задаётся там же — характеристикой листа или числом.

**Рост области от круга.** Поле ядра `scaling.additionalAreaSize` (VTTG
0.9.580) — на сколько растёт размер области за каждый круг ячейки выше
базового: «Туманное облако» — сфера 20 фт и `20` за круг, на 3-м круге — 60 фт
(`engine/spellAreaScaling.ts`). Поставленный шаблон ядро менять не умеет,
поэтому у такого заклинания круг спрашивается ДО шаблона (плашка со списком
кругов «2-й круг — 40 фт», `chooseAreaCastLevel`), шаблон ставится уже нужного
размера, а окно броска получает тот же закреплённый круг.

Круг выбирается в одном месте и одним и тем же списком. Нужен он раньше окна
броска (область или цена от круга, раздача снарядов, выбор целей) — его
спрашивают заранее: плашкой `SpellCastLevelPromptModal`
(`composables/castLevelPrompt.ts`) либо списком в окне снарядов и целей. В окне
броска такой круг виден, но выключен, с подписью «Круг выбран ранее»
(`spellLevelLocked`). Не нужен заранее — выбирается в окне броска. Один доступный круг
не спрашивается; без поля всё как раньше — сначала шаблон, круг потом. Круг
группы заклинаний существа растит область так же. Заговоры поле не читают.

**Для сайта (core-app):** `scaling.additionalAreaSize` — целое число больше
нуля в единицах области заклинания, только у заклинания 1+ круга с областью.
Пример `{"scaling":{"additionalAreaSize":20}}`.

**Зона на месте шаблона.** Эффект заклинания с доставкой «зоной на месте
области» (`effectTarget: 'zone'`) не ложится ни на цели, ни на заклинателя: после
применения каста на месте шаблона остаётся зона сцены с этими эффектами
(`spellZones.buildSpellZoneDraft` → `custom-area:create-for-entity`). Полигон
строится из шаблона (`templateGeometry.templateToPolygon`) и накрывает те же
центры клеток; Сл 0 и формулы заклинателя (`@mod.spell`, `@prof`…) подставляются
числами до отправки (`stampSourceSaveDcs`, `bindSourceEffectFormulas`); эффекты
помечены `magical` — спасброски от них получают преимущество защиты от магии и в
копиях на существах. Срок — по длительности заклинания: минута = 10 раундов,
час = 600, дольше суток и «до рассеивания» — бессрочно; мгновенное заклинание зону
не оставляет. Отсчитывает срок ядро на ходу заклинателя. Зона концентрации
кончается вместе с кастом (см. «Концентрация» выше). Статус, наложенный
при входе в зону заклинания (`endsWithAreaId`), снимается, когда зоны не стало.
Доводит каст один помощник на все пути — лист, горячая панель, заклинания
существ (`client/composables/spellCastCompletion.ts`): там же на заклинателя
ложатся его эффекты (в том числе аура) — раньше многочастный бросок и существа их
не накладывали.

### Условия: когда они считаются

Это главная развилка контракта — от неё зависит, где условие вообще применимо.

| Семейство | Сколько | Когда считается |
|---|---|---|
| `self.creatureType === "<тип>"` | 15 | **на листе**, фазы 2 и 3 |
| `roll.hasAdvantage` / `roll.hasDisadvantage` | 2 | при броске |
| `target.hp.*` | 3 | при броске (без единой цели — откладывается по целям) |
| `target.creatureType === "<тип>"` | 15 | при броске (то же откладывание) |
| списком и «не из списка» (`=== "a, b"`, `!== "a, b"`) | любые типы | так же, как одиночный тип того же субъекта |
| `incoming.attackType === "…"` | 3 | при входящей атаке, только для ключа `armorClass` |

Из этого следует правило, нарушить которое легче всего: условие носителя уже
посчитано в итоговых статах, поэтому **плоский бонус с ним при броске повторно
не суммируется** (`evaluateConditionalBonuses` его пропускает), а вот
кость-формулы бонус-урона в статы не попадают никогда — их
`collectBonusDamageFormulas`, наоборот, оценивает. Условия по цели на числа
листа не влияют вовсе.

### Токены формул

Значение изменения — формула; её разбирает `formulaParser`.

| Токен | Что подставляет |
|---|---|
| `@mod.str` … `@mod.cha`, `@mod.spell` | модификатор характеристики |
| `@str` … `@cha` | значение характеристики |
| `@prof`, `@level` | бонус мастерства, уровень персонажа |
| `@classLevel` | уровень в СВОЁМ классе (у эффекта без класса — `@level`) |
| `@speed.walk`, `.fly`, `.swim`, `.climb`, `.burrow` | БАЗОВАЯ скорость листа |
| `@dmg.<тип>` | помечает слагаемое типом урона |
| `@dmg.choice(<тип>,<тип>,…)` | тип урона на выбор бросающего — один из списка |
| `@dmg.random(<тип>,<тип>,…)` | тип урона случайно из списка, шансы равные |
| `@heal`, `@heal.temp` | лечение и временные хиты |
| `@spellDc` | Сл заклинаний владельца — только в Сл формулой |
| `@castLevel` | круг ячейки каста — подставляется при касте |
| `@paid.slotLevel`, `@paid.hitDice`, `@paid.hitDie`, `@paid.hitDiceRoll`, `@paid.counter`, `@paid.itemUses` | потраченное ценой ресурсом — подставляется при оплате (§ «Цена ресурсом») |
| `@damage` | урон события — только в Сл срабатывания на событии урона |
| `@dmg.event` | тип только что полученного урона — в уроне срабатывания на событии урона |
| `@tag.<ключ>` | сколько отметок с этим ключом лежит на существе (у счётчика — число ступеней); ключ — латиницей, цифрами и `_` |
| `@hp.temp` | текущие временные хиты |
| `@hitDice.left` | непотраченные кости хитов листа (у существа — 0) |
| `@target.full`, `@target.notFull` | гейт по хитам цели |
| `@target.status.<ключ>` | гейт: у цели есть состояние (`prone`, `bloodied`, своё состояние мира) |
| `@self.status.<ключ>` | гейт: у самого бросающего есть состояние |
| `@target.type.<тип>` | гейт по типу существа цели |
| `@choice.<ключ>` | значения выбора, сделанного на листе владельца, списком через запятую — в условиях (§ «Выбор владельца») |
| `@mod.feat` | модификатор характеристики, выбранной в черте эффекта (§ «Выбор владельца») |

**Порядок расчёта: формулы читают итоговые числа листа.**

1. Сырые характеристики листа.
2. Изменения самих характеристик эффектами (`ability.*`) считаются от сырых
   чисел — здесь круг размыкается: «Сила += мод. Мудрости» и «Мудрость +=
   мод. Силы» друг от друга не зависят.
3. Свои бонусы листа к характеристикам (`system.abilityBonuses`) — от чисел
   после шага 2.
4. Итоговые характеристики, модификаторы, бонус мастерства.
5. Всё остальное — КД формулой, Сл, урон, лечение, цена, максимум счётчика,
   прибавки события, числа срабатываний, прочие строки листа — от итогов
   шага 4.

Контекст с итоговыми числами строит `buildResolvedFormulaContext`
(`resolvedFormulaContext.ts`) — от `resolveActorStats`, тем же расчётом, что
и лист: черта «+1 к Харизме» поднимает и Харизму на листе, и Сл «8 + @prof +
@mod.cha» умения. Внутри конвейера (`effectPipeline.ts`) он запрещён — там
итоговые числа ещё считаются: строки листа, кроме `ability.*`, идут вторым
проходом с характеристиками после первого, а производные ключи Фазы 3 — от
итогов шага 4. Свои бонусы листа к характеристикам второй проход ещё не
видит: они применяются в Фазе 3. Эффекты, уже наложенные на цели, несут
числа, подставленные при наложении, — пересчитываются они только новым
наложением.

**Ауры карты в контексте формул.** Лист считает итоговые числа вместе с
аурами карты, и броски на клиенте — так же: контекст формул клиент строит
одним помощником `buildEntityFormulaContext` (`useResolvedStats.ts`) — с
аурами (`listAmbientEffects`) или с готовыми числами, посчитанными с ними
(тест `resolvedFormulaContext` держит это). Движок аур сам не знает: он
считает с теми, что ему передали (`ambientEffects` — ход в `turnEffects`,
срабатывания сервера). Без аур намеренно считаются хранимые числа —
максимумы счётчиков черт и класса (`featGrants`, `counterResource`): число,
записанное в лист, не должно зависеть от того, кто стоит рядом в момент
пересчёта, — и радиус ауры формулой (`auraMath`): аура, чей радиус зависит
от чужих аур, замкнула бы расчёт. Цена ресурсом и числа действий
срабатываний (`effectPay`, `effectTriggerRunner`) аур пока не получают:
их вызывающие аур не передают — это следующий шаг того же правила. Шаг не
маленький: цену одного срабатывания разбирают трижды — клиент до вопроса
(`planEffectPay`), движок при исполнении (`payTriggerPrice`) и сервер в
отложенных вопросах (`deferredEffectSaves`), — и ауры должны дойти до всех
трёх разом, иначе варианты оплаты у вопроса и у исполнения разойдутся.

**Ауры карты в числах сущности.** То же правило для самих чисел: итоговые
числа сущности мира клиент считает одним помощником `resolveEntityStats`
(`useResolvedStats.ts`) — с аурами, как лист. Им считаются Сл спасброска
каста (`resolveSpellCasterSource`) и применения умения и предмета, числа
окна каста, бонусы к ячейкам, модификаторы «вырваться», показ Сл и урона на
вкладке заклинаний: раньше Сл каста и применения с листа шла без аур, а с
горячей панели — с аурами. Напрямую `resolveActorStats` клиент зовёт только
в местах, названных в тесте `entityStatsCallsites` с причиной: хранимые
числа листа и расчёты ЦЕЛИ (защиты, спасбросок, КД серии снарядов) — урон
цели движок и ядро считают без аур, и клиент тут с ними заодно.

`@castLevel` — круг ячейки, которым сотворено заклинание: «Лунный луч»
`(@castLevel)к10`, «Подмога» `5 * (@castLevel - 1)`. Рост «Боя» заклинания
(`scaling`) касается только урона самого заклинания, а этот токен — любых формул
его эффектов: модификаторов, урона при наложении и каждый ход, урона, лечения и
временных хитов срабатываний, радиуса ауры формулой, срока формулой, Сл формулой.
Число подставляется при касте тем же путём, что и числа заклинателя
(`bindSourceEffectFormulas` с `castLevel` в контексте; обход формул —
`effectTokenBinding.ts`, общий с `@classLevel`), — на цели, на заклинателе и в
зоне; дальше эффект живёт числом. В модификаторы цели круг подставляется тоже
(«Подмога» поднимает хиты цели), хотя остальные числа цели остаются её. Вне
каста (эффект листа, предмет) токен — ошибка формулы: строка не считается.
Размер области самого заклинания и число целей «Боя» — поля заклинания ядра
(`SpellScaling`), эффекту они не принадлежат.

**Для сайта (core-app):** новых полей нет — токен `@castLevel` пишется в
любые формулы эффекта заклинания.

**Числа получателя и функции чётности.** `@tag.<ключ>`, `@hp.temp` и
`@hitDice.left` в формулах листа считаются по носителю; в уроне срабатывания
их считает ПОЛУЧАТЕЛЬ урона (`turnEffects.bindRecipientTokens`): «1к8 за
каждую Точку давления на цели» — `(@tag.pressure)к8`, «теряет временные хиты
и получает столько же урона» — `@hp.temp * 2` (урон сперва съедает временные
хиты). У удара двумя типами одним броском `@dmg.event` — тот тип, который
прошёл условие срабатывания («урон выбранного типа»), а без условия — первый
(`pickEventDamageType`). `@dmg.event` заменяется типом урона события перед срабатыванием
(`effectDamageEvents.bindEventDamageType`) — до вопроса человеку, так что тип
доходит и у срабатывания с ценой «Реакция», галочкой «спрашивать» или ценой
ресурсом; вне события урона часть идёт без типа. Функции `even(x)` и `odd(x)`
дают 1 или 0 — развилка «чётное — временные хиты, нечётное — урон» пишется
множителем: `@paid.hitDiceRoll * even(@paid.hitDiceRoll)`.

**Для сайта (core-app):** новых полей нет — токены и функции пишутся в
формулы: `{ "formula": "2к12@dmg.event" }`,
`{ "formula": "(@tag.pressure)к8", "type": "force" }`,
`"ceil(@hitDice.left / 2)"`, `"@hp.temp * 2"`,
`"@paid.hitDiceRoll * odd(@paid.hitDiceRoll)"`.

`@speed.*` читает базовую скорость, а не итоговую: итоговую считает сам
конвейер, и формула зависела бы от собственного результата.

`@classLevel` — для формул умений класса: «Драконья устойчивость» поднимает
максимум хитов на уровень ЧАРОДЕЯ, и `@level` мультиклассеру насчитал бы вдвое
больше. Число подставляется в формулы там же, где эффекты собираются
(`classEffectScope.bindClassLevels`), а класс эффекта известен по метке в его id
(`class-effect:<ключ класса>:…`), которую ставит мастер класса. У эффекта без
такой метки — своего эффекта листа, предмета, вида, черты — токен читается как
`@level`: у одноклассника это одно и то же число.

Ресурсы класса тот же токен берут не из подстановки, а из контекста: класс у
счётчика записан своим полем (`classKey`), и `resolveCounterMaxIn` кладёт в
контекст уровень именно в нём. Ресурс черты класса за спиной не имеет — там
`@classLevel` тоже читается как `@level`.

Больше нигде класса за формулой не стоит: у заклинания, предмета и действия
существа своего класса нет, и `@classLevel` в них — тот же `@level`. Писать его
там незачем, а форме действия существа он и вовсе запрещён вместе с остальными
`@`-переменными.

Токены-гейты (`@target.*`) — не переменные, а условия на слагаемое: ядро
`expandDamageParts` снимает их и разворачивает часть в ветки. Ветки по хитам
взаимоисключающие, по типу — нет: безусловное слагаемое достаётся любой цели,
типовое ложится сверху только «своим». Отсюда — усиление круга получает ровно
одна ветка внутри ветки по хитам, иначе апкаст удвоится.

Состояния (`@self.status.*`, `@target.status.*`) — такие же гейты, и только
на ПРИБАВКУ: «1к8 + 2к6@target.status.prone» добавляет 2к6 лежащей цели.
Отрицания нет. Состояние бросающего известно до броска, и лишние слагаемые
гасит сама развёртка (`selfHasStatus`; без бросающего — у урона эффекта —
состояний нет). Состояние цели идёт веткой с гейтом `targetStatusGate` и
сверяется в `damageReachesTarget` при нанесении урона — и у единой цели тоже.
Есть ли состояние, решает `entityHasDamageStatus`: наложенный эффект состояния,
а «Окровавленный» (`bloodied`, состояние канона) — ещё и по хитам, без значка.
В окне части урона состояния ставят вкладки «Статусы цели» и «Статусы
атакующего»: на каждой — список всех состояний, канон и мира.

«Иначе другой урон» — это «или» у действия существа (`damageAlternatives`,
`creatureDamageAlternatives.ts`): набор урона целиком заменяет основной.
Условие варианта — состояния в его же формуле: рой — основной урон
`4к8@dmg.necrotic + 2`, вариант `2к8@dmg.necrotic@self.status.bloodied + 2`.
Вариант с состояниями берётся сам, когда все они есть (верхний из сработавших),
и выпадает, когда нет; состояние цели проверяется только у единой цели. Способ
варианта: `formula` (по умолчанию — решают состояния в формуле; без них вариант
не берётся), `ask` — спросить бросающего, `random` — бросить случай. Состояние
в формуле главнее способа. Состояния и случай решаются до окна броска
(`runWithCreatureDamageChoice`), а `ask` — в самом окне: вызывающий собирает
по набору на вариант (`buildCreatureRollVariants` → проп `damageVariants`),
и окно показывает поле «Урон». Строки поля — «подпись: формула», у основного
урона тоже. Если варианты отличаются от основного только типом (так
компендиум пишет «один тип на выбор»), каждая строка называется типом из
справочника, а формула идёт без типа: «Кислотный: 1к6+3», «Огненный: 1к6+3»
— ручные подписи вариантов («Огонь») тогда не показываются, чтобы подпись не
расходилась с типом. Иначе впереди своя подпись варианта или «Основной урон»,
а формула — с типом. Выбранный набор меняет в окне формулу, части,
бонус-части, вопрос о типе урона и применение; в начале броска чат называет
его («Укус: С преимуществом»). Шаблон области ставится до окна, поэтому его
цвет — по основному урону.

### Тип урона на выбор

«Цветной шарик», «Чародейская вспышка», «Духовные стражи», «Дыхание дракона»
наносят урон ОДНИМ типом из нескольких. Несколько токенов на одной кости
(`3к8@dmg.acid@dmg.cold`) значат другое — урон всеми типами сразу, цели
достаётся выгоднейшая защита, — и это значение не меняется. Для выбора есть
свой токен:

| Формула | Что значит |
|---|---|
| `3к8@dmg.choice(acid,cold,fire,lightning,poison,thunder)` | «Цветной шарик»: 3к8 одного типа на выбор |
| `1к10@dmg.choice(acid,cold,fire,lightning,poison,psychic,thunder)` | «Чародейская вспышка» |
| `3к8@dmg.choice(radiant,necrotic)` | «Духовные стражи» (урон зоны) |
| `2к6@dmg.choice(fire,cold) + 1к6@dmg.fire` | 2к6 на выбор и отдельно 1к6 огнём |
| `1к8+3@dmg.choice(fire,cold)` | тип на числе в конце — на весь блок `1к8 + 3` |
| `(1к8+3)@dmg.choice(fire,cold)` | скобки — одно слагаемое |
| `2к6@dmg.choice(fire,cold)@target.status.prone` | сверху по лежащей цели, тип на выбор |
| `4к6@dmg.random(acid,cold,fire,lightning,poison,thunder)` | тип выпадает случайно |

Правила записи — те же, что у `@dmg.<тип>`: токен на кости течёт вправо до
следующего вида, на числе в конце закрывает свой блок, скобки — одно
слагаемое, условия `@target.*`/`@self.status.*` пишутся рядом. Варианты —
ключи типов через запятую, без пробелов внутри ключа; регистр и повторы не
важны. Рядом с `@dmg.choice(…)` простые `@dmg.<тип>` того же слагаемого не
читаются. Старый служебный тип `@dmg.choice` без скобок остаётся как был.

**Для сайта (core-app) и авторов компендиума** формула — обычная строка:
сайт хранит её как есть, токен ничего не требует от схемы. Пишется он везде,
где пишется `@dmg.<тип>`: урон заклинания и ступени заговора
(`damageParts`, `cantripScalingTiers`), урон оружия и предметов, урон
эффектов (`damageParts`, `recurringDamage`, урон срабатываний) и бонус-урон
модификаторов `damage.*` (`1к4@dmg.choice(acid,cold,fire,lightning,thunder)` у
«Стихийного оружия»), урон действий существ и их урон «или».

В форме строки урона (`DamagePartRow`) токен собирает вкладка «Тип на
выбор»: отметить два типа или больше и нажать «На выбор бросающего»
(`@dmg.choice(…)`) или «Случайно» (`@dmg.random(…)`) —
`buildPickedDamageTypeChoiceToken`, типы в порядке справочника.

Когда решается выбор:

- **В окне броска** — у заклинаний, оружия и действий существ, с листа и с
  хотбара (окно атаки или урона; у заклинания без урона — окно выбора
  круга). Вызывающий отдаёт окну вопрос (`requestDamageTypeChoice` → проп
  `damageTypeChoice`): все списки источника — его урон, эффекты «на цель» и
  зоны. Окно показывает поле «Тип урона» на каждый список (один на
  одинаковый список, сколько бы ни было целей и частей) и туда же добавляет
  остаток — бонус-урон собственных эффектов листа (`changes damage.*`).
  В начале броска, раньше урона, попадания и эффектов, окно решает
  `@dmg.random`, пишет в чат «Цветной шарик: тип урона — Огненный» и отдаёт
  итог вызывающему (`onChoose`). Тот подставляет его
  (`applySourceDamageTypeChoices`) во всё, что ляжет после броска, — поэтому
  эффект на цель и урон «Духовных стражей» в начале хода идут типом,
  выбранным при касте. Части урона этого броска окно решает тем же итогом
  (`settleDamageTypeChoices`). Ведущий, бросающий за существо, видит то же
  окно.
- **Плашкой, где окна нет** (`runWithDamageTypeChoices`): заговор или
  врождённое заклинание без броска, действие существа без броска, применение
  предмета. Плашка «какой вариант?» спрашивает тип до действия, итог так же
  подставляется во все формулы источника и уходит в чат.
- **Где спросить некого** — урон эффекта, у которого нет источника броска
  (эффект, повешенный ведущим вручную; бонус-урон снарядов после окна), —
  тип выпадает случайно с равными шансами (`settleDamageTypeChoices` в
  `rollEffectDamageParts`). Урон без типа был бы хуже: к нему не применились
  бы ни сопротивления, ни уязвимости.

Ограничения: у снарядов («Сияющие сферы Эльминстера») выбор один на каст, а
не на каждую сферу; вложенные эффекты срабатываний (эффект, который
накладывает срабатывание) выбор источника не получают и решаются случайно.

Показ: плитка урона в строке листа (действия и заклинания существ,
заклинания персонажа, оружие) всегда компактна — одна формула урона, который
бросается всегда, и значок-развилка `DAMAGE_VARIANTS_STAT_ICON`, если есть
выбор: урон «или» или тип на выбор, как бы он ни был записан. Сами варианты — в
подсказке: «На выбор: Кислотный/Холодный/Огненный» (или «Случайно: …»), у урона
«или» — набор и условие. Добавка по состоянию стороны (`@self.status.*`,
`@target.status.*`) в плитку тоже не пишется: её строка «+ 1к8 (атакующий:
Окровавленный)» идёт в подсказку, а о ней говорит значок
`DAMAGE_BONUS_STAT_ICON` (место под значок одно, выбор важнее —
`resolveDamageStatIcon`). Раскладывает показ движок
(`splitConditionalDamageDisplay` → `combineDamagePartDisplays`). У урона целиком
под условием постоянной части нет (`baseFormula` пуст) — так записан «Святой
мститель» без своей основы: одни добавки `2к10` по исчадиям и нежити. Текст
плитки собирает `formatDamageTileFormula` (`client/composables/damageTypeChoice.ts`):
постоянные кости с прибавкой, без костей — одна прибавка («+3»), без того и
другого — заглушка `DAMAGE_NO_CONSTANT_LABEL` («—») со значком добавок; сами
добавки — в подсказке. Полный текст добавок в плитку не идёт (до 0.8.187 он
раздувал бейдж в списке оружия и выдавливал название предмета). Итог формулы в
редакторе пишет то же «На выбор: …»; описание
эффекта — «3к8 на выбор: кислотой/холодом».

Доходит ли ветка до конкретной цели, решает `damageReachesTarget` — одна функция
на все три точки применения урона: оркестратор заклинаний, урон эффекта при
наложении и периодический урон. Точка, забывшая про гейт, катает все ветки
сразу, и `@target.full` превращается в двойной урон.

### Рукопашная или дальнобойная атака

В 2024-й одной записью бывают обе атаки: у существа «Бросок рукопашной или
дальнобойной атаки: +5, досягаемость 5 фт. или дистанция 30/120 фт.»
(метательное копьё, «Потусторонний удар»), у персонажа — рукопашное оружие со
свойством «Метательное» (кинжал, ручной топор, копьё, лёгкий молот, трезубец,
метательное копьё): им бьют или его бросают. Правило — в
`src/engine/attackKind.ts`, вопрос и чат — `src/client/composables/attackKindChoice.ts`.

**Данные.**

| Источник | Как записан | Досягаемость | Дистанция |
|---|---|---|---|
| Действие существа | `rangeType: "meleeOrRanged"` | `reach` (нет — 5) | `range: { normal, long? }` |
| Оружие | `rangeType: "melee"` + `weaponProperties` с `thrown` + `range.normal > 0` | `reach` (нет — 5) | `range` — дистанция броска |

У оружия нового значения нет: `rangeType` оружия — тип ядра (`WeaponRangeType`,
`melee | ranged`), и метательное рукопашное оружие описывается свойством.
Дальнобойное метательное (дротик) — просто дальнобойное, выбора у него нет.
Старые `melee` / `ranged` и записи без поля работают как раньше; `meleeOrRanged`
там, где вид не выбран (`checkCreatureActionRange`, ключи бонусов), читается
рукопашной — так эти записи работали до выбора.

**Формы.** Окно действия существа: тип атаки «Рукопашная или дальнобойная» —
открыты и досягаемость, и обычная/максимальная дистанция, сохраняются обе.
Окно оружия: у рукопашного с «Метательным» открыты поля дистанции броска, под
ними пояснение, а в предпросмотре под итогом атаки — «Бросок: +N» (свои бонусы
`attack.ranged` у броска другие, чем у удара).

**Бросок.** Перед атакой (лист и хотбар, `runWeaponAttackChoices` /
`runCreatureActionChoices`, затем варианты эффектов) — плашка «какой
вариант?» с вопросом «Вид атаки»: «Рукопашная / Дальнобойная», у оружия
«Удар / Бросок». Если цель выбрана и достаётся только одним видом (за
досягаемостью — только бросок), вопроса нет. Цель вне обеих дальностей —
атака идёт дальнобойной, и обычная проверка расстояния пишет «вне
досягаемости». В чат уходит выбранный вид: «Метательное копьё: бросок
(дальнобойная атака)», с пометкой «— по расстоянию до цели», если выбрался сам.

Дальше бросок идёт копией записи с конкретной дальностью
(`withCreatureActionAttackKind` / `withWeaponAttackKind`), то есть целиком
выбранным видом: проверка расстояния (досягаемость либо дистанция, помеха за
обычной дистанцией), флаги и прибавки `attack.melee` / `attack.ranged`,
`damage.melee` / `damage.ranged`, вид входящей атаки для эффектов цели.
Характеристика брошенного оружия — та же, что у удара: Сила, у
«Фехтовального» — бо́льшая из Силы и Ловкости. Боеприпас не тратится (у
метательного его нет); учёта брошенного оружия в системе нет — оружие остаётся
в руках.

**Импорт из компендиума TTG Club.** Нормализация существа
(`normalizeCreature` → `normalizeCreatureActionRangeType`) принимает
`rangeType` записей `traits`, `actions`, `bonusActions`, `reactions`,
`legendary.actions`, `lair.effects` в каноне и в написании перечисления
сайта: `meleeOrRanged`, `MELEE_OR_RANGE`, `melee_or_ranged` →
`meleeOrRanged`; `RANGE` → `ranged`. Незнакомое значение остаётся как есть.

**Контракт для API (`core-api`, `VttgCreatureMapper.rangeType`).** Запись с
типом атаки `MELEE_OR_RANGE` отдавать так:

```json
{
  "rangeType": "meleeOrRanged",
  "reach": 5,
  "range": { "normal": 30, "long": 120 },
  "distanceUnit": "ft"
}
```

`range.long` — только если есть; «дистанция 120 фт.» — `{ "normal": 120 }`.
Сейчас API отдаёт такие записи как `"melee"` с `reach` и `range`: они
работают рукопашной, как раньше, а сама по `melee` + `range` система вид не
угадывает — ошибочно заполненная дальность у чистой рукопашной записи дала бы
лишний вопрос. У оружия API менять не нужно: `VttgItemMapper` уже отдаёт
метательному `rangeType: "melee"`, свойство `thrown` и `range`.

Ограничения: помехи дальнобойной атаке вблизи врага (5 фт. от видящего
противника) в системе нет вовсе — ни у обычных дальнобойных, ни у броска.
Прибавки, записанные только на рукопашный урон (`damage.melee` с условием
«Атака: Силой» у «Ярости»), броску не идут: по правилам 2024 «Ярость»
действует на любую атаку Силой, для броска данным нужна та же строка на
`damage.ranged`.

### Тип существа

Словарь один на всю систему — 15 типов (`CREATURE_CATEGORIES`): им подписаны и
статблок существа (`system.type`), и вид персонажа, и чипы урона, и условия
эффектов. У листа порядок такой: свой выбор в настройках (`system.creatureType`)
главнее вида, без обоих лист считается гуманоидом. У существа умолчания нет:
чужой тип в статблоке оставляет сущность без типа — подставлять «гуманоида»
значило бы молча менять механику чужого мира.

**Условие по типу** (`engine/creatureTypeCondition.ts`) — тип носителя, цели или
атакующего из списка или вне его: `target.creatureType === "undead, fiend"`,
`self.creatureType !== "construct, undead"`,
`incoming.attackerCreatureType === "aberration, celestial, elemental, fey, fiend, undead"`.
Одиночный тип — список из одного, старые условия работают как были. Разбор
один на весь словарь: модификаторы (плоский бонус по типу носителя — на листе,
по типу цели — в броске), условие броска эффекта («Действует»: бонусы,
преимущество и помеха в своей атаке), защита («Атаки по носителю», КД) и
срабатывания (`selfCreatureType` / `otherCreatureType` и их «не из списка»;
«другая сторона» — атакующий, источник урона, наложивший). В окне «Действует»
это один пункт на субъект со списком типов и переключателем «Кроме этих
типов»; в условии срабатывания — выбор нескольких типов. Тип, которого нет в
данных, условию не отвечает ни «да», ни «нет». Бонус-кость по типу цели без
единой цели (область) раскладывается веткой на каждый тип списка — цель одного
типа проходит ровно одну; «не из списка» веткой не выразить, и без единой цели
такой бонус не бросается. Спасбросок знает тип того, кто его вызвал
(`source.creatureType`, `saveSourceConditions.ts`): эффект с таким условием
броска на числа листа не влияет, а в спасброске от существа нужного типа
включает свои флаги и прибавки («Защита от зла и добра» — преимущество). Тип
источника берётся у заклинателя или существа; в запросе игроку едет в
нагрузке (`sourceCreatureType`); у эффекта, который потом бросает сервер
(зона, ход), наложивший при наложении пишет свой тип рядом с
`sourceActorId` — поле эффекта `sourceCreatureType`.

**Для сайта (core-app):** новых полей нет — меняется запись условия: список
типов в кавычках через запятую и оператор `!==` для «не из списка» (в
`changes[].condition`, `rollCondition`, `triggers[].condition`,
`landingCondition`, `choice.condition`). Новый субъект — `source.creatureType` (тот, кто
вызвал спасбросок); поле эффекта `sourceCreatureType` ставит система при
наложении, сайту его писать не нужно. Старая система понимает только один
тип и `===`: условие со списком она не узнает и не применит.

### Выбор владельца в условиях и формулах

Умение ссылается на выбор, сделанный в другом месте листа: «спасброски против
заклинаний существ из вашего Гримуара — с преимуществом», «Сл = 8 + бонус
мастерства + модификатор характеристики, увеличенной этой чертой». Эффект пишет
токен, лист владельца подставляет своё (`engine/effectChoiceBinding.ts`):

- `@choice.<ключ>` — значения выбора списком через запятую. Стоит на месте
  списка в условии: `target.creatureType === "@choice.monster-manual"`,
  `source.creatureType === "@choice.monster-manual"`,
  `damage.type === "@choice.energy"`. Тип существа в списке читается ключом
  (`undead`) либо названием («Нежить»).
- `@mod.feat` — модификатор характеристики, выбранной в ЭТОЙ черте:
  заклинательной (выбор вида «заклинательная характеристика») либо первой
  повышенной ею. Становится обычным `@mod.cha`.

Ответы ищутся сначала у черты, которой принадлежит эффект (`originId` вида
`feat:<id>`), затем по всему листу: выборы вида
(`system.species.featDataChoices`), классов (`system.classes[].choiceAnswers`),
черт и вариантов умений (`features[].choices`; ответ варианта доступен и под
коротким ключом). Подставляет владелец — там же, где уровень своего класса
(`bindOwnerTokens`): при сборе своих эффектов, аур и эффектов «на цель». Аура
несёт выбор того, кто её излучает. Токен без ответа остаётся как есть: условие
с ним не выполняется, формула уступает запасному числу.

Ответы на выборы класса, подкласса и их умений (`featData.choices`) мастер
класса теперь пишет в запись класса на листе (`choiceAnswers`). У персонажей,
созданных раньше, их нет: выбор «Гримуара» надо сделать заново — иначе
условие по нему не выполняется.

Собственные выборы черты (`features[].choices`) спрашивает каждый путь, которым
черта попадает на лист: окно выбора при перетаскивании, мастер предыстории,
мастер вида (и у выбранной черты, и у выданной дарами без выбора) и мастер
уровня — у черты вместо повышения характеристик (шаг характеристик), у черты,
выбранной в умении, и у выданной дарами записи (в строке того, кто её дал).
Правило одно — `engine/takenFeats.ts` (`buildTakenFeat`, `isTakenFeatAnswered`,
`withTakenFeatAnswers`): вопросы те же, что у окна выбора
(`resolveFeatChoicesToAsk`), без ответа шаг не пройти. До 0.8.186 мастер уровня
клал черту без ответов: «Телекинетик» ложился без прибавки и характеристики, а
`@mod.feat` в Сл его умения оставался без значения — у заклинателя молча
бралась Сл заклинаний. Персонажам, получившим черту так раньше, выбор надо
сделать заново (снять черту и взять снова).

В окне: у условия «Действует» по типу существа — поле «или ключ выбора
владельца»; у условия срабатывания — части «Другая сторона — тип из выбора
владельца» и «Урон типа из выбора владельца» (значение — ключ выбора); в
строке модификатора условие вписывается текстом.

**Для сайта (core-app):** новых полей у эффекта нет — токены пишутся в уже
существующие строки: `@choice.<ключ>` на месте списка в `rollCondition`,
`changes[].condition`, `landingCondition`, `triggers[].condition`
(`target.creatureType === "@choice.<ключ>"`,
`source.creatureType === "@choice.<ключ>"`, `damage.type === "@choice.<ключ>"`);
`@mod.feat` — в любой формуле эффекта черты (`dcFormula`, значения, урон).
Ключ — ключ выбора из `featData.choices` (буквы, цифры, `-`, `_`, `#`, `:`).
Значения выбора типов существ должны быть ключами типов либо их названиями.

```json
{
  "name": "Тайное вмешательство",
  "flags": ["save.advantage.vsSpell"],
  "rollCondition": "source.creatureType === \"@choice.monster-manual\""
}
```

```json
{ "applySave": { "ability": "strength", "dc": 10, "dcFormula": "8 + @prof + @mod.feat", "onSuccess": "negate" } }
```

### Наложивший эффект в условиях броска

Эффект лежит на противнике, а условие — о том, кто его наложил
(`sourceActorId` эффекта):

- `target.isSource === true` / `=== false` — цель броска носителя (не) тот, кто
  наложил эффект: «помеха на броски атаки против вас» («Мерцание») и «помеха
  атакам по всем, кроме вас» («Непристойный жест»). Условие броска эффекта
  (`rollCondition`) или строки (`changes[].condition`);
- `incoming.attackerIsSource === true` / `=== false` — атакует (не) наложивший:
  «преимущество на атаки по цели для всех, кроме вас» — у защитного эффекта.

Без цели, без атакующего или без наложившего часть не выполняется. В окне —
пункты списка «Действует» и библиотеки условий.

**Для сайта (core-app):** четыре строки условия — `target.isSource === true`,
`target.isSource === false`, `incoming.attackerIsSource === true`,
`incoming.attackerIsSource === false` — в `rollCondition` и
`changes[].condition`. Пример:
`{"flags":["attack.disadvantage"],"rollCondition":"target.isSource === false"}`.

### Вид и подтип существа, второй тип

**Условие по виду** (`engine/speciesCondition.ts`): `self.species === "эльф"`,
`self.species !== "дварф, дуэргар"`, `target.species === "…"`,
`target.species !== "…"`. Вид — ключ и название вида и подвида персонажа либо
подтип статблока существа (`system.subtype`, через запятую); сравнение без
регистра. У существа без подтипа и персонажа без вида названий нет: «из
списка» не выполняется, «не из списка» — выполняется. Условие о носителе
считается на листе (годится для постоянных чисел — «Пояс дварфов»), в
срабатываниях и условии наложения (`landingCondition`: «Когти вурдалака» —
`self.creatureType !== "undead" && self.species !== "эльф"`); о другой стороне
— в срабатываниях.

**Второй тип существа**: строка `creatureType.extra` (значение — ключ типа)
добавляет тип к своему, а не заменяет («получаете тип существа цели в
дополнение к собственному»). Условия по типу считают оба: «из списка» — любой
из типов, «не из списка» — ни один. Токен `@target.type.*`, тип источника
спасброска и подпись листа видят только основной тип.

**Для сайта (core-app):** условия по виду — строки
`self.species ===|!== "<названия через запятую>"` (в `changes[].condition`,
`rollCondition`, `landingCondition`, `triggers[].condition`) и
`target.species ===|!== "…"` (в `triggers[].condition`); ключ строки
`creatureType.extra` со значением-типом
(`{"key":"creatureType.extra","mode":"override","value":"fey"}`).

### Иммунитет к состоянию от существ типа, снятие по типу наложившего

`conditionImmunities` у эффекта с условием `source.creatureType === "…"` в
`rollCondition` — иммунитет только к состояниям, которые накладывают существа
этих типов («Защита от зла и добра»: не может быть очарована или испугана
такими существами). Тип накладывающего берётся у заклинателя, у существа
действия либо с эффекта (`sourceCreatureType`); неизвестен — иммунитета нет.
Эффект без такого условия даёт иммунитет всегда, как раньше.

Действие `removeCondition` с `fromCreatureTypes` снимает только состояния,
наложенные существами этих типов («Рассеивание добра и зла»): тип наложившего
система пишет на эффект при наложении; состояние без него остаётся.

«Иммунитет на 24 часа после успешного спасброска» выражается без новых полей
(сценарий C18): срабатывание источника с условием «нет отметки от наложившего»
(`self.tagFromSource !== "<ключ>"`), при успехе — действие `applyTag` с этой
отметкой на 24 часа.

**Для сайта (core-app):** `conditionImmunities` + `rollCondition` с
`source.creatureType` — уже существующие поля, меняется только их совместный
смысл; у действия `removeCondition` — необязательный массив
`fromCreatureTypes` (ключи типов существ):

```json
{ "type": "removeCondition", "conditionKey": "charmed", "fromCreatureTypes": ["fey", "fiend", "undead"] }
```

### Спасбросок: характеристика на выбор и Сл от проверки

- `altAbilities` у спасброска эффекта (`applySave`) и срабатывания
  (`triggers[].save`) — ещё характеристики на выбор бросающего: «спасбросок
  Силы или Ловкости». Бросающий берёт лучшую из названных
  (`engine/saveAbilityChoice.ts`), при равенстве — первую по записи.
- `applySave.dcSkill` — Сл равна итогу проверки навыка применившего («совершите
  проверку Харизмы (Запугивание); спасбросок Мудрости со Сл, равной результату
  проверки»). Работает у эффекта «при применении»: после выбора цели
  применивший бросает проверку (обычное окно навыка, со всеми его бонусами),
  итог записывается Сл; закрытое окно применение отменяет и ничего не тратит.
  `dc` остаётся запасным числом.
- «Штраф к спасброску за каждого пострадавшего» — без новых полей: варианты
  одной группы со своей `dcFormula` (`… + N`), число называет игрок при
  применении.

**Для сайта (core-app):** `altAbilities` — массив характеристик (до 5) у
`applySave` и `triggers[].save`; `dcSkill` — ключ навыка у `applySave`:

```json
{ "applySave": { "ability": "strength", "altAbilities": ["dexterity"], "dc": 0, "dcFormula": "8 + @mod.con + @prof", "onSuccess": "negate" } }
```

```json
{ "applySave": { "ability": "wisdom", "dc": 10, "dcSkill": "intimidation", "onSuccess": "negate" } }
```

Порог крита по цели: строка `critThreshold` с условием о цели
(`target.creatureType === "…"`) считается в броске атаки оружием
(`resolveRollCritThreshold`) — новых полей нет.

### Мелкие блоки этапа 2A

**Тип урона заклинания на выбор** (`engine/spellDamageRetype.ts`). Строка
эффекта носителя `spell.damageType` со значением — ключом типа урона (слово из
списка, как у замен оружия: `getChangeValueOptions`). При касте
заклинания с уроном (лист, хотбар, заклинания существа) тип каждой части урона
и урона его эффектов становится выбором «свой или новый» — обычным
`@dmg.choice(…)`, и вопрос задаёт тот же разбор, что у «Цветного шарика»: в
окне броска или плашкой. Свой тип всегда первый — «можете» соблюдается
выбором. У оружия тип меняет `weapon.damageType` (без вопроса).

**Прибавки «в момент события»** (`engine/offSheetChanges.ts`). Строки-прибавки
(`mode: "add"`, значение — формула), которых на листе нет:

- `tempHp.gain` — «+5 к получаемым временным хитам»: считается при каждой
  выдаче (`healingLimits.withTempHpGainBonus`) — лечением, эффектом,
  срабатыванием;
- `attack.reach` — «досягаемость +10 футов»: считается при проверке расстояния
  рукопашной атаки оружием и действием существа
  (`withMeleeReachBonus` в `attackKindChoice.ts`). «На одну атаку» задаёт срок
  эффекта или его снятие после броска атаки.

**Минус кость к урону.** Строка урона со знаком минус (`damage.all` =
`-1к6`) вычитается из урона атаки носителя: вычет защиты цели и спасбросок не
меняют, итог не опускается ниже нуля (`useSpellDamageWithParts`). Одинаково у
атак персонажа и существа: вычет — отдельная бонус-часть броска. Роллеру
клиента она отдаётся как вычитание из нуля (`toRollerFormula`: `-1к8` →
`0-1к8`) — ведущий минус перед костью он читал как «минус одна кость» и не
бросал ничего, отчего урон оставался полным. Критическое попадание кости
вычета не удваивает (`isDeductionFormula`): это не кости урона.

**Флаги.** `defense.suppressResistances` — сопротивления урону не действуют,
иммунитеты и уязвимости остаются (`defense.suppressAll` снимает и иммунитеты).
`damage.concentrationDisadvantage` — урон носителя заставляет цель бросать
спасбросок концентрации с помехой; с условием о цели (`rollCondition`) — только
по таким целям (`effectTriggerRunner.imposesConcentrationDisadvantage`).

**Источник спасброска: школа и типы урона** (`engine/saveSourceTraits.ts`).
Условия броска рядом с `source.creatureType`:
`source.spellSchool === "divination"` (школа заклинания, список через запятую)
и `source.damageType === "fire, radiant"` (то, что вызвало спасбросок, наносит
урон одного из типов — считая урон его эффектов и зон). Сведения собирает тот,
кто накладывает (`describeSpellSaveSource`), они едут в цели спасброска и в
нагрузке запроса. Повторные спасброски наложенного эффекта (сервер) их не
знают.

**Условия срабатываний.** `self.hp.max <= N` — максимум хитов носителя не
больше N; `target.isSourceSide === true` — другая сторона события — наложивший
эффект или фишка его стороны («пока вы или ваши союзники не нанесёте урон»);
отношение фишек берётся со сцены, без неё выполняется только для самого
наложившего.

**Концентрация применения** — `activation.concentration: true` (только у
`mode: "use"`): применение идёт как каст с концентрацией — метка у
применившего, прежняя концентрация кончается, с концом этой снимается
наложенное (`effectActivationUse.applyEffectSource`).

**Складывание одноимённых** — `stackable: true` у эффекта: повторное наложение
ложится рядом, а не заменяет прежнее (`effectAutomation.mergeAppliedEffects`).

**Отметка от наложившего.** Отметки с одним ключом от РАЗНЫХ наложивших лежат
рядом («невосприимчив к Ужасающему облику этого привидения»); та же отметка от
того же наложившего обновляется. Счётчик ступеней (`stack`) и отметка без
наложившего — общие, как раньше.

**«Состояние снялось» по сроку.** Событие `conditionLost` приходит и когда
состояние кончилось по сроку (граница хода, счёт раундов —
`dnd5eSystem.expireWithConcentration`). Граница срока отдаёт ядру только
«изменилось ли», поэтому выполняется то, что остаётся на носителе (отметка,
снятие, эффект, урон ему); строка в чат и действия другим сторонам не уходят.
Вне боя сроки не тикают — это ядро.

**«При наложении» у эффекта заклинателя.** Эффекты заклинания «на себя»
уходят боевым снимком, как эффект на цели (`landCasterEventEffects`), — и
событие наложения сервер видит в нём («Связь с иным планом»: спасбросок, урон
и состояние срабатывания). Урон срабатывания с целью «выбранная» у эффекта на
себе бьёт по носителю.

**Действие существа без броска.** Действие без атаки, урона и спасброска с
эффектами «на цель» выбирает получателя на карте — тем же разбором, что
применяемое умение (`applyActionUseEffects`): рецепт «условие при наложении +
спасбросок в срабатывании» собирается и у существ.

**Действие существа со спасброском без урона.** Спасбросок или область в «Бое»
действия без частей урона («Пленяющий стручок», «Господство над разумом»,
«Ужасающий облик» с уроном в эффекте) окна броска не открывает
(`runDamagelessCreatureAction`): бросать существу нечего. Цель (выбранная или
все в шаблоне области) бросает спасбросок действия, эффекты «на цель» ложатся
по исходу — вместе с их собственным уроном (`damageParts` эффекта) и
«только при успехе» (`applyOnSuccessOnly`); эффекты «на себя» — следом. Путь
один у листа существа и горячей панели. Данные менять не нужно.

**Для сайта (core-app):**

- ключи строк (`changes[].key`): `spell.damageType` (значение — ключ типа
  урона, `mode: "override"`), `tempHp.gain`, `attack.reach` (прибавка,
  формула);
- флаги: `defense.suppressResistances`, `damage.concentrationDisadvantage`;
- условия броска (`rollCondition`, условие строки): `source.spellSchool ===
  "<школа, …>"`, `source.damageType === "<тип, …>"`;
- условия срабатываний: `self.hp.max <= <число>`,
  `target.isSourceSide === true`;
- поля: `activation.concentration` — `true`; `stackable` — `true` (поле
  эффекта).

```json
{ "name": "Психические заклинания", "changes": [{ "key": "spell.damageType", "mode": "override", "value": "psychic", "priority": 20 }] }
```

```json
{ "name": "Корона света", "rollCondition": "source.damageType === \"fire, radiant\"", "flags": ["save.disadvantage"] }
```

```json
{ "name": "Дар медузы", "activation": { "mode": "use", "range": 30, "concentration": true }, "effectTarget": "target", "conditionKey": "restrained", "duration": { "type": "minutes", "value": 1 } }
```

```json
{ "name": "Ослабляющий выстрел", "effectTarget": "target", "changes": [{ "key": "damage.all", "mode": "add", "value": "-1к6", "priority": 20 }] }
```

### Ресурс, который не возвращает отдых и который появляется пустым

Ресурс записи (`counters` класса, умения, черты, вида) описывает отдых двумя
способами (`engine/classTypes.ts`, `CounterDefinitionExtras`):

- `recovery` — откат одним словом: `short`, `long`, `short-one`. Слова «не
  восстанавливается» у него нет: продолжительный отдых возвращает всё всегда;
- `shortRest` / `longRest` — раздельные правила `{ mode, amount }`, `mode`:
  `none` | `all` | `amount`. Задано хоть одно — отдых читается по ним
  (недостающее — «ничего»), а `recovery` не читается вовсе. Так же устроен
  счётчик на листе (`getCounterRecoveryRules`) и ресурс на сайте.

До 0.8.190 система читала у определения только `recovery`: выгрузка сайта
отдаёт для «ничего коротким и ничего продолжительным» ближайшее слово `long`, и
«Очки мутации» друида круга мутации восстанавливались продолжительным отдыхом.
Теперь правила определения едут на счётчик (`counterDefinitionRest`) — в мастере
класса, у ресурсов черт и видов; счётчик, заведённый раньше и не настроенный
игроком, получает их на следующем повышении уровня.

`startsEmpty: true` — ресурс появляется на листе пустым (0 из максимума), а не
полным (`initialCounterCurrent`): его набирают действием — эффектом «вернуть
ресурс» с `set` («Очки мутации» — от потраченной ячейки). Без поля — как
раньше, полным. В мастерской мира (класс, умение, черта, вид): поле
«Восстановление» получило четвёртый выбор «Отдых не восстанавливает», рядом —
галочка «Появляется пустым»; раздельные правила, которые выбором не сказать,
форма несёт как есть.

**Для сайта (core-app) и API (core-api):**

- отдых: менять нечего — `mechanics.counters[].shortRest` / `longRest` уже есть
  в записи и в выгрузке (`VttgClass.Counter`, `VttgFeatData.Counter`); «не
  восстанавливается» = оба правила с режимом `NONE`;
- `startsEmpty` — новое необязательное булево поле ресурса
  (`mechanics.counters[]`). Сайту — галочка «Появляется пустым» в форме
  ресурса; API — поле в `ResourceCounter` (JSONB механики: незнакомое поле
  при сохранении теряется) и в обеих выгрузках (`VttgClass.Counter`,
  `VttgFeatData.Counter`), в выгрузку — только `true`.

```json
{ "key": "mutation-points", "name": "Очки мутации", "max": "9 + max(1, @mod.wis)", "recovery": "LONG_REST", "shortRest": { "mode": "NONE", "amount": 1 }, "longRest": { "mode": "NONE", "amount": 1 }, "startsEmpty": true }
```

### Варианты умения класса: выбираемый список и справочный

У умения класса или подкласса бывает список вариантов (`choices`; на сайте —
`options`). Что с ним делает мастер класса и повышения уровня, решает одно:
есть ли у умения настройка выбора (`choiceConfig`; на сайте — `optionsChoice`).

- **Настройка есть — список выбираемый.** Мастер спрашивает столько вариантов,
  сколько в ней указано (`count`, рост — `progression`), и не пускает дальше,
  пока они не выбраны («выбрано N из M»). На лист ложится запись каждого
  выбранного варианта («Боевой стиль: Оборона») с его дарами и эффектами.
- **Настройки нет — список справочный.** Мастер ничего не спрашивает, шаг не
  блокируется, счётчика нет; список показан в строке умения для чтения. Так
  записывают то, чем пользуются по ситуации, а не берут насовсем: мутации
  «Мутирующей формы», таблицу «Волны дикой магии», приспособления ловчего.

До 0.8.192 список без настройки спрашивал ровно один вариант
(`classFeatureChoiceTotalAt`), и мастер требовал «выбрать одну мутацию».
Теперь признак тот же, что у сайта (`isReferenceClassFeatureChoices`).

**Механика вариантов справочного списка** (`choices[].activeEffects`,
`choices[].featData`) не теряется: выбранных у такого списка нет, поэтому она
достаётся владельцу умения ВСЯ (`collectReferenceOptionGrants`). Каждый
открытый вариант со своей механикой получает на листе свою запись («Умение:
Вариант») с эффектами и дарами — тем же путём, что и выбранный вариант; само
умение остаётся своей записью. Вариант без механики записи не получает — он
только в списке. Вариант со своим уровнем доступа (`requiredLevel`) приходит
на этом уровне. Отсюда правило для автора: эффекты вариантов справочного
списка делают включаемыми (`activation`), а не постоянными — постоянный
действовал бы всегда и у всех вариантов разом.

**Свои классы мира (обратная совместимость).** Класс, собранный в мастерской
мира, где у умения есть варианты, а галочка «Из списка выбирают» не стоит,
после обновления перестаёт спрашивать вариант: список стал справочным, а
механика всех его вариантов выдаётся сразу. Если игрок должен выбирать —
откройте умение в форме класса, в блоке «Варианты» отметьте «Из списка
выбирают» и задайте «Сколько выбрать» (и ступени роста, если число растёт).
Галочка сама не ставится при добавлении вариантов.

**Уже собранные персонажи.** У кого в таком умении был «выбран» один вариант
— ничего не ломается: запись варианта («Мутирующая форма: Тёмное зрение») и
её эффекты остаются на листе, сохранённый выбор (`featureChoices`) больше ни
на что не влияет и не показывается. На следующем повышении уровня мастер
докладывает на лист записи остальных вариантов с механикой, которых там ещё
нет (сверка по названию записи и источнику). Запись самого умения, которую
раньше заменял выбранный вариант, задним числом не появляется — её даёт
только повторное взятие класса.

**Для данных сайта:** список, из которого по правилам берут N вариантов
(«изучаете два варианта…»), обязан нести `optionsChoice` — иначе система
выдаст механику всех вариантов сразу.

## Инвентарь существа

У существа, как и у актёра, есть корневая коллекция `equipment` — тот же
`DnDGameItem`, что и в снаряжении листа персонажа, и та же панель
(`ActorEquipmentTab.vue`, параметризована пропом `entity: DnDSceneEntity`).
Хранение бесплатное: хост пишет сущность на диск целиком (`JSON.stringify`), про
корневые коллекции ничего не знает и ничего не вырезает — ровно так же, как
живут `spells` существа.

Что из механики работает одним кодом с листом персонажа: бросок атаки и урона со
строки предмета (включая оружие со спасброском, versatile-хват, магический
бонус, условные бонусы и `@`-формулы), защиты цели по типу урона, эффекты и ауры
надетых предметов, заряды предметов, вес и предел переносимого веса.

Чего у существа нет намеренно:

- **владений оружием и бронёй.** По статблокам 2024-й монстр умеет то, чем
  вооружён: `resolveWeaponProficiency` для существа возвращает `true` всегда, а
  точечно снять бонус мастерства можно режимом `proficiencyMode: 'never'` на
  самом предмете. Заводить существу `system.proficiencies` **нельзя**: в
  `effectPipeline` ветка `system.savingThrows` существа стоит третьим `else if` и
  перехватывается ЛЮБЫМ объектом `proficiencies` — владения спасбросками монстра
  погаснут безусловно. Навыки переживут: у них есть запасная ветка по
  `system.skills`, и погаснут они, только если завести в `proficiencies` ещё и
  `skills`;
- **плитки переносимого веса вместе с её настройкой** — их прячет проп
  `show-carrying-capacity`. Сам расчёт при этом общий и работает (Сила и размер
  у существа есть); скрыт показ: перегруз и у персонажа ничем не грозит, а в
  статблоке монстра лишняя плитка только шумит. Кошелёк (`system.currency`),
  наоборот, у существа ЕСТЬ и показывается. Умолчанием поле не заводится нигде —
  ни в `DEFAULT_CREATURE`, ни в нормализации: пустой кошелёк и отсутствующий
  выглядят одинаково (нулями), а в статблоке 2024-й кошелька нет вовсе;
- **перетаскивания оружия на панель быстрого доступа** (`allow-hotbar-drag`):
  макрос `weapon-attack` ищет владельца среди актёров, и кнопка вышла бы мёртвой;
- **порождения действия статблока.** Надетое оружие НЕ добавляет строку в
  «Действия»: у монстра действие уже описано плоскими числами
  (`CreatureAction.attackBonus`/`damageParts`), и автогенерация дала бы дубль
  строки и дубль на панели быстрого доступа. Два способа бросить — из статблока
  и из инвентаря — живут рядом осознанно.

### Передача предметов между листами

Правило переноса живёт в движке одной функцией — `transferItem`
(`src/engine/itemTransfer.ts`). Сторону обмена она проверяет не по типу
сущности, а по наличию инвентаря (`hasInventory` в `entityGuards.ts`, тип
`DnDInventoryEntity`): участвуют персонаж, существо и любой будущий носитель
предметов — сундук, транспорт, фамильяр, — как только заведёт у себя
`equipment`. Правила переноса при этом править не придётся.

Путей вызова два, и оба идут через одну и ту же функцию:

- **контракт системы** — `transferItemBetweenEntities`, его зовёт ядро при
  перетаскивании токена на токен. На существе пока не срабатывает: ядро ищет
  обе стороны только среди актёров (см. § «Чего не хватает…», п. 13);
- **лист** — предмет перетаскивается из строки инвентаря на другой ОТКРЫТЫЙ
  лист (`useItemTransfer`). Работает уже сейчас и в любую сторону:
  существо → существо, существо → персонаж, персонаж → существо.

Предмет именно ПЕРЕЕЗЖАЕТ: уходит из инвентаря отправителя и появляется у
получателя с новым идентификатором и снятой экипировкой. Отправителя лист
получателя обновляет сам полной записью через сокет — его собственный лист может
быть закрыт, и записать его больше некому. Берётся предмет из инвентаря
отправителя по идентификатору, а не из нагрузки перетаскивания: нагрузка — это
снимок, снятый в начале жеста.

### Класс доспеха и инвентарь

Ветку расчёта КД выбирает **тип сущности**, а не наличие поля `equipment`
(`effectPipeline.ts`, шаг 7). Это не косметика: пока признаком была строчка
`'equipment' in actor`, появление инвентаря у существа увело бы **весь
бестиарий** в актёрскую ветку — и, поскольку владений брони у монстра нет, любой
предмет с известным `baseType` в мешке навесил бы ему пять флагов помехи, включая
`attack.disadvantage` и помеху на инициативу. КД при этом остался бы правильным,
и связать промахи с мешком было бы нечем.

Поэтому по умолчанию КД существа — число статблока, а надетая броня его не
трогает. Вход в расчёт от снаряжения один и явный: способ расчёта `default` в
окне КД (у существа он подписан «От снаряжения»). Способ, которого у записи нет,
читается для существа как `flat` — так ведёт себя статблок.

## Чего не хватает для полноценного SDK

Список получен эмпирически — по тому, что реально пришлось сделать руками, чтобы
система собралась вне монорепы.

1. ~~**Нет опубликованного SDK-пакета.**~~ Пакет не нужен: нейтральное ядро
   `@vtt/shared` (`types`, `contracts`, `VttSystem`, `systemRegistry`, утилиты)
   отдаёт само приложение во время работы — как у Foundry.

   - **Серверу** — загрузчик VTTG 0.9.503+: перед `import()` серверного
     `index.js` он ставит хук разрешения модулей Node, и `import … from
     '@vtt/shared'` получает ТОТ ЖЕ экземпляр ядра, что исполняет сервер, вместе
     с общим `systemRegistry` (`vttg/docs/CREATING_USER_SYSTEM.md` §6.4).
     Доступны корень пакета и подпути из его `exports`: `wsEvents.js`,
     `wsProtocol.js`, `wsClient.js`, `types/index.js`, `constants/permissions.js`,
     `initiativeUtils.js`, `assetPaths.js`; любой другой даёт
     `ERR_PACKAGE_PATH_NOT_EXPORTED`. В сборке ядро помечено external
     (`scripts/lib/serverBuildOptions.mjs`).
   - **Клиенту** — через `globalThis.__VTTHost` (`@vtt/shared` external в
     `vite.config.ts`).
   - **Типы** — из соседнего чекаута `../vttg/packages/shared` (`tsconfig.json`),
     того же, откуда приходят типы модулей `@/…` (п. 7).

   Движок правил при этом целиком живёт в системе и едет внутри бандла — он
   принадлежит системе, а не платформе. Раньше ядро лежало ручной копией в
   `sdk/` и вшивалось в серверный бандл: копия отставала от приложения (на
   2026-09-13 — 11 файлов, около 870 строк), и одна система работала на двух
   версиях ядра — клиент на живом, сервер на копии. Вернуть копию не даёт страж
   сборки (§ «Проверка бандла»). Цена — `compatibility.minimum` не ниже 0.9.503.

   Поверхность ядра, которую реально зовёт серверный бандл, узкая: `isRecord`,
   `generateId`, `isCreatureEntity`, `isActorEntity`, `typedObjectEntries`,
   `removeItems`, `pushUnique`, `isPointInCircle`, `getHealthCondition`,
   `convertDistance`, `HEALTH_CONDITIONS`.
2. **Не опубликован список модулей хоста.** 49 спецификаторов (`@/stores/…`,
   `@/shared_ui/…`, `@/core/…`, `pinia`, `@vueuse/core`, `@nuxt/ui/composables`),
   которые система резолвит в рантайме из `globalThis.__VTTHost`, перенесены
   вручную. Это главный публичный контракт платформы — он должен versioned-ся.
3. **Не опубликован пресет сборки.** Три обязательные настройки (`define`
   process.env, `interop: 'esModule'`, отключение авто-импорта компонентов Nuxt UI)
   воспроизведены вручную; при ошибке любая из них ломает систему неочевидно.
4. ~~**Самоссылки через алиас приложения.**~~ Закрыто у себя: исходники ссылались на
   собственные файлы как `@/systems/dnd5e/…` — снаружи такого пути нет, и он держался
   на алиасе сборки. Все такие импорты переписаны на относительные пути, алиас убран
   из `vite.config.ts` и `tsconfig.json`. Для внешнего автора грабли остаются: файл,
   переехавший из монорепы, приносит такой адрес с собой и молча собирается только
   при своём алиасе.
5. **Ассеты приложения по абсолютным URL.** `/assets/modals/*.webp` отдаёт веб-корень
   VTTG; при внешней сборке их надо помечать внешними, иначе сборка падает.
6. **Идентификатор системы зашит в трёх местах:** `system.json`, `systemEntry.ts`
   (вызов `VTTSystems.register`) и движок (`readonly id`, `systemId`). Для системы,
   которую предлагается копировать и переименовывать, id должен браться из манифеста
   в одном месте.
7. **К модулям хоста не поставляются типы.** Пункт 2 — про список
   спецификаторов, этот — про их сигнатуры. У 287 импортов `@/…` (45 уникальных
   модулей) локального исходника нет, и проверить их нечем.

   **Решение:** `tsconfig.json` резолвит `@/*` в СОСЕДНИЙ чекаут монорепы
   (`../vttg/packages/client/src/*`), а оттуда же — и ядро `@vtt/shared`
   (`../vttg/packages/shared`). На сборку это не влияет — файл существует
   только ради редактора (`noEmit`), а пути сборки живут в `vite.config.ts`.
   Деградация мягкая: без соседнего чекаута возвращаются `TS2307` на эти
   импорты, и ничего не ломается.

   Цена отсутствия этих типов измерена: 55 × `TS2307` и 46 × implicit any
   (при том что `any` запрещён правилами проекта), а под масками `any`
   скрывались настоящие расхождения — они всплыли сразу, как только путь
   появился. Заглушки `declare module '@/*'` эту дыру не лечат, а маскируют.
   Отдельного пакета с `.d.ts` модулей хоста и ядра не планируется: источник
   типов — соседний `../vttg`, и строка `@/*` остаётся.

   Побочный эффект: `npm run typecheck` может показывать ещё и ошибки САМОГО
   хоста (в разное время это были `systemBootstrap.ts` TS7017, `UColorPicker.vue`
   — `EyeDropper`, `useFolderTreeController.ts` — `ContextMenuItem` из
   `@nuxt/ui`). Они по ту сторону границы и правятся только на стороне хоста.
8. ~~**Глобал `VTTSystems` не типизирован.**~~ Закрыт пунктом 7: объявление
   `declare global { var VTTSystems }` живёт в `core/systemBootstrap.ts` хоста
   и подхватывается вместе с остальными его типами. Отдельной декларации в
   системе не нужно: пакета с `.d.ts` не планируется, типы по-прежнему идут из
   `../vttg`. `TS7017` вернулся бы, только если `@/*` перестанет смотреть в
   монорепу.
9. **Типы `@nuxt/ui` не достаются из корневого входа.** `import type
   { DropdownMenuItem } from '@nuxt/ui'` не резолвится: корневой вход пакета —
   это Nuxt-модуль, а типы компонентов в Nuxt-приложении подставляет
   авто-генерация `#ui`, которой при обычной Vite-сборке нет. Приходится
   импортировать из подпути (`@nuxt/ui/components/DropdownMenu.vue`). Тем же
   болеет и сам хост (`useFolderTreeController.ts`).
10. **Нет dev-режима доставки системы.** Внешнему автору доступен только цикл
    «пересобрал → положил папку → перезагрузил страницу» (его и автоматизирует
    `npm run dev`). HMR упирается ровно в три места контракта загрузчика, и все
    три — на стороне хоста:

    - клиент подключается КЛАССИЧЕСКИМ `<script>` (`clientSystemLoader.ts`), а не
      `type="module"` — ESM с dev-сервера так не загрузить;
    - путь точки входа обязан быть относительным (`isSafeRelativeAssetPath`), а
      файлы отдаются только из папки системы через хэш-гейт доверия — то есть
      указать адрес dev-сервера нельзя **by design**;
    - реестры (листы, макросы, типы предметов) заполняются один раз при
      `register()`, поэтому даже с рабочим HMR правка не-Vue модуля требовала бы
      своего `accept` с `unloadClientSystem()` + `runSystemRegistration()`.

    Что при этом УЖЕ готово со стороны хоста: `globalThis.Vue` в dev — это
    dev-сборка Vue, а значит `__VUE_HMR_RUNTIME__` на месте, и SFC свопились бы
    штатно. Externals (`@/…`, `pinia`, `@nuxt/ui`) в dev-графе решаются
    плагином-виртуалкой поверх `globalThis.__VTTHost`. То есть недостающее — это
    небольшая dev-only лазейка в загрузчике (под `isDev` + localhost), и её
    место — в SDK-контракте, а не в обходных путях каждой системы.

11. ~~**Компоненты `@/shared_ui/…` не расширяемы слотами.**~~ Закрыт со стороны
    хоста в VTTG 0.9.348: у `FieldsetLabel.vue` появился слот `actions` —
    кнопки блока (шестерёнка настройки, сброс) встают справа от подписи. До
    него системе оставался свой дубль контейнера, расходящийся с оригиналом при
    каждой его правке. Общее правило осталось прежним: чего не хватает в
    блоке-обёртке хоста — добавляется слотом ТАМ, а не копией здесь.

12. **У зрения токена есть только тёмное зрение.** `Token.vision` в `@vtt/shared`
    (`../vttg/packages/shared/src/types/base.ts`) знает
    `enabled`/`range`/`darkvision`/`angle` — слепого зрения, истинного зрения,

24. **Ядро не отдаёт данные, без которых часть правил эффектов не собрать.**
    Доработка эффектов (`docs/EFFECT_SCENARIOS.md`) упиралась в контрактные
    дыры. Три из них закрыты со стороны хоста (VTTG 0.9.533+), причём две
    были записаны слишком сильно: данные у ядра были, их просто не отдавали
    системе.

    - ~~**номер раунда не доезжает до правил**~~ — закрыто: в
      `SystemTriggerContext` появился `getCombatRound()`. Раунд ядро знало и
      раньше (`EncounterState.round`, срок зон в раундах). На клиенте номер
      берётся из трекера инициативы, как и «чей ход». Отсюда расписание
      «на раунде N» (E17);
    - ~~**маршрут фишки не отдаётся системе**~~ — закрыто. Маршрут система
      видела и раньше: ядро зовёт `syncAreaEffects` и
      `applyAuraTriggerEffects` на каждой клетке пути. Не было длины пути и
      разового вызова на всё перемещение — теперь есть
      `applyMovementEffects(entity, movement)`: длина в футах по правилу
      диагоналей сетки (та же функция, по которой клиент красит запас хода),
      пройденные клетки и признак «переставили правила». Отсюда событие
      «Когда носитель проходит путь» (E09);
    - ~~**область нельзя переставить и нельзя нарисовать стеной**~~ — закрыто.
      Стена была и раньше: луч шаблона с шириной — вытянутый прямоугольник, и
      зона заклинания повторяет его клетка в клетку (Z19). Переставить область
      система теперь может через `moveArea(areaId, {dx, dy})`, а вершины
      областей сцены приходят в `getSceneSurroundings().areas`. Отсюда
      действие «Сдвинуть зону» (Z18). Переместить зону действием в
      выбранную точку по-прежнему нечем: «При действии» — клиентский путь без
      контекста правил (Z18b).

    Открытыми остаются три дыры:

    - **игрового времени нет вовсе** — ни часов мира, ни «прошло N минут».
      Без него не собрать срабатывание по времени и отсрочку в минутах
      (пробелы E16, E18);
    - **у фишки нет третьей координаты.** Расстояния считаются на плоскости,
      поэтому высота области остаётся плоской (Z20);
    - **видимость пары существ ядро системе не отдаёт.** У фишки есть зрение,
      тёмное зрение, угол обзора и свет, а системе приходят соседние фишки
      целиком — но не стены: без них «видит» нельзя посчитать честно.
      Отсюда молчат условия «вижу / в темноте», событие «на глазах ранили
      союзника» и выданные чувства в расчёте сцены (TC09, E14, K10). Свет от
      носителя (K09) — отдельный вопрос, его ядро берёт хуком (п. 33).

    Правило №0 соблюдено: ни одна из этих дыр не подменена внутри системы.
    Там, где данных нет, срабатывание молчит, а настройка в окно не
    предлагается, — каждая записана строкой `⛔` в каталоге сценариев.

    Со стороны системы всё готово, кроме отправки: вопрос собирает

    Запретить»), у ведущего его откроет то же окно вопроса, что и у
    срабатываний, а `readGmApprovalVerdict` засчитывает только ответ ведущего — иначе
    игрок перехватил бы свой запрос и разрешил бы себе сам. Нужно от ядра:
    адресат «ведущие в сети» в `RollRequestOptions` и
    `ServerRollRequestOptions` (внутри сервера такой адресат уже есть —
    `RecipientBasis 'admins'`), а перехват такого запроса — только ведущим.

    Подменять адресата (слать запрос игроку «самому себе», чтобы ведущий
    перехватил его из списка ожидающих) система не стала — правило №0.

26. ~~**Выбранная цель помечена цифрой «1».**~~ Закрыто со стороны хоста
    (VTTG 0.9.546+): в режиме `distinct` над выбранной фишкой галочка вместо
    числа. На VTTG старше остаётся «1» — это только вид, правилам не мешает,
    поэтому `compatibility.minimum` ради него не поднимается. Что было:

    Режим выбора целей на карте
    (`projectileStore`) система включает и для целей эффекта, и для
    получателя предмета — в режиме `distinct`, где у каждого ровно одна
    отметка. Ядро же всегда рисует над фишкой число снарядов
    (`SceneTokenLabels.vue`), и «1» читается как «первый из нескольких».
    Нужно от ядра: в режиме `distinct` показывать отметку вместо числа.
    Своего значка поверх сцены система не рисует — правило №0.

26. **Марка броска `{@roll …}` — контракт хоста без экспорта.** Кнопкой её

27. **У слота панели быстрого доступа нет состояния «включено».** Кнопка

28. **Категории снаряжения — закрытый список D&D в нейтральном ядре.**

    обход станет единственным источником списка.

29. **Значок слота панели быстрого доступа застывает при перетаскивании.**

    **Сейчас в системе:** значок кнопки применения берётся функцией
    `getItemIcon` (`src/client/ui/actor/utils/itemIcon.ts`) — той же, что
    рисует строку инвентаря, так что при перетаскивании они совпадают. Нужно
    от ядра: поле вроде `icon?: string` в `MacroSlotState`, которое слот
    предпочитает сохранённому, и показ картинки по URL в `HotbarPanel`.

30. ~~**Границы ходов доходят только до участников боя.**~~ Закрыто со стороны
    хоста в VTTG 0.9.597: `VttSystem.expireTurnEffects` и `runSourceTurnEffects`
    ядро зовёт для каждого актёра и существа мира, по разу на сущность
    (`expireTurnEffectsForAll` и `applySourceTurnEffects` в
    `vttg/packages/server/src/modules/initiative/initiativeModule.ts`), а
    `participantIds` остаётся составом боя. Раньше границы доходили только до
    `encounter.entries`: эффект «до конца следующего хода наложившего» на
    существе, которого нет в инициативе, не истекал никогда («Ужас дракона» на
    живой проверке 02.10: герой в бою, цель — нет), срабатывания «в конце хода
    наложившего» у такого носителя молчали.

    **Сейчас в системе:** эффект носителя вне боя, который ждёт хода
    наложившего-участника, истекает точно — на границе этого хода. Границей
    раунда (`expireOutsiderTurnEffects` из `decrementEffectDurations`) срок
    идёт только там, где ждать нечего: срок по собственному ходу носителя вне
    боя и по ходу наложившего, которого в бою тоже нет, — первый раунд снимает
    пропуск «хода наложения», следующий — сам эффект. На ядре старше 0.9.597
    раунд служит границей всем turn-эффектам такого носителя: система узнаёт
    новое ядро по первой границе хода, пришедшей сущности вне боя, и до неё
    точный срок не ждёт (иначе на старом ядре эффект висел бы вечно, а на
    новом срок шёл бы дважды).

31. **Полоса хитов над фишкой не знает итогового максимума.** Ядро рисует её
    по `system.hitPoints.max` как по непрозрачному блобу (`useSceneTokens`), а
    в контракте `VttSystem` нет метода «максимум хитов сущности». Итог системы
    (`resolveEntityMaxHp`) — это запись листа плюс эффекты `hitPoints.max`
    («Ложная жизнь») и Телосложение сверх листа: прибавки предыстории и
    повышения характеристик лежат эффектами, и их модификатор входит в хиты
    каждого уровня. Лист, лечение и бой считают по итогу, полоса — по записи.

    **Сейчас в системе:** итог отдаётся везде, где читает сама система, и в
    сводке HUD. Нужно от ядра: метод вроде `VttSystem.getEntityMaxHitPoints`
    (или использование `getEntityHitPoints` и для полосы над фишкой).

32. **Серверная часть системы не видит записи мира, а сущности нормализуются
    не на каждой записи.** Состояния мира («Мастерская» → «Состояния») живут
    записями `items`, и сервер системы о них не знает: правки канона и правило
    «вешать автоматически» (`autoConditions.ts`, «Окровавленный» при половине
    хитов) работали бы только в браузере, а урон и эффекты хода считаются на
    сервере. Сами правила пересчитываются в `normalizeActor` /
    `normalizeCreature`, но ядро зовёт их на сервере только при загрузке мира,
    а на клиенте — для существ на каждом обновлении, для персонажей никогда.

    **Сейчас в системе:** правило состояния, разбор записей мира на сервере
    (`Dnd5eSystem.onWorldItemsChanged`) и пересчёт в нормализации.

> **Закрыто на стороне хоста (VTTG 0.9.575+):** хук
> `VttSystem.onWorldItemsChanged(items)` — после загрузки мира и после каждой
> правки записи; `normalizeActor` / `normalizeCreature` зовутся сервером перед
> сохранением и рассылкой каждой записи сущности (создание, правка,
> `commitSystemMutation`) и клиентом при приёме актёра, как у существ
> (`server/src/core/systemEntitySync.ts`). На более старом VTTG значки по
> правилу сверяются только при загрузке мира и у существ на клиенте.

> **Закрыто на стороне хоста (VTTG 0.9.427+):** панель выделенного токена больше
> не актёрская. `WorldScene` резолвит выделение в `selectedEntity` (актёр ИЛИ
> существо), панель переименована в `SelectedEntityPanel` и принимает
> `SceneEntity`, хиты берёт через `getEntityHitPoints` (устаревший
> `getActorHudSummary` остался запасным путём), а в `UiSystem` появился третий
> слот — `quickActionsModal`. Система его занимает `QuickCreatureActionsModal`;
> кнопку действий ядро показывает только у существа. Быстрые окна снаряжения и
> заклинаний тоже приняли существо: проп `actorId` у всех трёх окон теперь несёт
> идентификатор любой выделенной сущности.


33. ~~**Свет фишки не спрашивает систему.**~~ Закрыто со стороны хоста в
    VTTG 0.9.580: хук `resolveEntityLight` ядро зовёт при расчёте света фишки
    и в подписи перерисовки. Было так: сцена брала свет фишки только из
    её настроек `token.light` (`computeTokenLightSources`,
    `useTokenLightSources.ts`; перерисовка — по `tokenLightSignature`,
    `useSceneLightingManager.ts`), и у контракта `VttSystem` нет хука, через
    который система дала бы свет от эффекта. Переписывать `token.light` из
    системы нельзя: это настройка ведущего, и снятие эффекта затирало бы её.

    **Нужно в ядре:** необязательный хук
    `VttSystem.resolveEntityLight?(entity): Partial<LightEmitter> | undefined`
    по образцу `resolveEntityVision` — ответ поверх `token.light` (берётся
    сильнейший), учёт ответа в `computeTokenLightSources` и в подписи
    перерисовки света (как у хэша зрения в `useSceneVision`).

    **Что сделано в системе:** поле эффекта `light`, итог носителя и метод
    `Dnd5eVttSystem.resolveEntityLight`. Хук необязательный: старое ядро его
    не зовёт, и нижняя версия хоста из-за него не поднималась.

34. **Граница срока эффекта отдаёт ядру только «изменилось ли».**
    `VttSystem.expireTurnEffects` и `decrementEffectDurations` возвращают
    `boolean`, а не `SystemDeferredTriggerResult`, как остальные хуки
    срабатываний. Поэтому срабатывание «Когда с носителя снимается состояние»
    (`conditionLost`), пришедшее по истечении срока, может изменить только
    самого носителя: строку в чат, спасбросок по запросу владельцу и правки
    других сторон («урон тому, кто наложил») системе отдать некуда.

    **Сейчас в системе:** событие по сроку прогоняется
    (`expireWithConcentration` в `dnd5eSystem.ts`), выполняется то, что
    остаётся на носителе (отметка, снятие, эффект, урон ему), спасбросок
    бросает сервер; остальное молча не уходит. **Нужно от ядра:** тот же
    итог `SystemDeferredTriggerResult` у двух хуков срока (сводка, отложенные
    броски, `related`). Вместе с п. 30: вне боя сроки не тикают, и событие
    не приходит вовсе.

35. **Полная запись сущности не сливается и не знает версии.**
    `actor:updated` / `creature:updated` заменяют сущность тем, что прислал
    клиент. Системе в `normalizeActor` прежнюю сущность не дают — слить
    пришедшее с тем, что сервер изменил после копии клиента, ей не из чего, а
    отказа «устаревшая запись» у ядра нет. Изменение сервера, не дошедшее до
    клиента (конец каста другого заклинателя, урон, легшая метка), полной
    записью затирается.

    **Сейчас в системе:** боевой снимок несёт разницу эффектов и журнала
    срабатываний и сливается на сервере системой (`combatEffectChanges.ts`);
    полная запись во время игры собирается одним помощником
    (`changeEntitySheet` в `entitySheetWrite.ts`) из свежей сущности в
    момент отправки, меняет только разделы листа (ячейки, заряды, счётчики,
    предметы), не трогает хиты и эффекты и несёт журнал, посланный своими
    боевыми снимками. Окно «до ответа сервера» сужено, но не закрыто: запись,
    ушедшая раньше, чем пришёл ответ на чужую правку, всё ещё её затрёт.
    Сохранения листов и окон настройки остаются полной записью — это правка
    владельцем. **Нужно от ядра** одно из: `VttSystem.mergeEntityUpdate(existing,
    incoming, user)` — система сливает запись с прежней сущностью; канал
    правки разделов `entity:patch`; номер ревизии сущности с отказом
    устаревшей записи.

36. **Менеджер окон закрывает окно молча.** `closeModal(id)` убирает окно,
    но обработчик `onUpdate:open` из его свойств не зовёт: тот срабатывает,
    только когда окно закрывает себя само. Тому, кто закрывает чужое окно
    программно, неоткуда сообщить открывшему, что окно закрыто.

    **Сейчас в системе:** окно броска, которое заменяется повторным действием
    того же источника, закрывает помощник `closeRollWindow`
    (`diceRollWindow.ts`). Обработчик закрытия вызывающий отдаёт помощнику
    (`onClose`), тот хранит его рядом с id окна и зовёт сам после
    `closeModal` — свойства окна в менеджере для этого не читаются.
    **Нужно от ядра:** `closeModal` зовёт `onUpdate:open(false)` закрываемого
    окна либо принимает признак «сообщить окну».

37. **Ядро шлёт боевой снимок, который ничего не меняет, и само же о нём
    предупреждает.** `targetStore.applyToTarget` / `applyEffectsToTarget`
    (`packages/client/src/stores/targetStore.ts`) зовут
    `emitEntityCombatState` всегда, даже когда хук системы цель не изменил
    (удар по существу с 0 хитов, «-0 HP»); сервер такой снимок отвергает и
    пишет «снимок отвергнут системой: неверная форма либо ничего не
    изменилось» (`entityManager.ts`, `applyCombatState`).

    **Сейчас в системе:** свои снимки помощник записи не шлёт, когда менять
    нечего (`changesCombatState`); снимки ядра ей не подвластны — удар
    оружием и урон окна броска по цели с 0 хитов по-прежнему дают
    предупреждение. На игру оно не влияет.
    **Нужно от ядра:** либо `targetStore` не шлёт снимок без изменений
    (сравнить копию до и после хука), либо сервер различает «ничего не
    изменилось» (молча) и «неверная форма» (предупреждение).

## Проверка бандла

Проверки живут в `scripts/lib/bundleChecks.mjs` и стоят и в `npm run build`, и в
`npm run dev`: негодный бандл сборку роняет, а в watch-режиме не ставится в
приложение.

### Сервер — `dist/index.js`

Страж смотрит граф модулей esbuild (`metafile`), а не текст бандла:

- **в бандле нет копии ядра** — ни один входной файл не лежит в `sdk/`, в
  `…/packages/shared/…` или в `node_modules/@vtt/shared/…`. Иначе сервер системы
  снова работает на своей, отстающей версии ядра, а клиент — на ядре приложения,
  и `systemRegistry` копии расходится с приложением. Типичная причина — алиас
  `@vtt/shared` на `../vttg` вместо `external`;
- **у приложения просят только то, что оно отдаёт** — корень `@vtt/shared` и
  подпути из его `exports` (п. 1 § «Чего не хватает для полноценного SDK»).
  Иначе Node роняет загрузку `index.js` с `ERR_PACKAGE_PATH_NOT_EXPORTED`.

Сборка печатает, что именно бандл берёт у приложения:
`[build-server] dist/index.js готов, от приложения: @vtt/shared`.

### Клиент — `dist/client.js`

После сборки `dist/client.js` обязан пройти пять проверок (иначе система молча
не поднимется в приложении):

- нет `process.env` — иначе `ReferenceError` до регистрации;
- есть вызов `VTTSystems.register`;
- нет своей копии `reka-ui` — иначе падает `setup` компонентов приложения;
- динамические `import('@/…')` переписаны на `globalThis.__VTTHost` — иначе они
  падают в браузере асинхронно;
- ассеты приложения (`/…`) не попали в реестр модулей хоста — иначе
  «Cannot read properties of undefined» при отрисовке.

Сборка печатает, сколько модулей бандл берёт у приложения через
`globalThis.__VTTHost` (`модулей хоста N`).
